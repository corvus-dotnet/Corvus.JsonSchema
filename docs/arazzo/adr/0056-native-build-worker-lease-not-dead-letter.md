# ADR 0056. The native-build worker claims under an advisory lease, and a failed build is terminal, not dead-lettered

Date: 2026-07-26. Status: **Accepted**. Scope: how the asynchronous native-publish build worker ([ADR 0055](0055-serverless-backend-aot-from-signed-executor.md)) claims build jobs, reclaims a build orphaned by a crashed worker, and records a failure. Builds on the store-as-queue ([ADR 0023](0023-two-process-store-as-queue.md)) and the advisory run lease ([ADR 0027](0027-runner-environment-binding.md)).

ADR 0055 made publishing a version to a serverless environment asynchronous. A build job moves through queued, building, then ready or failed, and the compile takes minutes. This record settles two questions that surfaced while the build worker was built: whether a repeatedly-failing build needs a poison or dead-letter queue, and why the build worker's claim does not reuse the advisory lease the run worker's claim uses. It carries forward the async-publish decision from 0055 and does not change it.

## Context

The native-publish state machine is a keyed entity. A `NativeBuildJob` is keyed by its target tuple (base workflow id, version number, environment, runtime identifier), so enqueuing a build is an idempotent upsert and a rebuild resets the same job to queued. A worker claims the oldest queued job, transitions it to building, native-AOT compiles and signs the version's binary, persists the binary back into the version, and completes the job ready or failed.

The same problem the build worker faces, one worker advances a durable unit of work at a time and a crashed worker's in-flight work is recovered, is already solved for runs. A run is a durable checkpoint in the shared store, advanced under an advisory single-owner lease with the etag as the authoritative guard ([ADR 0023](0023-two-process-store-as-queue.md), [ADR 0024](0024-collectible-assembly-per-version.md)). The build worker was built with the atomic claim but without that lease, which is what raised the two questions.

### Grounded architectural facts

- **The build claim is atomic, and the etag is the correctness guard.** `ClaimNextQueuedAsync` transitions the oldest queued job to building under each backend's native atomic primitive (`FOR UPDATE SKIP LOCKED` on Postgres and MySQL, `UPDLOCK, READPAST` on SQL Server, a conditional `FindOneAndUpdate` on Mongo, an optimistic compare-and-set on the document and key-value backends). Completion is guarded by the `WorkflowEtag`. A re-enqueue during a build changes the job's etag, so the in-flight worker's completion no longer matches and is abandoned. The conformance suite proves two workers never claim the same queued job.
- **The run lease is advisory; the run etag is authoritative.** The lease coordinates well-behaved workers and expires on a TTL so a crashed holder's run is reclaimed, but the authoritative guard against a double-advance is the etag on save, not the lease. A run is reclaimable exactly when it is running and no live lease is held.
- **A build is a one-shot idempotent operation.** Unlike a run, a build has no suspend and resume and is not re-entered across steps. Its only durable output, the native binary attached back into the version, is persisted only on success. So a crashed build has nothing to resume, and the correct recovery is simply to build again.

## Decision

**A failed build is a terminal state, not a dead-lettered message. There is no poison queue.** A dead-letter queue exists to stop a poison message blocking a redelivery queue, and to preserve a message that would otherwise be dropped after a number of failed deliveries. The build state machine is a keyed entity store, not a redelivery queue. The claim takes only queued jobs, and a failed build moves to the terminal failed state, so a failure never re-feeds the next worker and never blocks the queued jobs behind it. There is no automatic retry, because a rebuild is an explicit idempotent re-enqueue that resets the same job to queued. A failed job is a durable queryable row carrying the failure reason, the target, and the audit fields, so filtering jobs by the failed status is the inspection surface a dead-letter queue would otherwise provide. Both dead-letter purposes, do not block and do not lose, are already met by the failed state.

**Correctness rests on the etag, exactly as run advancement does.** The atomic claim, the etag, and abandoning a superseded completion together guarantee a job is neither advanced twice nor lost, with no lease involved. This is the same division of labour the run store makes: the lease is advisory and the etag is authoritative.

**Liveness and crash-reclaim use an advisory lease, mirroring the run lease, adapted for a one-shot operation.** Without a lease, a build orphaned by a worker crash sits in building forever, because the claim otherwise takes only queued jobs. So the build worker adopts the run store's lease model, with one adaptation. The lease lives on the job entity itself, a `leaseExpiresAt` with the claiming worker as owner and the etag as the ownership token, rather than in a separate advisory-lease primitive, because the build claim is already atomic at the row level and needs no cross-re-entry coordination. The claim takes the oldest job that is either queued or building with an expired lease, so an orphaned build is reclaimed the same way a run with no live lease is. The worker renews the lease on a heartbeat while the compile runs. That heartbeat is the one real difference from a run, which renews its lease at the step boundaries where it is re-entered. A build has no step boundaries, so it renews on a timer while it awaits the builder, with a TTL set comfortably above a normal build time.

**A fixed-timeout reclaim without renewal is rejected.** A sweep that reclaims any building job older than a fixed timeout, with no lease renewal, either fires too early and reclaims a legitimately slow build (producing a redundant second build) or too late and recovers a real orphan slowly. The lease with renewal removes that tension, so it is preferred over a bespoke stale-building sweep.

The lease and reclaim are implemented after the serverless end-to-end integration proof, because they are liveness and not correctness (below), and the integration proof validates the novel part, a real container Native-AOT compile end to end. This ADR is **Accepted**: the no-poison-queue and etag-correctness decisions already hold in the shipped worker, and the lease and reclaim are the accepted design for the orphan-liveness gap, implemented next.

## Consequences

- A build orphaned by a worker crash is reclaimed automatically once its lease expires, with no operator action and no separate reclaim sweep.
- The lease is a liveness optimisation, not a correctness dependency. Even two concurrent builds of one target during a lease handoff are safe, because each build is idempotent and only one completion wins under the etag while the other is superseded. So the lease is added after the shipped worker without reworking its correctness.
- A failed build is recovered by an explicit re-enqueue, which resets the same job to queued idempotently. There is no automatic retry and therefore no attempt cap to tune. An attempt cap becomes relevant only if a future change introduces automatic retry.
- The failed status is the diagnostic surface. The failure reason is a bounded tail of the build log, which is where a Native-AOT compile reports its error. If operators later need the full compiler and linker log, the right home is a build-log artifact stored per job, a diagnostics store and not a queue, and it is additive.
- The build worker does not depend on the run store's lease table. It mirrors the lease model on its own entity, and the two remain separate stores with the same lease semantics.
