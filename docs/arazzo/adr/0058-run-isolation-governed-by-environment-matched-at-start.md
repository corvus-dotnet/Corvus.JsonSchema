# ADR 0058. A run's required isolation is governed by its environment, advertised by runners, and matched at the start gate

Date: 2026-07-27. Status: **Accepted**. Scope: how the pluggable execution-backend seam ([ADR 0055](0055-serverless-backend-aot-from-signed-executor.md), which replaced the proposed [ADR 0028](superseded/0028-pluggable-execution-backends.md)) becomes selectable. That is, how a run's required isolation is expressed, how a runner advertises the isolation it provides, and where dispatch matches the two. Builds on the runner registry and the runner-environment binding ([ADR 0027](0027-runner-environment-binding.md)) and the start gate ([ADR 0026](0026-triggers-async-by-default.md)).

## Context

Phase 1 extracted `IRunExecutionBackend` with a coarse `RunIsolationModel` of `InProcess` or `Isolated`, and the serverless backend (ADR 0055) implements `Isolated`. Nothing selects it. Today the start gate (`startCatalogWorkflowRun`, and the schedule fire path) admits a trigger only if a live runner hosts the targeted version, via `IRunnerRegistry.IsVersionHostedAsync(baseWorkflowId, versionNumber)`. That check is isolation blind, so an `Isolated` runner and an in-process runner are interchangeable to it, and the serverless backend is dead code outside its tests.

Three questions settle the selection layer: where a run's required isolation comes from, what a runner advertises, and where the match happens. The hosting scan is on the dispatch hot path (it runs on every trigger), so any addition to it must stay allocation free and string free, the way the existing `RunnerRegistration.HostsVersion` predicate already is (it enumerates the registration document's bytes and compares values, realising no strings).

## Decision

**A run's required isolation is governed by its environment.** An environment carries a `requiredIsolation` policy (`InProcess` or `Isolated`, default `InProcess`) alongside its existing governance flags (`requireEvidence`, `allowsDraftRuns`). It is not declared on the version and not requested per run. The environment is the security anchor for any out-of-process backend (one environment per runner, admin authorized; a function or guest executes with the environment's credentials), so mandating isolation is an environment governance decision, set by an environment administrator. A version is not intrinsically bound to an isolation model. It is dispatchable to any environment whose runners provide that environment's required isolation. A default of `InProcess` makes every existing environment behaviour preserving: nothing is gated unless an administrator opts an environment into `Isolated`.

**A runner advertises a single runner-level isolation model.** Its `RunnerRegistration` carries an `isolationModel` (`InProcess` or `Isolated`), the model its configured backend provides (from `IRunExecutionBackend.IsolationModel`). One environment per runner and one backend per runner means one advertised model per runner; a mixed-mode runner is not a shape this model needs.

**Dispatch matches at the start gate.** `RunIsolationModel` is a comparable strength axis where `Isolated` is stronger than `InProcess`, so a runner satisfies a requirement when its advertised model is at least as strong as the required one (an `Isolated` runner can serve an `InProcess` requirement, not the reverse). The start gate resolves the target environment's `requiredIsolation` from the environment document it already loads for the reach check, then admits the trigger only if a live runner in that environment both hosts the version and advertises a sufficient isolation model. When none does, it returns `409` naming the missing isolation. Among satisfying runners a warm one (the version already `loaded`) is preferred, extending the existing warmth signal rather than adding a new one.

**The match stays on the string-free hot path.** The isolation comparison is added to `RunnerRegistration.HostsVersion` as a value compare over the registration document's `isolationModel` (the enum's wire token compared as UTF-8, no string realised), in the same shape as the existing base-workflow-id and version compares. The environment's `requiredIsolation` is realised only at the leaf, from the already-parsed environment document, never threaded as a string through the scan. The registry seam gains an isolation-aware `IsVersionHostedAsync` overload; the isolation-blind overload remains for the read surfaces that do not gate on it.

## Consequences

- The serverless (`Isolated`) backend becomes selectable: an environment set to `requiredIsolation = Isolated` routes its runs to runners that advertise `Isolated` and host the version, and refuses the trigger otherwise.
- Existing environments and runners are unaffected. `requiredIsolation` defaults to `InProcess`, `isolationModel` defaults to `InProcess`, and the isolation-blind hosting reads keep working, so the change is behaviour preserving until an administrator opts in.
- Isolation is expressed once, on the environment, as a governed policy an administrator controls, rather than scattered across versions or per-run requests. If a future need arises for a version to raise the floor (a workflow that must never run in-process regardless of environment), that is an additive version-level minimum layered on this environment floor, not a change to it.
- The match gates on hosting and isolation only. Gating dispatchability on the target's native binary being built and deployed (`INativeBuildJobStore.IsTargetReadyAsync`) is the adjacent readiness concern, wired alongside this in Phase 2.
- The dispatch hot path keeps its allocation posture: the added comparison realises no strings, so the scan's cost is unchanged.
- This moves the pluggable-backend seam from advertised-but-unselectable to selectable. It does not add a new backend; the serverless backend it makes reachable is ADR 0055's.
