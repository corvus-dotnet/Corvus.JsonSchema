# ADR 0059. The serverless deploy and invoke run on the runner as the secure boundary, and the control plane holds no user cloud secrets

Date: 2026-07-27. Status: **Accepted** (the callback-token construction in decision 5 is the accepted direction, pending a security review before it ships). Scope: how deploying a version's signed native binary to a function platform, invoking the deployed function, and the function's callback to the checkpoint endpoint are secured. That is, where each operation runs, what identity it uses, and how an operator configures a runner securely. Builds on the signed-artifact chain ([ADR 0055](0055-serverless-backend-aot-from-signed-executor.md)), the runner-environment binding ([ADR 0027](0027-runner-environment-binding.md)), the isolation match ([ADR 0058](0058-run-isolation-governed-by-environment-matched-at-start.md)), and the source-credential and secret-resolver model (§13).

## Context

ADR 0055 built the serverless backend up to a signed native binary attached to a version's package, verifiable with `WorkflowAotBuildService.VerifyNativeArtifact`. What remains is to deploy that binary to a function platform (AWS Lambda first) and invoke the deployed function. These are new operations, and unlike build and sign they cross into the user's own cloud account and back.

The platform already has a security model that these operations must honour. The runner is the environment's execution agent. It holds the environment's credentials, which are resolved at use time from the user's own secret store through the deployment's `ISecretResolver` and are never persisted (§13, secrets are references). The control plane governs (it catalogues, builds, signs, and gates) but it does not custody the user's secrets. Deploying to and invoking a function in the user's AWS or Azure account needs the user's cloud credentials, so the question is which component holds them and where each operation runs.

There are four trust boundaries in the serverless path:

1. Build and sign the native binary. This is a control-plane operation against its own signing key, not the user's account.
2. Deploy the signed binary into the user's cloud account. This needs the user's cloud credentials.
3. Invoke the deployed function. This needs the user's cloud credentials.
4. The function's callback to the runner's checkpoint endpoint (§6b). This is the function authenticating to a platform surface.

## Decision

**1. The runner is the secure boundary, and the control plane holds no user cloud secrets.** The control plane builds and signs the native binary and coordinates deployment and dispatch state, but it never holds the user's AWS or Azure credentials. The runner already holds the environment's credentials, resolved from the user's own secret store, and it is the only component that acts inside the user's cloud account. This keeps the control plane out of the custody chain for the user's cloud, the same boundary the store-abstraction decision already draws (the serverless function reaches the durable store over HTTP through the runner, not with its own store credentials).

**2. Deploy and invoke both run on the runner.** Because each needs the user's cloud credentials, the runner performs both. The runner pulls the version's signed package from the catalog, verifies the native binary's attestation against the trust store before it deploys (decision 3), deploys the binary to the user's function platform using the user's cloud identity, records the resulting function URL, and later invokes that URL with the same identity (`ServerlessRunExecutionBackend`, already runner-side). The control plane provides the signed artifact and gates dispatch on a deployment being ready; it does not deploy. The deployer seam and the deploy step therefore live with the runner, not in the control plane.

**3. Provenance is verified at the boundary that crosses into the user's account.** The binary is signed at build with the control plane's own key in a KMS or HSM (ADR 0055), and the runner verifies the attestation's digest, target, version bind, and signature against the trust store before it deploys. A version reaches a serverless environment only through a fully signed chain. The function platform's own code-signing (for example AWS Signer) is the complementary control that enforces integrity at and after deploy.

**4. Invoke auth is the function platform's native mechanism, with no shared invoke secret.** The runner invokes the deployed function with its own cloud identity (which is the user's identity). For AWS this is a Lambda Function URL with `AuthType=AWS_IAM`, and the runner SigV4-signs the invoke with its IAM principal, which holds `lambda:InvokeFunctionUrl` for that environment's functions. The Azure equivalent (a native identity-based invoke) follows when the Azure target lands. The function URL is never public. The local RIE test path is unauthenticated by nature, since it is a localhost emulator, so it proves the mechanics but not the production invoke auth.

**5. Callback auth is a per-run, short-lived, scoped, runner-signed token. This is the accepted direction; its concrete construction must pass a security review before it ships.** When the runner dispatches a run, it mints a token bound to that single run id, scoped to `runs:checkpoint`, with a short expiry, signed by the runner, and carries it in the invocation payload alongside the checkpoint URL (the Model B invocation already carries the per-invocation checkpoint address). The function presents the token on each checkpoint POST. The runner verifies the signature, the run-id binding, the scope, and the expiry, and it rejects a replayed or forged token. No standing secret lives in the function. The token's exact claims, signature algorithm, anti-forgery and anti-replay construction, and rotation are a security-review item tracked before implementation. Until that review passes, the serverless callback is not production-secure and the serverless path stays behind the in-process fallback.

**6. The operator configures the runner's cloud identity with a platform-native identity, never static keys in the control plane.** The runner obtains the credentials it deploys and invokes with from the platform's own identity mechanism (AWS IRSA, an EC2 instance profile, or an ECS task role; Azure Managed Identity), or, where a platform-native identity is unavailable, from a scoped credential in the user's secret store resolved through the runner's `ISecretResolver`. That identity is least privilege, holding only the deploy and invoke actions for the environment's functions (for AWS, roughly `lambda:CreateFunction`, `lambda:UpdateFunctionCode`, `lambda:CreateFunctionUrlConfig`, and `lambda:InvokeFunctionUrl`). The control plane is never a custodian of these credentials, and static long-lived keys are never held by the control plane.

## Consequences

- The control plane is not a secret custodian for the user's cloud. A compromise of the control plane cannot deploy to or invoke functions in the user's account, which shrinks its blast radius. The custody stays where the environment's other credentials already are, on the runner.
- The runner's identity is the deploy and invoke authority. An operator must provision it (IRSA, an instance profile, a task role, or a Managed Identity), which is the main new operational requirement. The [running-a-runner guide](../guides/running-a-runner.md) documents it.
- The deployer moves runner-side. `IServerlessDeployer` and the deploy step live with the runner. `WorkflowAotBuildService.VerifyNativeArtifact` runs runner-side (the runner needs the trust store to verify before deploying). The deployment record (`WorkflowDeployment`) is written from the runner's report of what it deployed and read by the control plane's dispatch-ready gate.
- The callback token needs a security review before it ships. The token construction is deliberately left to that review rather than fixed here, and the serverless path is gated behind the in-process fallback until the review passes.
- Local RIE testing is unauthenticated, so the RIE harness proves the deploy and invoke mechanics but not the production auth. The production invoke auth (SigV4) and the signed callback token are proven separately, against a real function platform, when an account is available.
- Deploy and invoke both depend on the runner's cloud identity, so an environment whose runner has no configured cloud identity cannot host a serverless deployment. That is surfaced as a configuration error at the runner, not a silent dispatch failure.
