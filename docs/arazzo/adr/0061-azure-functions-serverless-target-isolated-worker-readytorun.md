# ADR 0061. The Azure Functions serverless target is a ReadyToRun isolated worker

Date: 2026-07-28. Status: **Accepted**. Scope: how Azure Functions joins AWS Lambda as a second serverless execution target, what part of the serverless stack branches per vendor, and why the Azure entry point is a framework-dependent ReadyToRun isolated worker rather than Native AOT, a custom handler, or the in-process model. Builds on the serverless deploy design ([ADR 0055](0055-serverless-backend-aot-from-signed-executor.md), and its 2026-07-28 per-target-form-factor amendment), the deploy security model ([ADR 0059](0059-serverless-deploy-runs-on-the-runner-as-the-secure-boundary.md)), and the local-emulation decision ([ADR 0060](0060-local-serverless-deploy-emulated-with-localstack.md)).

## Context

The serverless backend ships with one target, AWS Lambda (ADR 0055). ADR 0055 named Azure Functions as the second target, and the seam was built to anticipate it: the vendor-neutral core (`ServerlessInvocationHandler`, `ServerlessWorkflowRunHost`, `HttpWorkflowStateStore`) carries no AWS reference, `IServerlessDeployer` / `ServerlessDeployRequest` / `ServerlessDeployResult` have no vendor field, and the runner-side dispatch (`ServerlessRunExecutionBackend`) and function-URL persistence/resolution (`WorkflowDeployment.FunctionUrlOrNull`, `DeployedFunctionUrlResolver`) are URL-in, URL-out — they store and return whatever invoke URL a deploy produced, blind to the platform. So a second target does not touch dispatch, checkpointing, leases, the deploy queue, or the store.

Three things are Lambda-specific today and must branch for Azure: the vendor entry shim (`LambdaServerlessFunction`, the AWS custom-runtime loop over `ServerlessInvocationHandler`), the vendor deployer (`LambdaServerlessDeployer`, packaging a `provided.al2023` `bootstrap` zip and creating the function + a Function URL), and the AOT host-app assembler (`AotHostAppAssembler`), whose Program.cs entry call and `.csproj` (`<AssemblyName>bootstrap</AssemblyName>`, `Amazon.Lambda.*`, `<PublishAot>`) are Lambda literals with no target axis.

**Which .NET model, and which compilation form-factor, is the decision, and cold start decides it.** Azure runs .NET two ways: the **isolated worker** (a .NET process the Functions host drives, the only model that supports .NET 10; in-process retires 2026-11-10) and a **custom handler** (a plain web server the host proxies to). And a .NET app can be compiled three ways for cold start: JIT, ReadyToRun (precompiled IL that still loads the runtime), and Native AOT (a self-contained native binary). The key facts, established by research and a build spike:

- **Azure's platform-optimal cold start is ReadyToRun plus the host's placeholder pre-warm.** The Azure Functions team's own position (their Native-AOT issue, closed *completed*) is that "Functions does have the ability to run NativeAOT compiled apps, [but] we have a more efficient approach ... which ... combined with ready-to-run, yields better results in our environment than NativeAOT." So on Azure, a user Native-AOT app *opts out* of the best cold start.
- **Native AOT is only mandatory where the platform has no runtime.** Lambda's `provided.al2023` has none, so Lambda must be self-contained AOT ([ADR 0055 amendment](0055-serverless-backend-aot-from-signed-executor.md)). Azure's `dotnet-isolated` worker has the runtime, so framework-dependent R2R runs there and is the faster, recommended path.
- **A build spike confirmed the friction is on the AOT side, not R2R.** Compiling the assembled isolated-worker host-app (Worker SDK 2.x + `Microsoft.AspNetCore.App` + the neutral core) with `PublishAot` produced a native binary but a **managed `worker.config.json`** (`defaultExecutablePath: dotnet`, `defaultWorkerPath: handler.dll`) referencing a `handler.dll` a self-contained AOT publish does not emit — so the host would fail to launch it — plus 106 trim/AOT warnings and a 23.6 MB binary. The **same host-app compiled framework-dependent ReadyToRun built with zero warnings**, a `worker.config.json` that is *correct* (the app is genuinely launched as `dotnet handler.dll`), and the neutral core co-restored cleanly.

## Decision

**1. Azure Functions is a second target over the same neutral core and the same `IServerlessDeployer` seam.** Only the entry shim, the deployer, and the assembler's host-app templates and publish flags branch. Dispatch, checkpointing, the deploy queue, the deployment store, and the URL resolver are reused unchanged, because they are already vendor-blind.

**2. The Azure entry point is the .NET isolated worker, compiled framework-dependent ReadyToRun.** It is the .NET-10-supported, first-class model, and R2R plus the host placeholder is Azure's optimal cold start. The assembled host-app is a Functions isolated-worker app (`FunctionsApplication.CreateBuilder(args)` with `ConfigureFunctionsWebApplication` for the ASP.NET Core HTTP integration) that registers a `ServerlessInvocationHandler` built from the baked resolver and transport binder, and exposes one `[Function]` HTTP trigger that reads the invocation body (`{ runId, environment, checkpointUrl }`), calls `ServerlessInvocationHandler.HandleAsync` unchanged, and writes the outcome document as the response — the same contract `ServerlessRunExecutionBackend` speaks. Rejected: **Native AOT on Azure** (opts out of the platform's best cold start, and its Functions tooling is friction, per the spike); the **custom handler** (a polyglot escape hatch, a second proxied process, not the first-class .NET model); **in-process** (retired, no .NET 10).

**3. The assembler gains a serverless-target discriminator and a per-target compile form-factor.** `AotHostAppOptions` carries the target; the assembler forks the Program.cs entry (the isolated-worker host build + the `[Function]` HTTP trigger vs the Lambda runtime loop) and the `.csproj` — for Azure: `<OutputType>Exe</OutputType>`, `<AzureFunctionsVersion>v4</AzureFunctionsVersion>`, `<PublishReadyToRun>true</PublishReadyToRun>`, framework-dependent (`<SelfContained>false</SelfContained>`), `<FrameworkReference Include="Microsoft.AspNetCore.App" />`, and the Worker packages (`Microsoft.Azure.Functions.Worker`, `Microsoft.Azure.Functions.Worker.Sdk`, `Microsoft.Azure.Functions.Worker.Extensions.Http.AspNetCore`), and it emits `host.json`. `provided.al2023`, the `bootstrap` AssemblyName, `Amazon.Lambda.*`, and `<PublishAot>` stay Lambda-only. The transport binder (`Bind`, reading `ARAZZO_SOURCE__*`) and the executor rooting are shared. Because the Azure publish output is a **directory** (`handler.dll`, its dependency assemblies, `host.json`, `functions.metadata`, `worker.config.json`, `.azurefunctions/`), the container builder returns the whole published app for the Azure target, not the single `bootstrap` binary it reads for Lambda.

**4. Deploy is a run-from-package deploy of the published app zip to a `dotnet-isolated` Function App.** The Azure `IServerlessDeployer` (`AzureFunctionsServerlessDeployer`) uploads the app zip (the whole published isolated-worker app the container builder already zips, debug symbols excluded) to a blob container and points the Function App at it with the `WEBSITE_RUN_FROM_PACKAGE` app setting, returning the app's HTTP-trigger URL, which the existing store persists and the existing resolver returns. The blob upload uses an injected `BlobContainerClient` (Azurite locally, real Azure Storage in production, only the endpoint differing, the same pattern as the Lambda deployer's `IAmazonLambda`); the management-plane app configuration, over ARM, is a separate injected `IFunctionAppConfigurator` (real ARM in production, a recording fake in tests), because ARM has no local emulator. The deployer holds no cloud credentials beyond the injected clients, as the runner is the deploy boundary (ADR 0059).

## Consequences

- **Cold start is the reason, and R2R is Azure's best.** Framework-dependent ReadyToRun plus the host placeholder is the path Azure optimizes; a Native-AOT app would forgo it. The runtime is present, so nothing is gained by shipping it. Throughput is not a differentiator for this workload: each invocation is one I/O-bound run-advance (load checkpoint, call a source, save checkpoint).
- **The provenance chain adapts, per the ADR 0055 amendment.** R2R images retain the IL, so the deploy verifies the signed `executor.dll` (the same verify-the-signed-executor model the in-process backend uses), and the trusted set is the framework, the assembler-generated host, and the verified executor. A serverless deployment still runs only a verified executor.
- **The build is clean and fast, unlike the AOT path.** The R2R spike built with zero trim/AOT warnings and a correct `worker.config.json`, and R2R (crossgen2) is quicker than ILC — better for a form-factor the platform bakes anew per (environment, version).
- **The CI gate is asymmetric with Lambda's, because Azure has no management-plane emulator.** LocalStack presents the real Lambda API, so ADR 0060's gate emulates both the deploy (`CreateFunction`) and the execution. There is no LocalStack-for-Functions (Azurite emulates Storage only). So the Azure gate proves **execution** — it runs the published isolated-worker app under the **real Azure Functions host container** (`mcr.microsoft.com/azure-functions/dotnet-isolated`) and drives a run to completion over the runner's real checkpoint surface, the run-to-completion proof of ADR 0060's `ServerlessLiveExecutionLocalStackTests` companion. This gate is realized as **`ServerlessLiveExecutionAzureFunctionsTests`**: it compiles the framework-dependent ReadyToRun app in the builder container, mounts the published app into the runtime image's `/home/site/wwwroot` (HTTP-only, no Azure Storage), and dispatches a seeded Pending run to the `[Function("invoke")]` trigger, which reaches `Completed` with `callEcho` `{ "status": "ok" }` — the isolated worker reaching the test's Kestrel checkpoint surface and source through `host.containers.internal` (a `--add-host …:host-gateway` route). It shares one workflow fixture with the Lambda gate, so both vendors' execution is proven over the identical run. The **run-from-package deploy** is proven locally as far as the emulators reach: the storage half runs against Azurite (`AzureFunctionsServerlessDeployerAzuriteTests` checks the run-from-package URL the deployer mints fetches back the byte-identical package), and `AzureFunctionsRunFromPackageDeployTests` fetches the package from that URL as the App Service platform would and runs it to completion under the real Functions host; the ARM app-configuration half is proven against real Azure, the analogue of Lambda's SigV4 / `AWS_IAM` invoke auth being real-AWS-only (ADR 0059 decision 4, ADR 0060). The standalone `dotnet-isolated` runtime image does not itself download a `WEBSITE_RUN_FROM_PACKAGE` URL — that is an App Service platform operation — so the gate performs the platform's fetch and mounts the package in its place.
- **The invoke is one HTTP POST either way.** A Lambda Function URL and an Azure HTTP trigger are both an HTTPS POST of the invocation returning the outcome, so `ServerlessRunExecutionBackend` needs no per-vendor branch. The deployment store keeps a single `functionUrl` and no vendor column; the vendor is a deploy-time concern, invisible to dispatch.
- **Deployer selection is a host-wiring concern.** The `WorkflowDeployService` holds one `IServerlessDeployer`; a host that serves an Azure environment constructs the Azure deployer instead of the Lambda one. Nothing in the deploy queue or worker changes.

## Amendment (2026-07-29): Flex Consumption is the serverless plan, deployed by One Deploy, live-verified against real Azure

Live testing against a real Azure subscription refined the Azure deploy path, and the deployer now targets all plan types with the right per-plan mechanism.

- **Flex Consumption is the serverless plan.** Linux **Consumption** does not boot a run-from-package-by-URL isolated worker (the app stays 503 with the host *and* SCM down, so no logs); **Dedicated/Premium** plans need a VM quota a serverless subscription need not have (the test subscription's is zero); and **Flex Consumption** is Microsoft's recommended serverless plan (Linux Consumption reaches end of life on 2028-09-30). Our real .NET 10 isolated app boots and serves on Flex.
- **Flex uses One Deploy, not `WEBSITE_RUN_FROM_PACKAGE`.** Flex Consumption's only deployment technology is *One Deploy*: the package is posted to the app's Kudu One Deploy endpoint (`{scm}/api/publish`), stored in the deployment container, and run on start. So the Flex deployer, **`AzureFunctionsFlexDeployer`** (`…AzureFunctions.Deploy.Arm`), posts the version's package there and waits on the deployment status. Authentication is an **Azure Resource Manager AAD bearer token** (Flex disables SCM basic authentication by default, so publishing credentials are rejected); the runner injects the credential (ADR 0059). The `WEBSITE_RUN_FROM_PACKAGE` deployer (`AzureFunctionsServerlessDeployer` + `ArmFunctionAppConfigurator`) remains for the plans that support that mechanism (Windows, Linux Premium/Dedicated), so the target supports all plan types.
- **Live-Azure verified, at zero standing cost.** `ArmFunctionAppLiveDeployTests` provisions a real Flex Consumption dotnet-isolated (.NET 10) Function App, runs the production Flex deployer against it, and proves the platform loaded *our* function from the deployment (the `invoke` route stops being a 404 and is served by our handler), then **tears down every resource it created** (the app, its plan, its Application Insights, and its storage), so there is zero cost between runs. No subscription or resource-group identifiers are baked into source — they arrive only through environment variables — and CI authenticates through the pipeline's Azure credentials (the reusable workflow's `testPhaseAzureCredentials` secret slot), so no secret is committed.
