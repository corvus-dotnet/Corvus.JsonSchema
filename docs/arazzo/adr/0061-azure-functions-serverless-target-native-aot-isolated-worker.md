# ADR 0061. The Azure Functions serverless target is a Native-AOT isolated worker

Date: 2026-07-28. Status: **Accepted**. Scope: how Azure Functions joins AWS Lambda as a second serverless execution target, what part of the serverless stack branches per vendor, and why the Azure entry point is a Native-AOT isolated worker rather than a custom handler, Ready-to-Run, or the in-process model. Builds on the serverless deploy design ([ADR 0055](0055-serverless-backend-aot-from-signed-executor.md)), the deploy security model ([ADR 0059](0059-serverless-deploy-runs-on-the-runner-as-the-secure-boundary.md)), and the local-emulation decision ([ADR 0060](0060-local-serverless-deploy-emulated-with-localstack.md)).

## Context

The serverless backend ships with one target, AWS Lambda (ADR 0055). ADR 0055 named Azure Functions as the second target, and the seam was built to anticipate it: the vendor-neutral core (`ServerlessInvocationHandler`, `ServerlessWorkflowRunHost`, `HttpWorkflowStateStore`) carries no AWS reference, `IServerlessDeployer` / `ServerlessDeployRequest` / `ServerlessDeployResult` have no vendor field, and the runner-side dispatch (`ServerlessRunExecutionBackend`) and function-URL persistence/resolution (`WorkflowDeployment.FunctionUrlOrNull`, `DeployedFunctionUrlResolver`) are URL-in, URL-out — they store and return whatever invoke URL a deploy produced, blind to the platform. So a second target does not touch dispatch, checkpointing, leases, the deploy queue, or the store.

Three things are Lambda-specific today and must branch for Azure: the vendor entry shim (`LambdaServerlessFunction`, the AWS custom-runtime loop over `ServerlessInvocationHandler`), the vendor deployer (`LambdaServerlessDeployer`, packaging a `provided.al2023` `bootstrap` zip and creating the function + a Function URL), and the AOT host-app assembler (`AotHostAppAssembler`), whose Program.cs entry call and `.csproj` (`<AssemblyName>bootstrap</AssemblyName>`, `Amazon.Lambda.*`) are Lambda literals with no target axis.

The serverless design's fixed point is that a deployed function is **one Native-AOT binary per (environment, version)** with the executor baked in (ADR 0055): Native AOT cannot load runtime IL, so baking is what makes it possible, and the neutral core is reused verbatim. **Cold start is the serverless metric that decides the Azure entry model**, and the options differ sharply on it:

- **In-process** is retired (end of support 2026-11-10) and has no .NET 10 build, so it is not a candidate.
- **Ready-to-Run (R2R)** is the Functions team's usual cold-start recommendation, but R2R still loads the .NET runtime and JITs — it is not whole-program AOT. ADR 0055 bakes the executor into a single Native-AOT binary and forbids loading runtime IL, so R2R would re-litigate 0055, not implement it. It is out.
- **A custom handler** (a plain web server the Functions host spawns and HTTP-proxies to) is AOT-clean and reuses the neutral core, but it is a polyglot escape hatch: a second process the host proxies to, not the .NET-optimized path, and its cold start is not the specifically-tuned one.
- **The isolated worker in Native-AOT mode** is Microsoft's recommended path and the only model that supports .NET 10. Native AOT on the isolated worker boots without JIT and without the WebJobs host's dependency graph, cutting cold start dramatically (reported ~2 s → tens of ms). It is a first-class .NET model with ASP.NET Core HTTP integration.

## Decision

**1. Azure Functions is a second target over the same neutral core and the same `IServerlessDeployer` seam.** Only the entry shim, the deployer, and the assembler's host-app templates branch. Dispatch, checkpointing, the deploy queue, the deployment store, and the URL resolver are reused unchanged, because they are already vendor-blind.

**2. The Azure entry point is the .NET isolated worker compiled with Native AOT.** It is the cold-start-optimal, .NET-10-supported, first-class model, and it keeps the design's Native-AOT fixed point (unlike R2R). The assembled host-app is a Functions isolated-worker app (`FunctionsApplication.CreateBuilder(args)` with `ConfigureFunctionsWebApplication` for the ASP.NET Core HTTP integration) that registers a `ServerlessInvocationHandler` built from the baked resolver and transport binder, and exposes one `[Function]` HTTP trigger that reads the invocation body (`{ runId, environment, checkpointUrl }`), calls `ServerlessInvocationHandler.HandleAsync` unchanged, and writes the outcome document as the response — the same contract `ServerlessRunExecutionBackend` speaks (POST the invocation to the resolved URL, read the `outcome`). The custom handler, R2R, and in-process models are rejected for the reasons in Context.

**3. The assembler gains a serverless-target discriminator.** `AotHostAppOptions` carries the target (AWS Lambda or Azure Functions); the assembler forks the Program.cs entry (the isolated-worker host build + the `[Function]` HTTP trigger vs the Lambda runtime loop) and the `.csproj` — for Azure: `<OutputType>Exe</OutputType>`, `<AzureFunctionsVersion>v4</AzureFunctionsVersion>`, `<PublishAot>true</PublishAot>`, `<FrameworkReference Include="Microsoft.AspNetCore.App" />`, and the Worker packages (`Microsoft.Azure.Functions.Worker`, `Microsoft.Azure.Functions.Worker.Sdk`, `Microsoft.Azure.Functions.Worker.Extensions.Http.AspNetCore`), and it emits `host.json`. `provided.al2023`, the `bootstrap` AssemblyName, and `Amazon.Lambda.*` stay Lambda-only. The transport binder (`Bind`, reading `ARAZZO_SOURCE__*`) and the executor rooting are shared unchanged.

**4. Deploy is a zip deploy of the AOT-published host-app to a `dotnet-isolated` Function App.** The Azure `IServerlessDeployer` packages the publish output and zip-deploys it, returning the function's HTTP-trigger URL, which the existing store persists and the existing resolver returns. The deployer holds no cloud credentials beyond the injected client / publish profile, as the runner is the deploy boundary (ADR 0059).

## Consequences

- **Cold start is the reason.** The isolated worker in Native AOT is the measured-optimal, Microsoft-recommended, .NET-10-first-class path, so a deployed Arazzo function pays tens of milliseconds, not seconds, on a cold dispatch. Throughput is not a differentiator for this workload: each invocation is one I/O-bound run-advance (load checkpoint, call a source, save checkpoint), so the entry model's per-invoke overhead is lost in the round-trips.
- **The build surface is heavier than Lambda's, and is a validation risk.** The Azure host-app pulls the Functions Worker SDK, its function-metadata source generator, and the ASP.NET Core framework reference into a Native-AOT publish — more moving parts than the Lambda `provided.al2023` bootstrap, in a build the platform bakes anew per (environment, version). This is proven the same way the Lambda path was: the CI gate builds and runs a real one. The `[Function]` trigger is placed so the Worker source generator discovers it in the compiled host-app.
- **The CI gate is asymmetric with Lambda's, because Azure has no management-plane emulator.** LocalStack presents the real Lambda API, so ADR 0060's gate emulates both the deploy (`CreateFunction`) and the execution. There is no LocalStack-for-Functions (Azurite emulates Storage only). So the Azure gate proves **execution** — it runs the assembled Native-AOT isolated-worker app under the **real Azure Functions host container** (`mcr.microsoft.com/azure-functions/dotnet-isolated`) and drives a run to completion over the runner's real checkpoint surface, the run-to-completion proof of ADR 0060's `ServerlessLiveExecutionLocalStackTests` companion. The **zip-deploy** path is proven against real Azure, the analogue of Lambda's SigV4 / `AWS_IAM` invoke auth being real-AWS-only (ADR 0059 decision 4, ADR 0060).
- **The invoke is one HTTP POST either way.** A Lambda Function URL and an Azure HTTP trigger are both an HTTPS POST of the invocation returning the outcome, so `ServerlessRunExecutionBackend` needs no per-vendor branch. The deployment store keeps a single `functionUrl` and no vendor column; the vendor is a deploy-time concern, invisible to dispatch.
- **Deployer selection is a host-wiring concern.** The `WorkflowDeployService` holds one `IServerlessDeployer`; a host that serves an Azure environment constructs the Azure deployer instead of the Lambda one (a config-driven switch in the runner host). Nothing in the deploy queue or worker changes.
