# ADR 0062. Authenticated serverless checkpoint callbacks use a run-scoped bearer token

Date: 2026-07-29. Revised 2026-08-07: the authenticator is required, not optional, and the control plane maps no checkpoint surface without a secret (audit finding H1). Revised 2026-08-22: the token binds the full `(environment, runId)` address (ADR 0065 decision 9). Status: **Accepted**. Scope: how a deployed serverless function authenticates its checkpoint callback to the runner's checkpoint surface, so that surface can be exposed beyond a private network (for example to a real cloud function) without being an open write endpoint. Builds on the serverless backend design ([ADR 0055](0055-serverless-backend-aot-from-signed-executor.md)) and the runner-as-deploy-boundary model ([ADR 0059](0059-serverless-deploy-runs-on-the-runner-as-the-secure-boundary.md)).

## Context

A serverless run advances out of process: the runner invokes the baked function, which restores the run from its checkpoint, advances it, and checkpoints it back over HTTP to the runner's checkpoint surface, `GET` and `POST /environments/{environment}/runs/{runId}/checkpoint` (`WorkflowCheckpointEndpoints`), which the function-side `HttpWorkflowStateStore` speaks. The invocation carries `{ runId, environment, checkpointUrl }`.

The caller of that surface is not a user with an OIDC session. It is a machine, acting for one specific run, that needs a credential scoped to that run and no more. An ambient authenticated principal (the host's auth scheme) cannot be presented by a dispatched function, and without a run-scoped credential the surface either only works unauthenticated, which a publicly reachable callback cannot be, or admits any authenticated caller to every run in the deployment.

Options considered: (a) a cloud-native identity, the function presenting its managed identity or IAM role for the surface to validate against each cloud's identity provider; rejected as vendor-specific, coupling the surface to every cloud. (b) A single shared API key; rejected because it is not run-scoped, so a leak compromises every callback. (c) A run-scoped, short-lived token the runner mints and the surface validates.

## Decision

**The function authenticates its checkpoint callback with a run-scoped, short-lived bearer token (`CheckpointToken`) the runner mints and the checkpoint surface validates, and the surface cannot be mapped without that validation.**

- **Shape.** The token is `{expiryUnixSeconds}.{base64url(HMAC-SHA256(secret, "environment:runId:expiry"))}`, a symmetric HMAC over the run's full `(environment, runId)` address and an expiry. The address is bound by the signature but not transmitted, because the checkpoint endpoint already knows both halves from the request URL. The signed message decomposes uniquely: the environment-name grammar admits no colon, so the first colon ends the environment; the run-id grammar admits no colon; and the expiry is a canonical decimal (no sign, whitespace, or leading zeros), so exactly one token string authenticates a run. The token needs no cloud identity provider and is opaque to the function, which never interprets it.
- **Mint.** The runner's `ServerlessRunExecutionBackend` mints one per dispatch through its checkpoint-token issuer and writes it into the invocation as `checkpointToken`. `CheckpointToken.Issue` and `TryValidate` take the `WorkflowRunAddress` and reject a secret shorter than `MinimumSecretBytes` (256 bits), so a weak key is caught at mint.
- **Present.** `ServerlessInvocationHandler` reads `checkpointToken` from the invocation and sets it as `Authorization: Bearer` on the per-invocation checkpoint client, so it rides every load and save. It refuses to send a token over a non-HTTPS checkpoint URL (loopback exempt), so a bearer credential never crosses the internet in cleartext.
- **Validate.** `MapWorkflowCheckpointEndpoints` takes a **required** `authenticateCheckpointToken` delegate, `(address, token) => CheckpointToken.TryValidate(secret, token, address, now)`, where `address` is built from the route's `{environment}` and `{runId}`, both grammar-validated before the token is checked. A request without a valid token is a `401`. Validation compares the HMAC in constant time against the URL's address and the token's expiry, so a token minted for another run, or for the same run id at another environment, does not validate on this one. Comparing the canonical base64url signature text rather than decoded bytes neutralises base64 malleability, and HMAC is not length-extendable.
- **The control plane maps no checkpoint surface without a secret.** `MapArazzoControlPlane` takes a `checkpointSecret`; absent, the surface is not mapped at all, which is the [ADR 0016](0016-control-plane-security-mode.md) posture of absent rather than open. A deployment that dispatches no out-of-process runs needs no such surface, and one that does must say so by configuring the secret. A secret below `MinimumSecretBytes` fails the mapping rather than the first callback.
- **The token is this surface's reach gate.** No reach or lease check is added alongside it. The caller is a dispatched function holding no principal to derive reach from and no lease, which is the exact case this record exists to answer; requiring a lease here would refuse every legitimate callback. What bounds the caller is that the token names one run and expires. Ambient authorization (`requireAuthorization`) still composes with it: the principal says a caller belongs to the deployment, the token says which run it may read and overwrite.
- **One coordinator per host.** ADR 0065 decision 6 requires the per-run single-flight interlock to be per run, not per component. The coordinator holds that interlock in memory, so both this map method and the runner API's take the host's coordinator rather than each building one.

The token binds the run via the URL rather than transmitting a claim, so it is the minimal credential: a valid token proves only "the runner authorised checkpoints for *this* run, until *this* time".

## Consequences

- **Blast radius is one run, briefly.** A leaked token authenticates only its own run and only until it expires. It cannot be replayed against a different run, nor against the same run id at another environment, nor after expiry.
- **Vendor-neutral and self-contained.** Symmetric HMAC means no dependency on a cloud identity provider or a JWT library, and the token validates in-endpoint with no auth-middleware registration, so the same mechanism works for any serverless vendor and for a purpose-built listener host.
- **The function stays a dumb carrier.** It holds no signing key and interprets nothing; it copies an opaque string from the invocation to a header. Only the runner (mint) and the checkpoint surface (validate) know the secret, and in the common topology they are the same host, so the secret need not travel.
- **The mechanism cannot be left inert by omission.** As first introduced the issuer and the authenticator were optional, and four of the five call sites (the production control plane, the serverless runner demo, and both local execution gates) mapped the surface with neither, so it fell through to ambient authorization, admitting any authenticated caller to every run and, in `ControlPlaneSecurityMode.Open`, everyone. Only the public listener was wired correctly. Making the delegate required and gating the mapping on the secret forecloses that class rather than fixing its instances.
- **Deployment obligations and the accepted residual.** The token is a bearer credential: it rides the invocation payload (keep it out of the cloud platform's invocation logs) and the callback channel (HTTPS, enforced), and within its lifetime it can be replayed, mitigated by a short lifetime (which must still exceed a single invocation's duration, or checkpoints mid-run start failing) and, for saves, by the monotonic write-sequence that drops a replayed or stale checkpoint. The shared secret's custody, entropy source, and rotation (a key id enabling old and new during a roll) are the deploying host's responsibility. A validator-side maximum-lifetime ceiling, a run-scoped OIDC or JWT credential, and moving the secret into the environment's key custody (ADR 0059) are refinements this shape does not preclude.
- **It is the prerequisite for a public checkpoint listener.** With this, the checkpoint surface can be exposed to a real cloud function, or to a scale-to-zero listener that stands in for the runner in a CI run-to-completion test, without being an open write endpoint.

## Deployment record: the public listener on Azure Container Apps

The public checkpoint listener (`Corvus.Text.Json.Arazzo.ServerlessCheckpointListener`) is the host that wires this mechanism end to end: it maps `MapWorkflowCheckpointEndpoints` with a `CheckpointToken.TryValidate` authenticator over a shared Azure Storage run store, plus the workflow's `echo` source. It is proven live on Azure Container Apps, a real scale-to-zero public HTTPS surface. The specifics, so a run-to-completion gate can stand it up and tear it down at zero cost between runs:

- **Provider registration.** Container Apps needs `Microsoft.App` and `Microsoft.OperationalInsights` registered on the subscription. `Microsoft.App` is not registered by default; registration is asynchronous and must complete before `containerapp env create`.
- **The image is a pre-published context, not a source build.** The listener `Dockerfile` stages a framework-dependent published app onto `mcr.microsoft.com/dotnet/aspnet:10.0` and runs no `dotnet publish` itself, so the build context is the publish output.
- **Container App configuration.** External ingress on target port 8080 (`ASPNETCORE_URLS=http://+:8080`), `--min-replicas 0`, and the storage connection string and base64 checkpoint secret supplied as Container App secrets referenced by env (`ARAZZO_CHECKPOINT_STORAGE=secretref:storage-conn`, `ARAZZO_CHECKPOINT_SECRET=secretref:checkpoint-secret`), never as plaintext. No endpoint, secret, or storage identifier is baked into source.
- **Teardown must include the auto-created workspace.** `containerapp env create` auto-creates a Log Analytics workspace that deleting the environment can leave behind. A zero-cost teardown deletes the Container App, the managed environment, that workspace, the registry, and the storage account.
- **Cold start is expected.** Scale-to-zero means the first request cold-starts; a reachability or invoke poll must tolerate the initial non-`200`.
- **Reachability proof.** Over public HTTPS the deployed listener answers `GET /health` `200`, `GET /demo/echo` `{"status":"ok"}`, a no-token checkpoint request `401`, a valid-token request `404` (the token validated and the store was queried), and a token minted for a different run `401`. The valid-token `404` proves the container reached the real storage account, so the surface is a genuine token-authenticated public endpoint.

Three run-to-completion gates share that listener's store, each seeding a Pending run, dispatching a real function with a run-scoped token and the listener as `checkpointUrl` and `echo` source, and reading the run back `Completed`: `ServerlessRealCloudCheckpointListenerTests` (a local Azure Functions runtime image), `ArmFunctionAppLiveDeployTests` (a real Flex Consumption app that also tears itself down), and `ServerlessRealCloudCheckpointListenerLambdaTests` (an AWS Lambda under LocalStack). All three were verified live against the deployed listener, so the mechanism is proven vendor-neutral over one listener.
