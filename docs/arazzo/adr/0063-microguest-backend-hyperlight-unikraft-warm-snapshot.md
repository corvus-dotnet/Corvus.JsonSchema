# ADR 0063. The micro-guest execution backend runs the AOT executor in a Hyperlight micro-VM restored from a warm snapshot

Date: 2026-07-31. Status: **Accepted**. Scope: the third `IRunExecutionBackend` — per-run micro-VM isolation on the runner's own machine — covering what runs inside the guest, how the micro-VM is hosted and invoked, how per-run isolation and speed are both kept, and how readiness and provenance reuse the serverless machinery. Builds on the pluggable-backend seam and signed-artifact chain ([ADR 0055](0055-serverless-backend-aot-from-signed-executor.md) and its per-target form-factor), the isolation match ([ADR 0058](0058-run-isolation-governed-by-environment-matched-at-start.md)), the runner-as-secure-boundary model ([ADR 0059](0059-serverless-deploy-runs-on-the-runner-as-the-secure-boundary.md)), and the checkpoint-callback token ([ADR 0062](0062-authenticated-serverless-checkpoint-callbacks.md)).

## Context

The backend set has two members: the in-process collectible-ALC backend (`InProcess`) and the serverless backend (`Isolated`, a cloud function per (environment, version), Lambda and Azure Functions targets). The remaining row is the micro-guest: `Isolated` execution without a cloud round-trip, on the runner's own machine, with a hypervisor boundary per run. [Hyperlight](https://github.com/hyperlight-dev/hyperlight) (CNCF sandbox, a VMM embedded as a library, micro-VM creation in milliseconds over KVM/mshv/WHP) is the technology named for this row, and its sibling [hyperlight-unikraft](https://github.com/hyperlight-dev/hyperlight-unikraft) runs ordinary Linux ELF binaries inside Hyperlight micro-VMs under a Unikraft guest kernel with an ELF loader.

A feasibility spike (2026-07-31, WSL2/KVM) settled the crux questions empirically; its grounded facts:

- **The guest payload is the existing pipeline's artifact.** A .NET 10 Native AOT static `linux-musl-x64` binary boots and runs managed code under hyperlight-unikraft — including a **plain, unmodified `HttpClient` round-trip to a host listener through the egress allowlist**, which is exactly the Model-B capability (restore run, call sources, checkpoint back over HTTP). Core Hyperlight alone cannot host the executor (guests are purpose-built `no_std` Rust/C; there are no .NET host bindings), and the Wasm route (hyperlight-wasm + componentize-dotnet) is two experimental layers with an unproven WASI HTTP stack; both are rejected.
- **Three guest-side defects were isolated, each with a settled fix.** (1) .NET 10 dies before any managed code because its GC's startup address-space reservation (a 64 GiB `PROT_NONE` mmap) is fatal on the no-paging Unikraft kernel (.NET 9 tolerates the failed reservation; .NET 10 does not) — fixed by embedding `System.GC.HeapHardLimit` at publish. (2) The upstream kernels take entropy from a cmdline seed the host never passes, so `getrandom` fails and `Guid.NewGuid` throws — fixed in the kernel config with `LIBUKRANDOM_LCPU` (RDRAND/RDSEED, which the micro-VM CPUID exposes) plus `LIBUKRANDOM_DEVFS`. (3) The guest's host-proxied socket layer (`LIBHOSTSOCK`: syscalls forwarded over a JSON-RPC bridge, the **host** opens the sockets and enforces a per-connection allow/block policy) is IPv4-only, and `SocketsHttpHandler`'s default dual-mode `AF_INET6` socket fails — fixed by embedding `System.Net.DisableIPv6`. Everything else in the async socket stack (epoll, eventfd, non-blocking connect, `TCP_NODELAY`) works as-is.
- **The execution model is evolve-once, restore-per-run.** The host boots the kernel, loads the ELF, and snapshots ("evolve", ~90–260 ms measured); each run is then a snapshot **restore** (~20–40 ms) plus a call, and restores are hermetic — guest state does not leak between runs. Application argv is baked into the initrd at sandbox build, so per-run data cannot ride argv without discarding the snapshot.
- **Versions and toolchain.** hyperlight-unikraft 0.12.1 (crates.io) over hyperlight-host 0.16.0, Rust 1.89; the CLI/library builds as a static musl binary in a container. Kernels build with `kraft-hyperlight` (the `danbugs/kraftkit` fork, branch `hyperlight-platform` — the README's `unikraft/kraftkit` branch is stale — Go ≥ 1.26) over `unikraft/unikraft` and `unikraft/app-elfloader` branches `plat-hyperlight`. All pre-1.0: everything is pinned and built hermetically in containers, like the AOT builder image.

## Decision

**1. The micro-guest backend is a third `IRunExecutionBackend`, runner-side, advertising `Isolated`.** Dispatch, leases, timers, message delivery, the isolation match (ADR 0058), and every admission check are untouched. The environment's runners provide the isolation; an environment whose runner hosts micro-guests satisfies `requiredIsolation = Isolated` exactly as a serverless runner does.

**2. The guest binary comes from the existing signed-executor AOT pipeline, as a new runtime target.** The workflow AOT builder gains the `linux-musl-x64` static target (alpine-based builder image, clang/lld, `StaticExecutable`, conservative `IlcInstructionSet=x86-64` for the micro-VM's CPUID) with a micro-guest entry template around the same vendor-neutral core (`ServerlessWorkflowRunHost`, `HttpWorkflowStateStore`). The template embeds the two proven runtimeconfig knobs — `System.GC.HeapHardLimit` sized to the micro-VM's memory, and `System.Net.DisableIPv6` — and exits via `_exit` after its terminal checkpoint flush (runtime shutdown hangs in the unikernel; all durable state is already checkpointed). The artifact is built, signed, and attested exactly as the Lambda binary is (ADR 0055); Native AOT is forced here for the same reason as Lambda — the guest kernel has no .NET runtime (ADR 0055's per-target rule, applied to a new runtime-less target).

**3. Micro-VMs are held warm by a sidecar and restored per advance — the isolation is the VM boundary plus the hermetic snapshot restore, not process churn.** Starting fast is the point of a micro-VM backend, so the backend does not boot a kernel per advance. A small companion process (Rust, over the hyperlight-unikraft library, pinned and container-built) holds an **evolved sandbox per (environment, version)**: kernel booted, guest ELF loaded, snapshot taken before any run. `AdvanceAsync` POSTs the invocation to the sidecar's local endpoint — **the same `{ runId, environment, checkpointUrl, checkpointToken }` contract the serverless backend already speaks** — and the sidecar restores the snapshot (a pristine VM state; nothing survives from any previous run) and calls the guest. Because argv is frozen at snapshot time, the guest learns its work by fetching the invocation from the sidecar over the allowlisted guest network at start (the runtime-API shape the Lambda bootstrap already uses); the fetch answers instantly because the sidecar only restores when it holds an invocation. The guest then advances the run and checkpoints back to the runner over HTTP (Model B, ADR 0062 token), and per-advance cost is dominated by the ~20–40 ms restore rather than a ~1 s boot.

**4. Egress is allowlisted per (environment, version), a tighter posture than the cloud targets.** The sidecar builds each sandbox's network policy from exactly the hosts the run may reach: the runner's checkpoint surface and the environment's source base URLs. The policy is enforced host-side per connection, and loopback and link-local are denied by design, so the checkpoint surface binds a routable address — the posture the deployed listener already has.

**5. Readiness reuses the deployment machinery.** The runner's deploy worker drives a micro-guest `IServerlessDeployer` sibling: it verifies the native artifact's attestation (`WorkflowAotBuildService.VerifyNativeArtifact`, the same boundary check as the cloud deployers, ADR 0059), assembles the guest image (kernel + initrd CPIO around the verified binary), instructs the sidecar to evolve the sandbox, and records a `WorkflowDeployment` whose `functionUrl` is the sidecar's local invoke URL. The dispatch-ready gate, the deployments REST/CLI/console surface, and the isolation-posture strip all work unchanged; a micro-guest deployment is just a deployment whose platform is the runner's own machine.

## Consequences

- Per-run isolation at local latency: a hypervisor boundary per advance at ~tens of milliseconds, with no cloud dependency, no per-run cloud spend, and the same governed selection (ADR 0058) and operator surface (#216) as the serverless backend.
- The trusted base grows by the pinned Unikraft kernel, the ELF loader, and the hyperlight-unikraft host — the counterpart of trusting the Azure Functions runtime image for R2R. All are version-pinned and built hermetically in containers; the signed chain from executor IL to native artifact is unchanged, and verification happens before the guest image is baked.
- The runner host must expose a hypervisor (`/dev/kvm`, mshv, or WHP), which becomes an operational requirement documented in the running-a-runner guide; a runner without one cannot advertise this backend. GitHub Actions Linux runners have KVM, so the live gate is an opt-in `[integration]` test in the LocalStack gate's mold, driving the shared `serverless-check` workflow to completion through a real micro-VM.
- The sidecar is a new, small, non-.NET component owned by this repository. It contains no policy beyond sandbox lifecycle and the network allowlist; all workflow logic stays in the baked guest, and the invoke contract is the serverless one, so `ServerlessRunExecutionBackend`'s shape is reused rather than a new dispatch path invented.
- Upstream is pre-1.0 and moves: the kraftkit fork/branch drift and the .NET 9 example's stale ILCompiler pin were both hit during the spike. The pins (hyperlight-unikraft 0.12.1, hyperlight-host 0.16.0, Rust 1.89, Go 1.26, the two `plat-hyperlight` branches) live with the builder container definitions, and upgrades are deliberate, tested moves.
- The .NET 10 findings (GC reservation fatal on a no-paging kernel; hostsock IPv4-only; unseeded `CMDLINE_SEED` entropy) are candidate upstream contributions; until upstream absorbs them they are encoded in the assembler's micro-guest template and the kernel config this repository owns.
