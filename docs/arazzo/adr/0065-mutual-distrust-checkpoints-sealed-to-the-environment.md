# ADR 0065. Mutual distrust between the control plane and the runner: checkpoints are sealed to the environment

Date: 2026-08-01. Status: **Accepted**. Scope: the trust model between the control plane and runners in a multi-tenant deployment, and the confidentiality of workflow run state — who may hold which keys, what each party can read, and the phased hardening of the store seam. Builds on the two-process topology ([ADR 0023](0023-two-process-store-as-queue.md)), runner-to-environment binding ([ADR 0027](0027-runner-environment-binding.md)), the runner-as-secure-boundary model ([ADR 0059](0059-serverless-deploy-runs-on-the-runner-as-the-secure-boundary.md)), and the run-scoped checkpoint token ([ADR 0062](0062-authenticated-serverless-checkpoint-callbacks.md)).

## Context

A security review of the store seam (2026-08-01) found that the implemented model quietly assumed one trust domain around the shared durability store, and that assumption is wrong for the intended deployment:

- **The intended topology is multi-tenant, with runners owned by tenants.** ADR 0059 already places the environment's credentials in the tenant's own custody, resolved runner-side, precisely so the platform never holds them; environments belong to tenants, and a tenant's runner executes that tenant's workflows near that tenant's systems.
- **Run state is sensitive.** Checkpoints carry the run's evolving state — step inputs and outputs, extracted response data — which can contain anything the tenant's APIs return.
- **But every credentialed process could read everything.** The control plane and every runner hold full store credentials (one shared connection in the demo hosts), and the optional at-rest checkpoint encryption used a single symmetric key deliberately shared by the control plane and all runners, because "every process touching the shared state store must wrap identically". The environment fences (dispatch scoping, keyed gets, the ADR 0027 revocation fence) are enforced by store-layer code running inside the runner's own process — real against bugs, voluntary against a hostile runner. One hostile runner credential could read and decrypt every environment's run state, tamper with any run, rewrite another environment's deployment records, and forge registry and grant rows.

The missed principle, stated plainly: **the runner does not trust the control plane, and the control plane does not trust the runner.** The control plane governs — catalog, gating, dispatch, audit — and must be able to do so *without the ability to read tenant run state*. A tenant's runner executes — and must not be able to read another tenant's state, nor have its state readable by the platform.

What exists to build on is well-shaped for the fix. `ICheckpointProtector` is a pluggable seam that binds ciphertext to the run id and fails closed; `ProtectedWorkflowStateStore` wraps any backend, protecting the payload while the projected index entry — status, workflow id, **environment**, due time, awaiting channel, error type — passes in the clear so wait and dispatch queries work without payload access. That clear/protected split is already exactly the governance/execution boundary this ADR needs; what was wrong was only who held the key.

## Decision

**1. The trust matrix is mutual distrust.** The control plane trusts a runner only to execute runs in the environments it is bound and authorized for (ADR 0027); a runner trusts the control plane only for governance metadata and signed artifacts; no party reads another tenant's run state; the platform operator reads no tenant's run state. Every subsequent decision serves this matrix.

**2. Checkpoints are sealed to the environment with asymmetric envelope encryption.** Each environment has a checkpoint keypair. The **seal (public) key** is registered on the environment record — control-plane-visible, like any public key. The **open (private) key** lives in the tenant's own custody and is resolved runner-side through the deployment's secret resolution, exactly as the environment's other credentials are (ADR 0059); the control plane never holds it. Sealing is public-key operation, so any writer can produce a checkpoint — the control plane seals the initial `Pending` run document at start, runners seal every subsequent checkpoint — but only the environment's runners can open one. The envelope is ephemeral-static ECDH with HKDF to an AES-GCM data key, the run id bound as associated data (the existing anti-splice property), and a key identifier in the header so the opener selects the right private key and rotation is a registration event, not a re-encryption event. It ships as an `ICheckpointProtector`, so `ProtectedWorkflowStateStore` and every store backend inherit it unchanged.

**3. The control plane governs on metadata only.** The clear index projection is the control plane's entire visibility into a run: status, workflow and environment identity, timing, what the run awaits, and the error *type*. Any control-plane surface that previously rendered payload content presents sealed-state metadata for sealed environments. The control-plane-hosted `$draft` debug runner keeps a control-plane key for its own draft runs — drafts execute on the control plane by design and are not tenant production state.

**4. Run-start inputs transit the control plane, and are sealed at rest immediately.** Starting a run through the governed API necessarily shows the control plane the inputs in the request; the control plane writes the initial run document sealed to the environment's seal key and cannot read it back afterwards. This shrinks input exposure to the transit window and keeps the at-rest store uniformly sealed. A tenant-side start surface that keeps inputs away from the control plane entirely is a possible later step and is out of scope here.

**5. Phase 2: store-level, environment-scoped authority per runner.** Sealing is confidentiality; it does not stop a hostile store credential deleting or overwriting rows it cannot read. The second phase gives each runner a store principal scoped to its environments — row-level security keyed on the environment column for Postgres; each backend's native equivalent (scoped credentials per partition or container, database-per-environment where that is the grain) behind a seam so every backend stays first-class — provisioned at registration and revoked with the ADR 0027 fence, with a conformance isolation class proving a foreign credential can neither read nor write another environment's rows. Until phase 2 lands, a deployment running tenant-owned runners must treat the shared store's integrity and availability as shared-fate, and the running-a-runner guide says so explicitly.

**6. Phase 3, acknowledged and tracked, not decided here: executor provenance under mutual distrust.** Today a runner verifies the *control plane's* signature over the executor. A distrusted control plane implies the tenant countersigning authored content, with the runner verifying the tenant's signature over the workflow content hash in addition to the platform's build signature. That changes the authoring and catalog chain and is deliberately left to its own decision.

## Consequences

- Tenant run state becomes confidential against the control plane, other tenants, the store operator, and store backups — by key custody, not by policy code. A compromised control plane or foreign runner reads ciphertext.
- The control plane loses payload access **by design**. Run inspection at the payload level becomes a tenant-side concern (their runners hold the open key); the operator surface keeps everything the index projects.
- Environment lifecycle grows key provisioning: registering an environment includes its seal key, and rotation re-registers; the private key never crosses the platform boundary.
- Phase 1 does not stop tampering or deletion by a hostile store credential — AES-GCM authentication makes tampering *detectable* (opens fail closed), phase 2 makes it *impossible*. The two phases are one posture, sequenced.
- The conformance suite grows sealed-checkpoint coverage (seal-only writers, key-id routing, rotation, foreign-key failure), and the demo hosts rewire from the shared symmetric key to per-environment sealing.
