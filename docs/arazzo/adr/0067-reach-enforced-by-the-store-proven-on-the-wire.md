# ADR 0067. Reach is enforced by the store, mirrored queryably, and proven on the wire

Date: 2026-08-09. Status: **Accepted**. Scope: where the §14.2 reach predicate is applied for every durable store (state, catalog, observed-identity, and the management stores for environments, sources, source credentials and workspace workflows), what a backend must provide so the store can apply it server-side, and the evidence a conversion or a new backend must ship with. Builds on the reach semantics of [ADR 0001](0001-two-plane-access-model.md) and [ADR 0002](0002-grant-verbs-are-reach-not-scopes.md) and the fail-closed, non-disclosing enforcement of [ADR 0004](0004-fail-closed-non-disclosing-enforcement.md); those decide what reach means and how a denied row behaves, this decides where the predicate runs. Records the resolution of hazard H12 and audit item P1-2 as a standing invariant rather than a completed fix.

## Context

The reach predicate decides which rows a caller sees. Until the P1-2 remediation, where that predicate ran was a per-backend accident: the relational backends compiled it into the query, while Mongo, Redis, NATS and Azure Storage fetched rows across every tenant and discarded the out-of-reach ones in process, and the marker claiming pushdown (`SupportsRowSecurityFilter`) was a default interface implementation, so carrying the marker was the entire proof. The conformance suite asserted the functional contract, which an in-process filter satisfies perfectly, so every backend passed it.

That is the trap this record exists to close permanently: **an in-process reach filter is functionally correct and observationally indistinguishable from pushdown at the API**, which is exactly how it survives review. The difference is at the store boundary. With an in-process filter, cross-tenant rows physically leave the store, transit the driver and sit in control-plane memory on every list; a bounded page degrades to a scan whose size is set by other tenants' data (in the worst pre-remediation case, Mongo dropped its server-side limit precisely when a reach filter was present, so the scoped caller got the unbounded query); a count becomes a full stream with per-row admission; and a sound read-side audit is unbuildable, because the process reads what it must never disclose as a matter of routine. The remediation also surfaced two write-side failure modes with the same shape, correct-looking code whose defect only a reach-aware oracle catches: a queryable tag mirror synced on add only, so a re-tagging update left the listing deciding by stale tags in both directions at once, and a row key recomputed from current tags, so a re-tagged row became unaddressable while deletes reported success.

## Decision

**The store applies the reach predicate; the control plane never filters reach in process.** Backends whose query language can evaluate the predicate push it down into the native query. Backends whose query language cannot (the broker and key-value class) narrow through §14.4 label indexes so that only in-reach rows are ever fetched. A list's server-side page bound and its reach predicate coexist unconditionally: narrowing reach never widens the scan. Point reads keep their bounded in-memory reach decision over a key's few reach-disjoint candidates; that is a constant-size decision over rows already selected by key, not a filter over a stream.

**Every store answers the pushdown question explicitly, and the answer is enforced, not declared.** There is no default implementation of `SupportsRowSecurityFilter`, so a new store cannot inherit a claim it does not honour and silence is a build error. The conformance reach oracles are mandatory and assert the declared answer outright: a store that quietly stops pushing down fails suites rather than turning Inconclusive.

**A backend whose query cannot see inside the stored document mirrors the row's current reach labels as queryable data, transactionally with the document write.** The reach mirror is the side table on the relational backends, the `securityTags` array on Mongo and Cosmos, the label sets, subjects and entities on the broker-class backends. It is written with the add, and a re-tagging update re-sets it in the same write under the management stores' replace-or-carry contract. The transactionality is the point: a stale mirror fails in both directions simultaneously, the row stays visible to the scope it was moved out of (a leak) and invisible to the scope it was moved into (an availability loss), while the store's own point read, which evaluates the document's current tags, disagrees with the store's own list.

**Rows are addressed by the frozen create-time key.** Anything the row key derives from tags at create time is stored on the row and read back; it is never recomputed from the document's current tags. Recomputation plus a legal re-tag produces a row the store can no longer address: updates target a nonexistent key and deletes report success while leaving the row in place.

**Counts are bounded and share the list's predicate.** A count runs server-side over the same pushed-down reach predicate as the list it annotates, bounded at cap + 1, and the predicate is constructed by the same code path for both, so the two cannot drift and a count never streams rows to the client.

**The evidence standard is the wire, flip-verified.** Because correctness cannot discriminate a pushed-down filter from an in-process one, every conversion and every new backend ships with: the explicit pushdown answer; the mandatory conformance oracles green; wire proofs on the backend's own protocol (captured SQL, driver commands, request bodies) asserting the predicate's presence under a scoped caller, its absence under the unrestricted system caller, and the bound on the count; and flip verification in both directions, where disabling the reach condition fails exactly the leak-direction oracles, omitting the mirror write fails exactly the availability direction, and removing the update-side re-set fails exactly the re-tag oracle. A flip that fails more or less than its predicted set means the tests do not measure what they claim.

## Consequences

- Out-of-reach rows never leave the store, so the reach decision runs where the data lives. This is what makes a future read-side audit (GAP-7) possible at all, and it removes the class of scan whose cost is set by other tenants' data.
- Every future store implementer is confronted by the pushdown question at compile time and by the oracles at test time. Declaring `false` fails the reach suites closed, so an in-process filter is not a shippable state for a store carrying reach-labelled rows; a backend that cannot meet this decision is not a supported durability backend.
- The reach mirror is deliberate denormalisation with a write-side obligation. Every code path that changes a row's reach labels must carry the mirror in the same write; the management stores' update path is the one that exists today, and any future path (import, repair, migration) inherits the same rule.
- Wire proofs are per-backend by nature: the shared conformance suite carries the oracles, and each backend's test project carries its own wire observation and flip record. The cost is a per-backend test file; the alternative was trusting a declaration, which is hazard H12 verbatim.
- As of this record the state, catalog, observed-identity and management stores meet the decision on all ten backends: the Redis, NATS and Azure Storage management stores, the last three in-process filters, were converted to §14.4 label-index narrowing (each in its own commit updating the threat model), so H12 is closed with no remaining TB-4 in-process-filter residual and every backend's label-index design is in the mirror table.
- This ADR does not decide capability scoping (ADR 0001, ADR 0002), the non-disclosing behaviour of a denied row (ADR 0004), or the per-backend label-index layouts; a broker conversion that faces a genuine fork records its own decision.
