# ADR 0068. Execution budget: fuel, wall clock and depth, set per deployment and per environment, enforced by the runner and verified by the coordinator

Date: 2026-09-07. Revised the same day, on implementation: fuel is bounded by the per-step journal cap, which is the counter the coordinator verifies against. Revised 2026-09-18: the verification is decided after the sequence rule and the budget joins the frozen identity; the journal counts attempts, so fuel bounds a retry loop; the runner's enforcement, the metered sub-workflow scope and the system-run exemption are recorded below. Revised 2026-09-18 on building the transport bounds: a breach is a step failure and not a budget fault, the bounds are applied where every run executes and not by each binder, no source `Retry-After` header is read, and an unhandled executor failure ends the run. Status: **Accepted**. Implementation: **in progress**. Landed: the budget type, the deployment ceiling, the environment override and its API, the resolution recorded into every run at start; the coordinator's verification on every save with the control-plane-authored fault, the same check at claim time, the `budget-exhausted` refusal on both checkpoint surfaces and the runner client, and the resume refusal; the runner's own enforcement before every attempt, the per-attempt journal, the metered sub-workflow scope with the depth cap, the `retryAfter` clamp, and the scheduler run's exemption; the transport bounds (a step timeout and a response size on the budget, applied to every run's transports), transport failures routed to a step's `onFailure`, and the durable fault for an unhandled executor failure. Scope: what bounds a production run's resource consumption, where the bound is configured, where it is enforced, and how a run that exceeds it is classified. Resolves GAP-5 of the 2026-08-07 security audit and decides hazard H14. Builds on the mutual-distrust seam of [ADR 0065](0065-control-plane-owns-store-runners-encrypt-payload.md), which is why the bound is verified on the control plane and not only honoured on the runner, and on the capacity seam of [ADR 0066](0066-runner-api-rate-and-capacity-limiting.md), which bounds how many runs exist and says nothing about how much any one of them may do. Revised 2026-09-18 on closing the rest of the re-claim loop: the net covers resolving the executor and binding the transports as well as running it, a refusal is told from an outage by its cause, and no run store counts claims. Revised 2026-09-18: the WebSocket transport's opt-in message limit is recorded under the consequences. Revised 2026-09-19 on surfacing the budget: the ceiling has one definition, read from host configuration through the management seam, and the environment's budget resource, the run's budget and the documented fault types are recorded below. Revised 2026-09-19: a budget fault is no longer terminal. A resume re-budgets the run from its environment's current budget, bounded by the ceiling and the journal cap, and a remediated run provably keeps its budget and journal. Revised 2026-09-19: the console surfaces the budget on the environment and the run, which completes the surfacing. Revised 2026-09-19: a draft debug run is budgeted by the same resolution, since it calls real sources, and the scheduler's run is the only exemption.

## Context

Nothing bounds what a single production run consumes. A per-run step budget, a run deadline, a production cap on sub-workflow depth, a per-step response size cap, a per-step HTTP timeout and a ceiling on a source's `Retry-After` are all absent. The one depth cap that exists, `IWorkflowRun.MaxSubWorkflowDepth = 8`, is enforced by the draft-run recorder (`DraftRunStepRecorder.cs`) and the test tracer (`TracingWorkflowRun.cs`) and by nothing on the production path. The simulator is bounded: `WorkspaceSimulationJson.ReadBudget` defaults a simulation to 256 steps and clamps a request to 1,024 steps and 30 seconds, through the `SimulationBudget` type (`MaxSteps`, `WallClock`) in the testing library.

The consequence has a third party in it. A pair of steps that `goto` each other issues a real request to a configured source on every iteration, forever, and the operator's runner fleet becomes a sustained flood against someone else's API. Abuse and legal exposure land on the operator. This is the gap the audit ranked as the one that should not wait.

Two properties of the existing design constrain the answer. First, the runner is not trusted (ADR 0065): a bound the runner alone honours is a cooperative control, and a compromised or misconfigured runner is precisely the host that would not honour it. Second, the coordinator already re-reads every checkpoint body on every save (`WorkflowCheckpointCoordinator.SaveAsync` projects the index through `WorkflowCheckpointSerializer.TryProjectIndex`, the P1-8 remediation), and that body carries the run's step journal (`stepJournal`) and its creation time is on the index (`CreatedAt`). The control plane therefore already holds, on every save, the two numbers a fuel and wall-clock bound need, without a new read.

## Options

**Fuel only.** A maximum number of steps per run. Bounds the flood directly, since every step that reaches a source is one request. Does not bound a run that spends its steps slowly (a step that waits on a slow source, or a durable wait that resumes late), so a run can outlive any operational horizon.

**Wall clock only.** A deadline from creation. Bounds how long a run exists but not how many requests it makes inside that window, so a tight loop still floods until the deadline.

**Both, as one budget.** Fuel bounds requests, the wall clock bounds lifetime, and the depth cap bounds the one structural way to multiply both. The simulator already expresses exactly this shape.

**Where enforced: runner only, coordinator only, or both.** Runner-only is cooperative. Coordinator-only faults a run only when it next checkpoints, so a step that never checkpoints (a loop inside one advance) is bounded only by the runner's own advance. Both closes each gap with the other.

**Where configured: deployment, environment, or version.** A version-level budget is tenant-authored, and the budget exists to bound what a tenant's author can do. An environment-level budget matches how every other governed execution property is already set (`requiredIsolation`, `requireEvidence` on the environment record). A deployment-level budget is the operator's ceiling.

## Antagonistic review

*Against both:* two limits are two things to configure and explain. *For:* each alone leaves a loop the other closes, and the simulator's users already reason in both terms.

*Against coordinator verification:* it adds a comparison to the checkpoint hot path. *For:* the comparison is two integers against numbers the coordinator has already decoded for the P1-8 sequence check, and a bound only the runner honours is the H14 divergence restated with a different owner.

*Against a per-environment override:* a tenant environment administrator could raise it. *For:* the override may only tighten the deployment ceiling, never exceed it, and the same person already governs isolation and evidence on that record.

*Against faulting rather than pausing:* an operator may want to raise the budget and continue. *For:* a run that hit its budget has done something its author did not intend; resuming it past the bound is the same run continuing, and the right shape is a new run under a considered budget.

## Decision

**A run carries one execution budget with three limits: fuel (the maximum number of step attempts), a wall clock (the maximum age from creation), and the sub-workflow depth cap.** The vocabulary is the simulator's, so a workflow bounded in the designer is bounded the same way in production.

**Fuel counts attempts, and the journal holds one entry per attempt.** An attempt is one execution of a step, and each one that reaches a source is one request. A first visit, a revisit through a `goto`, and every retry are all attempts. A failed attempt that a `retry` action runs again is journaled with the status `Retrying`, and the attempt the step settles on follows it. `retryLimit` is the workflow author's and the specification puts no cap on it, so a journal that recorded a step once per visit would let one step with a large limit and a `retryAfter` of zero send requests for the whole wall clock on a single unit of fuel, invisibly to the coordinator. Counting attempts makes a retry loop spend fuel exactly as a `goto` loop does.

**The budget is configured at two levels and resolved at start.** The deployment sets the ceiling, an `ExecutionBudget` given to the management seam and to the control plane's mapping. An environment may carry an `executionBudget` override on its record, beside `requiredIsolation` and `requireEvidence`, which may only tighten: the API refuses a limit wider than the ceiling. The effective budget is resolved when the run starts, on every start path through the management seam, and recorded in the run's checkpoint, so a later change to the environment does not move a run's bound under it.

**Fuel cannot exceed the per-step journal cap.** The journal (ADR 0050) is the counter the coordinator verifies against, and it is exact only up to its cap of 500 entries; past the cap the run marks it truncated. A budget with more fuel than the cap would be unverifiable, so the type refuses to construct one, the deployment ceiling is at most the cap, and a truncated journal is over any admissible budget by definition. Raising fuel above the cap is a later decision that needs a control-plane-verifiable counter the runner-authored body does not offer today.

**The runner enforces the budget cooperatively, and the coordinator verifies it authoritatively on every save.** The generated executor announces every attempt before it reaches a source, and the run decides there: its journal together with the attempts announced and not yet journaled is the fuel already committed, and when none is left for this attempt, or the run is older than its wall clock, it records the budget fault itself and unwinds the advance, so a runaway run faults fast without a round trip. The run therefore stops with its journal at the fuel and never past it, which is the coordinator's predicate, so a runner that honours the budget never proposes a save the coordinator refuses on fuel. Its own deadline fault necessarily arrives after the deadline it reports, so the coordinator applies a save that is itself the terminal budget fault and waives only the deadline objection for it. A body that carries a budget fault record but leaves the run running, and a journal past the fuel, are still refused. The coordinator, on every checkpoint save, compares the journal length against the fuel and the run's age against the wall clock, from the same body it already projects, and refuses a save past either. A runner that does not honour the budget therefore cannot persist the run past it. The check is decided after the monotonic-sequence rule, so only the save that would otherwise be applied is judged and a stale or out-of-order arrival stays reported as the race it is. The budget and the run's creation time are part of the identity the coordinator freezes on the first save, beside the workflow id and the security tags: a later save that widens or drops the budget, or moves the creation time, is rejected as the identity re-point it is, so a runner cannot extend its own bound. On a save past the budget the control plane itself rewrites the last durable checkpoint as terminally faulted on the limit that was hit (the fault is recorded against the last journaled step), consuming the sequence the refused save proposed, and answers the runner API's and the serverless surface's `409` with the `budget-exhausted` problem type. The runner API applies the same predicate when a run is claimed, so a run whose wall clock ran out while it waited is faulted and handed back rather than resumed.

**A sub-workflow spends the root's fuel, and the depth cap applies in production at the value the recorder and tracer already enforce.** Eight, unless the budget says otherwise. A budgeted run hands each sub-workflow a metering scope: the child's attempts are decided by the root's budget and journaled into the root's journal under the invoking step's path, so the coordinator verifies them from the same journal, and nesting past the cap, by a `workflowId` step or a `goto` to a workflow, faults the run at the invoking step before the child makes an attempt. The scope only meters. A production sub-workflow has never had a run of its own (its retry delays are in-process, its receives block, its faults propagate to the root), and giving it one to count it would have changed all three, so the executor meters through the scope and otherwise executes the child as it always has.

**The built-in scheduler run carries no budget, and it is the only run that does not.** It is the platform's own run, not a tenant's workflow. It lives as long as its schedule and suspends on its own cadence timer, so a wall clock would fault every schedule a day after it was created and the `retryAfter` ceiling would cut any cadence longer than it. It reaches no source itself, and every run it fires starts through the management seam and is budgeted like any other. Budget resolution skips the scheduler's reserved workflow id, the id every store already treats as reserved.

**A draft debug run is budgeted like any run.** It is not a second exemption. A draft run calls real development sources under the runner's credentials ([ADR 0045](0045-debug-runs-never-credentials-in-browser.md)), and a working copy is unreviewed code, so a draft that loops is exactly the case this record exists for. It was started with no budget, which left it with no fuel, no wall clock and no depth cap. It is now budgeted at start by the one resolution (`ISecuredWorkflowManagement.ResolveExecutionBudgetAsync`, the deployment's ceiling tightened by its development environment's override), and a draft run started where no resolver is wired takes the platform default and never nothing. The management seam that serves the debug-run verbs is given the deployment's ceiling and the environment registry, so a draft run re-budgeted on resume is resolved as it was at start and cannot be widened to the built-in default. There is no separate draft budget, and the wall clock stays the run's age from creation: a debug session left paused past it faults when it is next stepped, and its author raises the environment's wall clock and resumes, or re-runs.

**A run that exceeds its budget faults, with a distinct error type per limit, and is resumed only by re-budgeting it.** `budget-fuel`, `budget-deadline` and `budget-depth` on the run's `ErrorType`. Dispatch never reclaims such a run, and no resume mode moves it under the budget it faulted on: a rewound run is still past its deadline and still has a full journal. But a run that hit its budget should not have to repeat the work it has done, so a resume of a budget-faulted run re-budgets it. The budget is resolved again exactly as a start resolves it, the ceiling tightened by the environment's override as it is now, and the resume proceeds only if the run is inside the result: room for at least one more attempt, an age from creation inside the wall clock, and for a depth fault a deeper cap than the one it hit. The remedy is therefore an environment administrator's act, raising the environment's limit, and no request can grant one run more than its environment allows. Three things bound it. The control plane writes the new budget to the checkpoint and audits it (`run.rebudget`, with the old and new limits), and the coordinator takes a run's budget only from the stored row, so a runner still cannot widen a budget. No run ever exceeds the deployment's ceiling, because the override only tightens. And fuel has an absolute limit, the journal's cap of 500 entries, so a run that made 500 attempts is never resumable. The wall clock stays the run's age from creation, so a run older than the ceiling's wall clock is beyond rescue under that ceiling. A run that did not fault on its budget keeps its frozen budget across a resume, so a later change to the environment still does not move a run's bound except by this act. The run's detail says in advance whether a resume would run (`rebudget`). Any run can instead be re-run from the beginning ([ADR 0072](0072-rerun-a-run-server-side.md)).

**The same budget bounds the per-step transport, and a breach is the step's failure, not the run's.** The budget carries a step timeout (a hundred seconds by default, and never more than ten minutes) and a maximum response size (sixteen mebibytes by default), set and tightened exactly as the other limits are. The timeout spans the whole exchange, from the send to the response having been read. `HttpClient.Timeout` cannot do that: the transport completes its send when the response headers arrive, which is where that timeout stops applying, so a body that stalled was unbounded in time, and the response parser's buffer doubles until end of stream, so a body that never ended was unbounded in memory. The run-path clients are shared by every run and step and so cannot carry a run's timeout. They carry a fixed fifteen-minute backstop, above the ten-minute ceiling, so the budget's bound is always the one that fires and a client is still never left to wait without limit. Fuel, the wall clock and the depth cap are verifiable by the coordinator from the checkpoint it already reads. The transport bounds are not: nothing in a checkpoint shows how long a request took or how large a response was, so they are the runner's to enforce and a breach cannot be a control-plane-authored fault. It is also an ordinary operational event, a slow or misbehaving source, which a workflow's author may reasonably want to retry. A step that breaches a bound has therefore failed, with no response, and its `onFailure` actions are dispatched without response context, the same way the step's own declared `timeout` always has been. Each retry is an attempt and spends fuel, so a source that never answers ends the run on `budget-fuel` and not in a loop.

**The bounds are applied where every run executes, not by each transport binder.** There are many binders (the credential-aware binder, the static registry, the serverless host's baked binder, each host's own), and several hand out transports from factories built before any run existed, so a bound each binder had to honour would be a bound any binder could forget. Every execution path, in-process, serverless and draft, runs through `HostedWorkflowExecution.RunAsync`, which bounds whatever the binder returned with the run's budget. A transport that reads a body from the network implements `IBoundableApiTransport` and bounds itself, since only it sees the body arrive, and a decorator passes the bounds to the transport it wraps. A transport that does not implement it, a mock or the simulator, has no network body and is bounded in time alone. A run with no budget, the scheduler's, takes the default budget's bounds, so no request on the run path is unbounded.

**Every failure of the exchange is a step failure, not only a breach of the two bounds.** A connection that fails, a body that stops arriving and a body that is not the JSON it claims have no response either, and before this record nothing on the run path caught any of them. They take the same route to `onFailure` as a timeout.

**No source `Retry-After` header is read.** The budget's `retryAfter` ceiling clamps the delay a workflow's `retry` action declares, which is the only retry delay the engine acts on. Honouring a source's header would be new behaviour and not a bound, and is not decided here. Every durable delay suspends through one method, which is where the ceiling is applied, so a reader added later inherits it.

**An executor failure that nothing handles ends the run as a durable fault, `executor-unhandled`.** Left to propagate, such an exception reached the host with the run still live: the lease was released, the run was claimed again, and the same step failed again. The attempt that threw had been announced and never journaled, so that loop sat outside the run's fuel and nothing ended it. The fault records the fixed error type and not the exception's message, because a run record is read by whoever may see the run and a message can name hosts and internals. A draft run, whose reader is the workflow's author, records the message. Two things still propagate, because the host and not the run must answer them: the caller's cancellation, which is how a host shuts down, and a failure to persist the run (a lost lease, a refused checkpoint, a store outage), which cannot be answered by persisting a fault.

**A run whose executor is refused, or whose transports cannot be bound, ends as a durable fault too.** Both happen before the executor runs, so before anything the executor's net catches, and both looped the same way: thrown to the host, the run stayed live and was claimed and refused again on every poll. A resolver's refusal is the same answer on every attempt (the run's id names no version, the version is not in the catalog or has no executor or manifest, its stored content hash diverges from its documents, the loader's verification of the assembly fails, or a baked host is handed a run for a version it does not serve), and ends the run as `executor-unresolvable`. A `WorkflowTransportBindingException` from the binder (a source with no binding in the run's environment, or a channel transport that could not be built) ends it as `transport-unbound`, for an operator to supply the binding and resume the run. Both keep the message off the run record, as `executor-unhandled` does, and both leave the same two things to propagate.

**A refusal is told from an outage by its cause, not by counting.** Anything else that resolution throws is taken to be the artifact source failing (the runner API, the catalog's store), which may pass. It propagates with the run left live, and the run is retried on the next poll. No run store carries a claim or delivery counter. After this, what escapes an advance is the host shutting down, a failure to persist, or the artifact source being unreachable: conditions of the host and its infrastructure and not of one run, which a per-run count would answer by faulting every run an outage touched.

**A sweep that is cut short hands back the claims it never reached.** The runner API's wait sweeps claim a batch and advance it one run at a time, each claim leased from the moment it is made. An advance that throws ends the sweep, since what escapes is a shutdown or an outage and pressing on would only fail each remaining run slowly. The remaining claims are released first, so none sits leased and unadvanced until its lease lapses. Dispatch claims one run at a time, and the store-backed dispatcher and worker lease each run as they reach it, so neither holds a batch to strand.

**The ceiling has one definition, and the budget is readable where it applies.** A deployment's ceiling is its host's configuration (`Arazzo:ExecutionBudgetCeiling`, the six limits by their API names, a limit left out being the default's), read into one `ExecutionBudget` and handed to the management seam alone. The control plane takes it from there (`ISecuredWorkflowManagement.ExecutionBudgetCeiling`). There had been a second input, an argument on the endpoint mapping, which nothing tied to the first: a host that set one and not the other would have validated overrides against one ceiling and resolved runs against another. It is removed. A ceiling may be wider than the default wherever the platform has no hard limit of its own, which is everything but fuel and the step timeout. An environment's override, the ceiling and the effective budget are read together from `GET /environments/{name}/executionBudget`, whose `effective` is resolved by the rule a run start applies, and the environment's own read stays a whole-document projection of the stored record. A run's frozen budget is `budget` on the run. The API states durations in whole seconds everywhere, which loses nothing, because every budget is resolved from whole-second limits. The six fixed fault types are documented on the fault's error, with their meaning and remedy, and the field stays an open string because a step's own failure lands there too.

## Consequences

- The platform cannot be aimed at a third party for longer than one budget. A mutual-`goto` pair, a retry loop, and a loop inside a sub-workflow each make at most fuel requests and live at most one wall clock, whatever the runner does.
- The budget is a property of the run, not of the environment at the moment of checking. Raising an environment's budget affects new runs, and a run already faulted on its budget only when someone resumes it. It never moves the bound of a run that is running.
- A remediation rewrites a run's checkpoint by property, carrying everything it does not name from the stored bytes. Re-serializing the run from a list of its fields had dropped the budget and the journal, so a rewound run came back unbudgeted with its fuel refunded.
- The coordinator's every-save check gains two comparisons over numbers it already has. Threat model TB-5's integrity row records that budget enforcement is now a control plane property, not a runner one.
- The simulator and production share a vocabulary. A budget the designer shows is the budget production applies, and the simulator's ceilings (1,024 steps, 30 seconds) are the designer's, not the deployment's.
- A run's journal reads as a record of attempts. A retried step has one `Retrying` entry per failed attempt before the entry it settled on, attempt numbers count from one, and a sub-workflow's steps appear under their invoking step's path. The console shows a step whose latest entry is `Retrying` as being retried.
- A workflow's author sees a transport failure as a failed step with no response. An `onFailure` action whose criteria read the response does not match it, and one with no criteria, or with criteria over `$inputs` and `$steps`, does. A step with no matching action faults the run at that step, as any failed step does.
- A transport that reads network bodies and does not implement `IBoundableApiTransport` is bounded in time and not in size. Every transport this repository ships that reads from the network implements it.
- An outage of the store or of the artifact source is retried on every poll until it heals, unbounded by design. The operator sees it in the host's logs, and no run is faulted for it.
- The WebSocket message transport can bound a received message (`WebSocketTransportOptions.MaxMessageSize`, off by default, in the general AsyncAPI package). It is the one message transport with no broker to bound a message for it. No run reaches it today, since the only channel transport factory is NATS. A WebSocket channel transport factory, when one is written, must set the limit from the run's budget as the API transports' response limit is.
- The REST API and the CLI surface the effective budget on the environment and on the run, and explain a faulted run's error type: which limit it hit, or which executor fault, and what to do. The CLI and the console can author an environment's override. In the console a budget-faulted run offers Resume exactly when the server says a re-budget would let it run, and Re-run otherwise.
- This record does not decide rate limiting on the governance plane (GAP-3), egress policy (GAP-4), or how many runs a tenant may hold (ADR 0066). It bounds one run.
