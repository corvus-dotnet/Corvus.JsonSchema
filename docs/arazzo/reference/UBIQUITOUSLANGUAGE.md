# Ubiquitous language

A living glossary of the terms this project uses, in the Domain-Driven Design sense: one name per
concept, used consistently in code, documents, APIs, UI copy, and conversation. **Maintained at the
root of the Arazzo design-docs folder; update it in the same change that introduces or refines a
term.** If a term here conflicts with usage elsewhere, this document wins and the other usage should
be fixed. Known conflicts and their resolutions are recorded in
[Normalization decisions](#normalization-decisions) at the end.

Sections, and the entries within each section, are ordered alphabetically. Where a definition uses
another entry's term (in exact or inflected form), its first use links to that entry.

Terms marked **(proposed)** are being introduced by in-flight design work and settle when that
design lands.

## API mechanics

| Term | Definition |
|------|------------|
| <a id="keyset-pagination"></a>**Keyset pagination** | The project-wide list idiom: `limit` + opaque `pageToken` in, `nextPageToken` out, ordered by a stable per-store key. Every list endpoint *and its store* is paged from the start. |
| <a id="problem-details"></a>**Problem details** | Errors are RFC 9457 `application/problem+json` (`type`, `title`, `status`, `detail`, `instance`); clients branch on status, never parse strings. |

## Arazzo document model

| Term | Definition |
|------|------------|
| <a id="action"></a>**Action** | A success action (`end`, `goto`) or failure action (`end`, `goto`, `retry` with `retryAfter`/`retryLimit`), attached to a [step](#step) or inherited from the [workflow](#workflow) level. |
| <a id="arazzo-document"></a>**Arazzo document** | A document conforming to the Arazzo specification (1.0/1.1): `info`, `sourceDescriptions`, one or more `workflows`, optional `components`. The unit the [workflow designer](#workflow-designer) edits and the [catalog](#catalog) stores. |
| <a id="components"></a>**Components** | The [Arazzo document](#arazzo-document)'s reusable library (`inputs`, `parameters`, `successActions`, `failureActions`) referenced via reusable objects. |
| <a id="criterion"></a>**Criterion** | A success/assertion condition (`simple`, `regex`, `jsonpath`, `xpath`) with optional `context` [runtime expression](#runtime-expression). Used in [step](#step) `successCriteria`, in [action](#action) `criteria`, and in [scenario](#scenario) `$outputs` expectations (judged by the same compiler). |
| <a id="implicit-dependency"></a>**Implicit dependency** (step) | An ordering edge a [step](#step) imposes not by declaring `dependsOn` but by reading another same-[workflow](#workflow) step's data through a `$steps.<id>.*` [runtime expression](#runtime-expression) (Arazzo 1.1 §5.8.5.2.4): the referenced step MUST complete first. The generator folds implicit dependencies into the same topological order as explicit `dependsOn` (`WorkflowExecutorEmitter.TopologicallyOrder`); a cycle in the combined graph is an error. Contrast **explicit dependency** (a `dependsOn` entry). |
| <a id="operation-surface"></a>**Operation surface** | The set of operations (OpenAPI) or channel operations (AsyncAPI) a [source document](#source-document) exposes; what a user browses to create [steps](#step). Described by `OperationDescriptor` / `AsyncApiChannelDescriptor`. |
| <a id="runtime-expression"></a>**Runtime expression** | An Arazzo `$…` expression (`$inputs`, `$steps`, `$outputs`, `$response`, `$statusCode`, …) evaluated during execution; parsed by `ArazzoExpression`. |
| <a id="source-description"></a>**Source description** | An entry in the [Arazzo document](#arazzo-document)'s `sourceDescriptions`: a named reference (`name`, `url`, `type` = `openapi` \| `asyncapi` \| `arazzo`) to a [source document](#source-document). In-document; distinct from a *source document* (the file itself) and a *[registered source](#registered-source)* (a `/sources` registry entry). |
| <a id="source-document"></a>**Source document** | The actual OpenAPI/AsyncAPI/Arazzo file a [workflow](#workflow)'s [steps](#step) bind against; stored inside the [package](#package) as `sources/<name>.json`. |
| <a id="step"></a>**Step** | One unit of work in a [workflow](#workflow). Binds to exactly one of: an OpenAPI operation (`operationId` or `operationPath`), another workflow (`workflowId`), or an AsyncAPI channel (`channelPath`, 1.1). Carries `parameters`, `requestBody`, `successCriteria`, `onSuccess`/`onFailure` [actions](#action), and `outputs`. |
| <a id="workflow"></a>**Workflow** | A named sequence of [steps](#step) within an [Arazzo document](#arazzo-document) (`workflowId`, `inputs` schema, `steps`, workflow-level `successActions`/`failureActions`, `outputs`, `parameters`, `dependsOn`). |

## Catalog and lifecycle

| Term | Definition |
|------|------------|
| <a id="baked-schemas"></a>**Baked schemas** | The precomputed `metadata/schemas.json` [package](#package) entry: per-[step](#step) schema metadata (typed inputs, resolved output types) that drives `/validate` and the UI's typed forms without re-parsing [source documents](#source-document). |
| <a id="base-workflow-id"></a>**Base workflow id** | The unversioned [workflow](#workflow) identity (`nightly-reconcile`) under which [versions](#version) group. |
| <a id="catalog"></a>**Catalog** | The control plane's immutable, [content-hashed](#content-hash), versioned store of [workflow](#workflow) [packages](#package), with governance metadata and search. |
| <a id="content-hash"></a>**Content hash** | SHA-256 over the RFC 8785 canonical form of the logical `{workflow, sources}` content — framing-independent, stable across repacks. The [version](#version)'s identity and the [executor](#executor)'s integrity binding. |
| <a id="draft"></a>**Draft** | **A [version](#version) not yet made [available](#availability) in any [environment](#environment).** A derived state (its availability set is empty), not a stored flag. A draft is exercised by [scenarios](#scenario) in the [workflow designer](#workflow-designer), then [promoted](#promotion) through environments. Once available anywhere it is no longer a draft. |
| <a id="executor-manifest"></a>**Executor manifest** | The `metadata/executor-manifest.json` [package](#package) entry: target framework, assembly digest, package-hash binding, entry type. Verified before an [executor](#executor) loads. |
| <a id="obsolete"></a>**Obsolete** | The retired governance status of a [version](#version) (`Active` → `Obsolete`); still addressable until [purged](#purge), never deletable while [runs](#run) reference it. |
| <a id="package"></a>**Package** (`.awp`) | The self-contained, deterministic, [content-hashed](#content-hash) container for a [version](#version): the [Arazzo document](#arazzo-document), every referenced [source document](#source-document), and named metadata entries. A complete input to code generation. |
| <a id="publish"></a>**Publish** | The act of minting a catalog [version](#version) from a [working copy](#working-copy), together with its [scenarios](#scenario) and the [evidence](#evidence) of their successful execution. A published-but-unpromoted version is a [draft](#draft). (Serving a version at an endpoint is *hosting*, not publishing — see normalization E.) |
| <a id="purge"></a>**Purge** | The destructive bulk-reap of [obsolete](#obsolete) [versions](#version), or of old completed/cancelled [runs](#run), that nothing references. Gated by a `:purge` [capability scope](#capability-scope) and bounded by purge [reach](#reach). |
| <a id="runnable"></a>**Runnable** | A [version](#version) that carries a compiled [executor](#executor) (code generation and compile succeeded at add). Only runnable versions can be [triggered](#trigger). |
| <a id="version"></a>**Version** (catalog version) | One immutable release of a [base workflow](#base-workflow-id): the [package](#package) plus governance metadata. The store assigns `versionNumber` and rewrites the workflow id to `{base}-v{n}` (the **workflow-id rewrite**). Content never changes after add; only governance metadata is mutable. |
| <a id="working-copy"></a>**Working copy** | The mutable [Arazzo document](#arazzo-document) under edit in the [workflow designer](#workflow-designer), with its [scenarios](#scenario). Durably saveable on its own, as many times as needed, without ever minting a catalog [version](#version) — so development iteration does not pollute the [catalog](#catalog). Persisted in the designer workspace (and optionally a Git branch); *[publish](#publish)* mints a catalog version from it. Prefer this term over "draft save": **[draft](#draft)** is reserved for an unpromoted catalog version. |

## Design, test, and validation

| Term | Definition |
|------|------------|
| <a id="advanced-node"></a>**Advanced node** | A schema construct the [schema editor](#schema-editor)'s visual tier summarises rather than fully forms — a keyword it does not render, `not`, `patternProperties`, a `$ref` carrying siblings, and the like. Shown as a labelled row that preserves the raw subschema and stays JSON-editable, so a round-trip never destroys or reorders it. |
| <a id="busy-action"></a>**Busy action** | A user-triggered service call wrapped by `runAction(trigger, work)` on `ArazzoElement`: the trigger is blocked from re-firing the instant it is activated (so a double-click issues the operation once), and if the work outlives about 150ms the trigger shows a spinner in place of its label. It leaves `disabled` to validation, spins only the network portion of a confirm-gated action, and is a courtesy against a double submission, never a substitute for server-side idempotency ([ADR 0053](../adr/0053-triggered-actions-guard-and-show-delayed-busy.md)). |
| <a id="change-classification"></a>**Change classification** | The label a [comparison](#comparison) assigns each element: *added* (present only on the right), *removed* (present only on the left), *changed* (present on both, content differs), *renamed* (a [step](#step) matched by binding under a new id — see [rename](#rename-step)), *moved* (a step reordered, content identical — never *changed*). |
| <a id="comparison"></a>**Comparison** (workflow) | A structured diff of two [workflow](#workflow) [versions](#version) (`diffWorkflowPair`): [steps](#step), flow edges, and workflow-level surfaces classified as added / removed / changed / renamed / moved (the [change classification](#change-classification)) on top of the graph projection and the document model's identity-aware structural diff. Rendered by `<arazzo-workflow-compare>` as side-by-side, overlay, or text (the [comparison modes](#comparison-mode)). |
| <a id="comparison-mode"></a>**Comparison mode** | The [comparison](#comparison)'s presentation, per dialog instance: **Side by side** (two surfaces), **Overlay** (one union canvas, the base [version](#version) solid and the other side's exclusives translucent as *ghosts*), or **Text** (a CodeMirror MergeView over the two serialized documents). |
| <a id="debug-run"></a>**Debug run** | The durable, forward-only server-side entity a [debug session](#debug-session) drives (REST `debugRuns` tag, §18): started from a [working copy](#working-copy), run/paused/stepped, resumable, and cancellable/deletable. Backed by a real [executor](#executor) whose transport is either a [scenario](#scenario)'s [mock transport](#mock-transport) or a live transport in a development-class [environment](#environment); forward-only means time-travel is a replay over the recorded [trace](#trace), not a rewind of the run. |
| <a id="debug-session"></a>**Debug session** | An interactive [simulation](#simulation) in the [workflow designer](#workflow-designer): run/pause/step a [workflow](#workflow) on the design surface against a [scenario](#scenario)'s [mock transport](#mock-transport) and [virtual clock](#virtual-clock), with breakpoints on [steps](#step), live state inspection, expression evaluation against the paused context, [trigger injection](#trigger-injection), and time-travel over the recorded [trace](#trace). |
| <a id="edge-corridor"></a>**Edge corridor** | The vertical gap — between adjacent nodes of a rank band, or just outside the row — that a band-skipping edge routes through on the [workflow designer](#workflow-designer)'s design surface, one waypoint per crossed band, so it runs beside the [steps](#step) and chain edges it would otherwise cut through. Straight wins: an edge keeps its own straight line where it already clears the band; only a line that would pierce a node snaps to the nearest corridor (`routeEdges`, design §6.3). |
| <a id="edge-lane"></a>**Edge lane** | An edge's slot within a shared [edge corridor](#edge-corridor) — or, for an upward retry/goto loop, its right-side vertical track: deterministic offsets a fixed pitch apart, ghosts sorted after solid edges, so no two edges draw the same line. The [comparison](#comparison) overlay relies on this to keep a ghost edge visible beside the chain it bridges. |
| <a id="evidence"></a>**Evidence** | The durable record that a [version](#version)'s [scenarios](#scenario) executed successfully: the scenario set (by [content hash](#content-hash)), per-scenario outcomes, and the engine/version identity, attached at [publish](#publish) and surfaced by the [catalog](#catalog). |
| <a id="guarded-json-editor"></a>**Guarded JSON editor** | A parse-gated raw-JSON textarea whose edits apply only when the buffer parses, holding the last valid value otherwise (`wireGuardedJson`). Per host, a blank buffer either deletes the value or holds the last valid one. The single shared idiom behind the [schema editor](#schema-editor)'s JSON tier, the payload editor, and the document inspector. |
| <a id="merge-target"></a>**Merge target** | The side of a [comparison](#comparison), opened with `mergeTarget: true`, whose document the host is editing (the [working copy](#working-copy)). It turns the comparison into an interactive merge and sources its document from the live model, never a snapshot. |
| <a id="mock-transport"></a>**Mock transport** | The simulated transport (`MockApiTransport`) that answers the operations a [workflow](#workflow)'s [source documents](#source-document) expose during a [simulation](#simulation), with scripted responses instead of real endpoints. (Not a *[runner](#runner)* — the [executor](#executor) is real; its transport and clock are simulated.) |
| <a id="rename-step"></a>**Rename** (step) | A [step](#step) matched across [versions](#version) by binding equality (same `operationId` / `operationPath` / `channelPath`+action / `workflowId`) under a different `stepId`. Presented as one changed step with a rename note, never a remove plus an add. |
| <a id="scenario"></a>**Scenario** | A named, declarative test for a [workflow](#workflow): inputs, scripted [mock-transport](#mock-transport) behaviour, triggers, [virtual-clock](#virtual-clock) advances, and expected outcomes/paths/outputs. Associated with the [version](#version) under design; carried forward when a new version of a published workflow is edited. |
| <a id="scenario-runner"></a>**Scenario runner** | The CLI (`scenarios run`) that executes a globbable set of [scenarios](#scenario) against a [workflow](#workflow) — in-process via the [simulator](#simulation) (standalone, no control plane) or against a control plane — with CI-grade reports and exit codes; wrappable as a GitHub Action. |
| <a id="schema-editor"></a>**Schema editor** | The typed JSON-Schema authoring form (`<arazzo-schema-editor>`) for a [workflow](#workflow)'s `inputs` and the [components](#components) library's input schemas, in place of a raw textarea. Edits a *subset* of JSON Schema as typed property rows and first-class `oneOf`/`anyOf`/`allOf` combiner nodes, stays lossless over the rest via **[advanced nodes](#advanced-node)**, offers a Form \| JSON toggle over the **[guarded JSON editor](#guarded-json-editor)**, a live typed preview, and a shared-type reference picker. |
| <a id="simulation"></a>**Simulation** | Executing a [workflow](#workflow)'s compiled [executor](#executor) against the [mock transport](#mock-transport) and [virtual clock](#virtual-clock), producing a [trace](#trace). Deterministic and replayable. |
| <a id="take-keep"></a>**Take / Keep** | The interactive-merge verbs on a change-list entry when there is a [merge target](#merge-target). *Take* adopts the other side's state for that one entry (the component emits `change-accepted`/`merge-text-applied`; the host applies it to its model, undoably). *Keep* marks the entry reviewed for the session — the [working copy](#working-copy) IS the merge state, so a change not taken is kept by definition; nothing is persisted. |
| <a id="trace"></a>**Trace** | The structured record of one [simulation](#simulation): the path taken, per-[step](#step) requests/responses, [criterion](#criterion) results, retries, [waits](#wait), outputs, and final outcome. |
| <a id="trigger-injection"></a>**Trigger injection** | Delivering a message trigger into a [debug run](#debug-run) that is `Suspended` on a message [wait](#wait) (REST `injectDebugRunMessage`): the payload is handed straight to the suspended run's correlated wait to [resume](#resume) it — nothing is published to a broker — so a message-driven [workflow](#workflow) can be driven interactively without an out-of-band producer. |
| <a id="virtual-clock"></a>**Virtual clock** | The simulated `TimeProvider` a [simulation](#simulation) runs against, so timer [waits](#wait) and retries elapse deterministically without real time passing. |
| <a id="workflow-designer"></a>**Workflow designer** | The UI for authoring an [Arazzo document](#arazzo-document): a visual design surface (diagram area + context inspector) and a text editor over the same [working copy](#working-copy). The design surface doubles as the interactive debugger for [simulations](#simulation) (the [debug session](#debug-session)) — it is an instrument, not an illustration. |

## Environments and promotion

| Term | Definition |
|------|------------|
| <a id="availability"></a>**Availability** | The many-to-many relation "[version](#version) V is available in [environment](#environment) E". Additive; governed by the target environment's [administrators](#environment-administrator). Admitted only where the version's [owner group](#owner-group) is the environment's (ADR 0065): a version carrying none is available only in an environment carrying none, which is what the platform environment carries, and a mismatch is refused as `tenancy-mismatch` at promotion, at both ends of a promotion request, at schedule creation and run-now, and again at [run](#run) start. |
| <a id="availability-matrix"></a>**Availability matrix** | The [version](#version) × [environment](#environment) grid showing each pair as [available](#availability), promotable, or not [ready](#readiness), with direct make/withdraw or request-[promotion](#promotion) actions. |
| <a id="availability-request"></a>**Availability request** | A request that a [version](#version) be made [available](#availability) in an [environment](#environment), routed to that environment's [administrators](#environment-administrator)' [approver inbox](#approver-inbox) (approve/deny/withdraw). The environment-scoped sibling of an [access request](#access-request), decided under the same [independent-decision](#independent-decision) rule. |
| <a id="deployment"></a>**Deployment** | One installation of the control plane, its stores, and the [runners](#runner) bound to it, spanning every [owner group](#owner-group) and [environment](#environment) it carries. The widest blast radius a single compromise can reach, and the scope at which a security posture is chosen (ADR 0016). Never a synonym for [workflow deployment](#workflow-deployment), which is the narrower act of publishing one [version](#version)'s [native binary](#native-binary) to a function platform. |
| <a id="environment"></a>**Environment** | A first-class governed deployment target ([administrator](#environment-administrator) set, audit) that [versions](#version) are made [available](#availability) in and [credentials](#credential) are bound per. |
| <a id="environment-administrator"></a>**Environment administrator** | A member of an [environment](#environment)'s governing set; approves [availability](#availability-request) and [runner-authorization](#runner-environment-binding) requests for that environment. The environment-scoped counterpart of a workflow [administrator](#administrator). |
| <a id="environment-name"></a>**Environment name** | An [environment](#environment)'s stable identity: 1 to 63 lowercase ASCII letters, digits or hyphens, not beginning or ending with a hyphen (a DNS-label shape), for example `production`, `staging`, `dev-mwa-1`. The name is half of every run's composite `(environment, runId)` store key (ADR 0065 §9), including in backends that encode that key as a delimited string (Redis key segments, NATS KV keys, Azure Table partition keys), so the grammar excludes every delimiter and forbidden character those encodings involve. Enforced by the contract's `EnvironmentName` schema at the HTTP ingress and by the environment draft factories in process. |
| <a id="environment-checkpoint-key"></a>**Environment checkpoint key** | A sealed [environment](#environment)'s key registration (ADR 0065). Each generation names the payload-key id its [checkpoint payloads](#checkpoint-payload) carry (the [payload key](#payload-key) itself stays in the tenant's custody, runner-side), plus the public **seal key** an [initiator](#initiator) wraps a [sealed start](#sealed-start)'s inputs to. Registering a new generation is a rotation, and the registrant signs a framed tuple naming the environment, key id, key, and signing instant with the private seal half, so a registration proves possession rather than being a string anyone can write. Into an environment that already holds a generation, the registration also carries a [rotation link](#rotation-link) from a generation it holds, or it is refused (decision 12). The proof is bounded: it establishes control of the seal pair, and cannot establish that the symmetric [payload key](#payload-key) exists, since that key must never reach the control plane. Replaying a registration re-registers the identical generation and changes nothing, which is what removes the need for a server-issued challenge. Managed through `/environments/{name}/keys`, under the environment's administrators. Retiring the last active generation is refused while more than one [owner group](#owner-group) exists. The control plane never holds a key that opens tenant data. |
| <a id="promotion"></a>**Promotion** | Making a [version](#version) [available](#availability) in an [environment](#environment), either directly ([environment administrator](#environment-administrator)) or via an [availability request](#availability-request) through the [approver inbox](#approver-inbox). [Readiness](#readiness)-gated, and gated on the version's [owner group](#owner-group) being the environment's. |
| <a id="readiness"></a>**Readiness** | The gate on [promotion](#promotion): every [registered source](#registered-source) the [version](#version) references must have a [usable](#usability) [credential](#credential) in the target [environment](#environment), and — where the environment sets `requireEvidence` — the version's [publish](#publish) [evidence](#evidence) must attest a **green suite** (at least one [scenario](#scenario) ran, none failed). Absent evidence, or an empty suite, counts as unevidenced and is refused there. Per-environment and default-off, so environments that never opt in keep the credential-only gate. |

## Execution

| Term | Definition |
|------|------------|
| <a id="aot-builder"></a>**AOT builder** (workflow AOT builder) | The control-plane build tooling that Native-AOT compiles a [version](#version)'s [native binary](#native-binary) from its already-signed [executor](#executor) IL (ADR 0055). It verifies the [executor manifest](#executor-manifest) signature before it compiles, so the native binary is provably derived from the signed IL, and builds one binary per runtime target. |
| <a id="checkpoint"></a>**Checkpoint** | The single row per [run](#run) that *is* the entire resumable state, stored as the [checkpoint row](#checkpoint-row): the [envelope](#checkpoint-envelope) ([cursor](#cursor), status, retry counters, journal, [wait](#wait), [fault](#fault), sequencing), the [payload](#checkpoint-payload) ([step](#step) outputs, inputs, correlation tokens) and the [control-plane region](#control-plane-region), plus the store's etag. |
| <a id="checkpoint-row"></a>**Checkpoint row** | The pinned stored layout of a [checkpoint](#checkpoint) (ADR 0065 decision 6): a framing version, an algorithm id, then length-framed regions in fixed order, the key id, the [envelope](#checkpoint-envelope) as the runner region, the salt, nonce, tag, [payload](#checkpoint-payload) and MAC, and last the [control-plane region](#control-plane-region). Opaque octets to every backend: nothing parses, patches or re-emits it. The prefix before the control-plane region is the *submitted bytes*, everything the [runner](#runner) writes, which the [checkpoint digest](#checkpoint-digest) is taken over. The key id and MAC regions carry the [checkpoint MAC](#checkpoint-mac) and come together or not at all. On an unsealed environment the encryption regions are empty and the payload is clear. |
| <a id="checkpoint-mac"></a>**Checkpoint MAC** | The one HMAC-SHA256 that makes a [checkpoint row](#checkpoint-row)'s runner region and [payload](#checkpoint-payload) inseparable (ADR 0065 decision 4): under the `envelope-mac` subkey of the [payload key](#payload-key), over the length-framed header, key id, runner region and SHA-256 of the payload region, never the [control-plane region](#control-plane-region). Computed by the [runner](#runner) on every save through its [runner key ring](#runner-key-ring) and verified by it on every load; the control plane holds no key and cannot verify one, so the runner API requires one under an active [environment checkpoint key](#environment-checkpoint-key) generation for a [sealed environment](#sealed-environment) instead. |
| <a id="runner-key-ring"></a>**Runner key ring** | A [runner](#runner)'s own allowlist (ADR 0065 decision 10): the [environments](#environment) it serves at all, and for each how. Default deny, read from the runner's own configuration and its own secret store, nothing on it from the control plane: an environment with no entry is not served, whatever [binding](#runner-environment-binding) the control plane writes, so a claim for it is handed back and a checkpoint for it is refused (`CheckpointEnvironmentNotAdmittedException`), and a runner with no entries serves nothing. A clear entry names the environment alone and is served clear. A sealed entry names the key generation the runner writes under, a reference into the runner's own secret store for the [payload key](#payload-key), and the pinned fingerprint of the seal key the tenant registered (the base64 SHA-256 of its SubjectPublicKeyInfo), which the runner checks against what the control plane advertises through the runner API's `getEnvironmentSealKey` at most once a minute, suspending the environment on any other key, a generation not held active, or no answer; it may also name the private seal half and the [initiator keys](#initiator-key) it pins (decision 9). An entry holds one generation or several, oldest first (decision 12), and the runner writes under its [write generation](#write-generation); the entry's minimum generation names one held, the oldest by default, and a row under an older held generation is refused. The payload key and the subkeys derived once from it are held for the runner's life. Every keyed environment has its [payload](#checkpoint-payload) encrypted under a [data key](#data-key) and its row sealed with the [checkpoint MAC](#checkpoint-mac) on every save, and verified and opened on every load; an entry marked sealed also refuses a clear row on load, except the genesis row the control plane writes before any runner has claimed. A runner whose payload key cannot be read, or is not a 32-byte key, or whose keyed entry has no pinned fingerprint, does not start. The serverless checkpoint listener and the serverless runner host carry one too and enforce the same allowlist (decision 11). |
| <a id="write-generation"></a>**Write generation** | The [key generation](#environment-checkpoint-key) a [runner](#runner) currently seals its saves under for an environment on its [key ring](#runner-key-ring) (ADR 0065 decision 12). The newest generation the ring holds to begin with; a runner that checks the runner API's advertised generations re-selects it at each check as the newest held generation advertised active whose seal key is the pinned one or reaches it along verified [rotation links](#rotation-link), so a rotation the tenant registers is followed without a restart, and a successor the outgoing key did not sign for is never written under. Rows under any held generation at or above the minimum still open, and a message wait parked under an older generation still wakes, since a delivery queries the blind index under every held generation. |
| <a id="rotation-link"></a>**Rotation link** | The predecessor's ES256 signature over the framed tuple (`environment-key-rotation`, environment, predecessor key id, new key id, new seal public key), made with the outgoing private seal half, that a registration into an environment already holding a generation must carry (ADR 0065 decision 12). Stored on the new generation for its life, kept through retirement, and advertised with it by `listEnvironmentKeys` and the runner API's `getEnvironmentSealKey`. Every party that pinned an earlier generation's fingerprint verifies the links for itself, back to the pin: a runner advances its [write generation](#write-generation) along them and a pinned [initiator](#initiator) seals to the farthest reachable active generation. A first generation carries none, and a link a retired predecessor signed still verifies, so a compromised generation is retired and its successor registered in either order. |
| <a id="sealed-environment"></a>**Sealed environment** | An [environment](#environment) whose [checkpoint rows](#checkpoint-row) carry an encrypted [payload](#checkpoint-payload) and a [checkpoint MAC](#checkpoint-mac). Two parties decide it independently and both fail closed (ADR 0065 decision 10): the [runner](#runner), from its [key ring](#runner-key-ring); and the runner API, which treats a tenant environment holding an active [environment checkpoint key](#environment-checkpoint-key) generation as sealed and refuses a submission for it that is not encrypted and MAC'd under a generation the record holds as active. The control plane's own serverless checkpoint surface applies the same rule. A reader without the key, which is every control-plane surface, sees a sealed run's [envelope](#checkpoint-envelope) alone: the step journal reports its steps and says the payload is sealed, and a re-run is refused. The platform environment is never sealed. |
| <a id="checkpoint-digest"></a>**Checkpoint digest** | The SHA-256 over a [checkpoint](#checkpoint)'s pinned submitted bytes (header, runner region, salt, nonce, tag, ciphertext, MAC), which is that checkpoint's *identity* in the [tenant anchor](#tenant-anchor) (ADR 0065). Never the server-owned control-plane region, which is joined at read time and is not the [runner](#runner)'s to commit to, so a cancellation or a budget fault written there leaves the digest alone. A [sealed start](#sealed-start)'s genesis row is digested over its own pinned layout under the genesis label, the sealed inputs and the initiator's signature, since no runner key has touched it; a plain start's clear genesis row is digested over its submitted bytes like any row. Always qualified. Bare "digest" means the [identity digest](#digest). |
| <a id="checkpoint-envelope"></a>**Checkpoint envelope** | The control-plane-readable half of a [checkpoint](#checkpoint) (ADR 0065): the run-management structure — [cursor](#cursor), status, [wait](#wait), [fault](#fault) classification, retry counters, sequencing, timing — every governance verb acts on. Clear by design so the control plane governs every [run](#run); contains no tenant data. |
| <a id="checkpoint-payload"></a>**Checkpoint payload** | The tenant-data half of a [checkpoint](#checkpoint) (ADR 0065): run inputs, [step](#step) outputs, final outputs, correlation tokens, as its own closed-schema document in the [row](#checkpoint-row). In a [sealed environment](#sealed-environment) the [runner](#runner) encrypts it (AES-256-GCM under a [data key](#data-key) derived from the environment's [payload key](#payload-key), with the run, environment, key id and sequence as associated data) before it leaves the runner's boundary, opaque to the control plane and to every other tenant; the row carries the salt, nonce and tag beside the ciphertext. A run's genesis row, written by the control plane, carries the [initiator](#initiator)'s seal for a [sealed start](#sealed-start) and clear inputs for a plain one. |
| <a id="sealed-start"></a>**Sealed start** | Starting a [run](#run) with inputs the control plane never reads (ADR 0065 decision 9). An [initiator](#initiator) the tenant controls fetches the [environment](#environment)'s public seal key, pins its fingerprint, chooses the [run id](#run-id), seals the inputs to the key (RFC 9180 HPKE, DHKEM(P-256, HKDF-SHA256), HKDF-SHA256, AES-256-GCM) under a binding of the environment, base workflow id, version, key generation and run id, signs the binding and the seal with its [initiator key](#initiator-key), and submits the seal. The control plane stores it as the run's [sealed genesis row](#sealed-genesis-row) and validates nothing in it; the [runner](#runner) that first claims the run opens it, validates the inputs against the version's inputs schema itself, and either advances or faults the run at its start (`sealed-start-inputs-invalid`, `sealed-start-unopenable`), so it is never claimed again. The run says it started sealed in every later save. A start that is not sealed (the console, a schedule, a trigger) is a plain start, and its run carries no such mark. |
| <a id="sealed-genesis-row"></a>**Sealed genesis row** | The [checkpoint row](#checkpoint-row) the control plane writes for a [sealed start](#sealed-start), at sequence 0 before any runner has claimed: the seal key generation as the key id, the control plane's envelope as the runner region, the seal's encapsulated key in the salt region, the sealed inputs as the payload and the [initiator](#initiator)'s signature in the MAC region, which is its only authenticator. Opened by a runner whose [key ring](#runner-key-ring) holds the seal key and pins the initiator, under the binding re-derived from the run's own address and the envelope's workflow id, never from anything else in the row; a keyless reader sees the envelope and no inputs. |
| <a id="initiator"></a>**Initiator** | The party that makes a [sealed start](#sealed-start): code the tenant controls, such as the CLI or a tenant-hosted trigger host, holding an [initiator key](#initiator-key). Never the control plane, and never a browser the control plane serves, since either could skip the pin or post plaintext. |
| <a id="initiator-key"></a>**Initiator key** | The P-256 signing key an [initiator](#initiator) holds, whose public half a [runner](#runner) pins in its own [key ring](#runner-key-ring) configuration (ADR 0065 decision 9). A [sealed start](#sealed-start) opens only under a signature one pinned key verifies: the seal key is public and the binding holds no secret, so without the signature anyone, the control plane included, could seal inputs of their choosing into the tenant's boundary. |
| <a id="control-plane-region"></a>**Control-plane region** | The region of a [checkpoint row](#checkpoint-row) the control plane writes and the [runner](#runner) never authors (ADR 0065 decision 7): the run's budget, a cancellation, a budget fault, a resume request and a debugger pause. Outside the runner's submitted bytes: a runner submits only its own bytes and the server joins them with the region it holds, and a writer that finds the row moved re-applies over the other's newer bytes, so a control-plane write never touches the runner's octets and never faults a runner's save. A resume request and a budget fault record the runner sequence they were made against and hold until the runner saves past it; a cancellation is unconditional. |
| <a id="claim"></a>**Claim** | Taking a claimable [run](#run) and its [lease](#lease) in one operation, the only way a [runner](#runner) is given work (ADR 0065). Claimable means a `Pending` run, a `Running` one whose lease has lapsed (an orphan a crashed runner left, which must be reclaimable or an interrupted run would never [resume](#resume)), or one the control plane marked resume-claimable. The candidate set is intersected server-side with the [environments](#environment) the runner's machine principal is bound to, which is why the environment is never a request parameter: a runner asking for one would be asking to claim another tenant's work. |
| <a id="correlation-id"></a>**Correlation id** | The key a message [wait](#wait) matches on, so an inbound message [resumes](#resume) exactly the [run](#run) that awaits it. Absence on either side widens the match rather than narrowing it; see [correlation match](#correlation-match). |
| <a id="cursor"></a>**Cursor** | The scalar state-machine position in a [run](#run)'s [checkpoint](#checkpoint) identifying which [step](#step) runs next; the core of [resume](#resume). |
| <a id="correlation-match"></a>**Correlation match** | The rule deciding whether a delivered message resumes a [run](#run) awaiting one. For a clear wait, absence is a wildcard on either side: a message carrying no [correlation id](#correlation-id) reaches every run awaiting the channel, and a run awaiting no particular correlation is reached by any message on it. Only two correlations that are both present and different fail to match. For a [blinded](#wait-index-blinding) wait the rule is equality on the index and nothing else: a delivery carrying a correlation id is claimed by its own index and by the channel-only index, so a run awaiting any message on the channel still wakes, and a delivery carrying none is claimed by the channel-only index alone, never by every correlated waiter. Pinned by the conformance suite across every backend, so it is the rule everywhere rather than one store's behaviour. |
| <a id="dispatch-pass"></a>**Dispatch pass** | One sweep of a [runner](#runner)'s dispatch loop: [claim](#claim) a [run](#run), [resume](#resume) it, release it, repeat until nothing is claimable or the pass hits its bound. The bound is what stops a backlog monopolising the runner, so a pass ending with work still queued is the design rather than a shortfall; the next pass takes the rest. Release happens on every exit path including cancellation, because cancellation is how a runner shuts down and a lease not given back strands its run until the TTL lapses. |
| <a id="enrolment-token"></a>**Enrolment token** | A short-lived, [environment](#environment)-scoped bearer token that admits a [runner](#runner) no [administrator](#environment-administrator) has named in advance (ADR 0065 decision 2). An administrator mints one and the deployment delivers it to the runners it starts there; a runner holds a token rather than the secret that mints them, because the secret would let it enrol any id for as long as it held it. Presenting one binds the authorization to the presenting [machine principal](#machine-principal) and enters `Pending`, so it buys a place in the approval queue rather than the right to execute. It is the alternative to [pre-authorization](#runner-pre-authorization), and the one that lets an environment scale its runners: pre-authorizing per instance otherwise requires something holding the standing power to pre-authorize any id, which is the blanket capability scoping registration exists to remove. |
| <a id="engine-version"></a>**Engine version** | The Corvus runtime version a [version](#version)'s [executor](#executor) IL was compiled against, recorded in its [executor manifest](#executor-manifest) (manifest format 2 and later). The [AOT builder](#aot-builder) references a matching runtime and refuses a mismatch, so a deployment's package feed must retain every engine version any live version still pins. |
| <a id="execution-backend"></a>**Execution backend** | The pluggable isolation model a [runner](#runner) dispatches a [run](#run) to: in-process collectible load context, per-run micro-guest, serverless function, or container — an isolation ↔ latency ↔ cost choice. |
| <a id="execution-budget"></a>**Execution budget** | The limits every production [run](#run) carries (ADR 0068). Three bound the run: fuel, the maximum number of [step](#step) attempts, where a first visit, a revisit and every retry each count and the run's journal holds one entry per attempt (a retried failure is a `Retrying` entry); a wall clock, the maximum age from creation; and the [sub-workflow](#sub-workflow-step) depth cap. Two more, the [transport bounds](#transport-bounds), bound a single step. The deployment sets the ceiling and an [environment](#environment) may only tighten it; the effective budget is resolved at start and recorded with the run. A [sub-workflow](#sub-workflow-step)'s attempts spend the root run's fuel, journaled under the invoking step's path. The built-in scheduler run is exempt (the system-run exemption), and the runs it fires are budgeted. The [runner](#runner) enforces it cooperatively, deciding before every attempt and faulting the run itself when no fuel or time is left, and the checkpoint coordinator verifies it on every save from the journal length and the run's age, refusing a save past either, so a runner that ignores the budget cannot persist the run past it. The budget and the run's creation time are frozen with the run's identity on its first checkpoint. Exceeding one of the three run limits is a [fault](#fault) with a distinct error type per limit (`budget-fuel`, `budget-deadline`, `budget-depth`), recorded by the runner when it honours the budget and by the control plane itself, from the last durable checkpoint, when it does not; the refused save is answered with the `budget-exhausted` problem type, the run is faulted rather than claimed if its budget ran out while it waited. It is resumed only by a *re-budget*: a resume resolves its budget again from its [environment](#environment) as it is now, and proceeds only if the run is inside the result, so the remedy is to raise the environment's limit and resume. Any run can instead be *re-run* (ADR 0072): a new run of the same version, environment and inputs, which the server reads from the original so that a run's inputs are never returned by the API. The vocabulary is the [simulation](#simulation) budget's. |
| <a id="executor"></a>**Executor** | The compiled assembly generated from a [package](#package) that runs the [workflow](#workflow); loaded per [version](#version) with digest verification against its [executor manifest](#executor-manifest). |
| <a id="fault"></a>**Fault** | A [run](#run) is *faulted* when a [step](#step) errors and `failureActions` do not resolve it: terminal-but-recoverable. The fault record captures step id, attempt, error, time, and retriability. A run whose [executor](#executor) fails in a way nothing in the workflow handles is faulted too, with the fixed error `executor-unhandled` (ADR 0068): the exception's message stays off the run record, except on a [draft](#draft) run, whose reader is the workflow's author. A run is faulted before its executor runs at all when the executor is *refused* (`executor-unresolvable`: the version is not in the catalog or not runnable, its content hash diverges, or the assembly fails the loader's verification) or when its transports cannot be bound (`transport-unbound`: a source has no binding in the run's [environment](#environment)). A refusal is the same answer on every attempt. An artifact source that cannot be reached is not a refusal, and leaves the run live to be retried. |
| <a id="host"></a>**Host** | The machine or process a component runs in, and so the ambient credentials that component can reach if code escapes it. Named where the blast radius is the surroundings rather than the component, for example a [runner](#runner) host carrying source secrets and a control-plane machine credential, or the build host carrying the [executor](#executor) signing key. Distinct from [execution backend](#execution-backend), which says where a [run](#run) executes rather than what it can reach from there. |
| <a id="isolation-model"></a>**Isolation model** | The execution isolation a party names (ADR 0058): `InProcess` (a collectible load context inside the [runner](#runner)) or `Isolated` (an out-of-process [execution backend](#execution-backend), e.g. a serverless function). An [environment](#environment) declares the isolation its [runs](#run) *require* (`requiredIsolation`, defaulting `InProcess`); a runner *advertises* the isolation it provides (`isolationModel`); the start gate and the control plane's admission checks match the two. |
| <a id="isolation-posture"></a>**Isolation posture** | The operator view of the [isolation-model](#isolation-model) match: per environment requiring `Isolated`, whether a live, authorized [runner](#runner) advertising `Isolated` serves it — *covered* (isolated-required runs can dispatch) or *uncovered* (they cannot, until one does). |
| <a id="lease"></a>**Lease** | The advisory single-owner, TTL-bounded claim that stops a horizontally-scaled [runner](#runner) fleet double-advancing one [run](#run). |
| <a id="lease-epoch"></a>**Lease epoch** | The monotonic counter the control plane stamps on each [lease](#lease) grant, ordering claims over one [run](#run) (ADR 0065). It is the run's counter and not the process's: the store mints it and persists it with the lease record, so it survives release, expiry, and the instance that granted it, and a second replica cannot re-issue a value already spent. Presented back on every operation over the run and compared rather than believed — a grant above the current one was never held, and one below re-presents a grant the run has moved past. Paired with the [store incarnation](#store-incarnation) it forms the anchor ordering key, so a restore that resets the counter cannot make an old grant outrank a new one; a runner in an anchored environment writes both into its region, beside each other, inside the [checkpoint MAC](#checkpoint-mac) and the [checkpoint digest](#checkpoint-digest). |
| <a id="machine-principal"></a>**Machine principal** | The identity a [runner](#runner) (or any non-human caller) authenticates as, and the single subject the whole [runner ↔ environment binding](#runner-environment-binding) hangs off: a runner registers under it, an [environment administrator](#environment-administrator) authorizes it, and the [runner API](#runner-api) resolves both binding reach and [lease](#lease) ownership from it. Because it is a client rather than a person, it is the client id the token names (`azp`, else `client_id`), falling back to the subject for a deployment identifying its runners by certificate. Registration and the runner API must resolve it identically, since the two disagreeing produces no error anywhere: the runner resolves to no bindings and is offered nothing, exactly as an unauthorized one is. |
| <a id="micro-guest-backend"></a>**Micro-guest backend** | The third [execution backend](#execution-backend) (ADR 0063): `Isolated` execution in a Hyperlight micro-VM on the [runner's](#runner) own machine, with the version's [native binary](#native-binary) (the `linux-musl-x64` target) running under a Unikraft guest kernel. A warm sidecar holds a booted, snapshotted micro-VM per (environment, version) and restores it hermetically for each advance, so every [run](#run) executes in a pristine VM state at local latency; egress is allowlisted to the checkpoint surface and the environment's sources. The sidecar boots only an image whose native attestation verifies under its own trust store, the same executor-signing public key the runner trusts. |
| <a id="native-artifact-attestation"></a>**Native artifact attestation** | The manifest the control plane signs to vouch for a [native binary](#native-binary) (ADR 0055): it binds the binary to its [version](#version) (the [content hash](#content-hash)), its runtime target, its engine version, and its own digest, with a detached signature. Carried under `metadata/native-attestation/<rid>`; a deploy verifies it against a trusted key before deploying the binary, so a binary swapped in storage or transit, or replayed from another version, is caught. The output-side counterpart of the [executor manifest](#executor-manifest) signature. |
| <a id="native-binary"></a>**Native binary** (native artifact) | The per-runtime-target native executable the [AOT builder](#aot-builder) produces from a [version](#version)'s signed [executor](#executor), stored in the [package](#package) as `metadata/native/<rid>`, one per .NET runtime identifier (the **runtime target**). Metadata, so it is excluded from the [content hash](#content-hash): adding or rebuilding a target never changes the version's identity. Native AOT does not cross-compile across operating systems, so each target builds on its own build host. |
| <a id="native-build"></a>**Native build** (build job) | The asynchronous build that produces a [native binary](#native-binary) for one (environment, runtime target): enqueued idempotently per target (re-enqueuing resets it to `Queued` — a rebuild), driven `Queued → Building → Ready \| Failed` by a build worker on the control plane. Producing it is the prerequisite to a [workflow deployment](#workflow-deployment). |
| <a id="nested-trace-record"></a>**Nested trace record** (`subTrace`) | The complete [trace](#trace) of one [sub-workflow](#sub-workflow-step) execution, attached to its parent [step](#step)'s record: `{workflowId, outcome, steps, stepsExecuted, …}` — the same trace shape, recursively. The root trace carries no `workflowId`; sub-traces always do. |
| <a id="re-anchor"></a>**Re-anchor** *(proposed)* | The single operator-signed recovery path for a [tenant anchor](#tenant-anchor) that is lost or legitimately behind the store after a restore (ADR 0065). An operation, not a permission: the operator is shown and signs the exact observed tuple, carrying a strictly monotonic per-run counter so an older signed record cannot be replayed. A rollback or substitution *within* one [store incarnation](#store-incarnation) is deliberately not re-anchorable, because signing it away would bless the attack. The anchor store admits the write by the acceptance predicate today; the runner's verification of the signature waits on the pinned operator key of ADR 0065 decision 8, so until then a hard-faulted run is cancelled envelope-only rather than recovered. |
| <a id="resume"></a>**Resume** | Continuing a [suspended](#wait)/[faulted](#fault) [run](#run) by mode: retry faulted [step](#step), rewind, skip, or **state patch** (an RFC 6902 patch to the run context, then retry). |
| <a id="run"></a>**Run** | One execution of a [workflow](#workflow) [version](#version) (`Pending` → `Running` → `Suspended`/`Completed`/`Cancelled`/`Faulted`), durable and [resumable](#resume). |
| <a id="run-id"></a>**Run id** | The stable identity of one [run](#run): exactly 32 lowercase hexadecimal characters (128 bits), validated at every ingress before any store touch (ADR 0065 decision 9). The grammar makes entropy structurally provable rather than asserted, satisfies every backend's key, path, and document-id constraint by construction, and bounds the covert-channel width to the id's own entropy. The native mint is a "n"-format GUID; a deterministic id comes from the [run-derivation key](#run-derivation-key) and emits the same shape. Debug runs are runs, so a debug-run id carries the same grammar. In-process fixtures are not ingresses and the `WorkflowRunId` constructor deliberately does not enforce it. The management client resolves a bare run id through the store's reach-filtered index query, the same predicate the runs listing pushes down, so a run's visibility by id can never drift from its visibility in the list; naming a run id is at least as explicit as naming a reserved workflow id, so the point lookup sees `$draft` and `$schedule` runs the browse hides. A run id is only ever half a key: every run-state store keys runs by the full [run address](#run-address), so the same id in two environments names two distinct runs. (The working-copy draft-run and trace stores are the exception: they key by run id alone, because a debug run is scoped to one working copy and its id is server-minted, so there is no cross-environment namespace to separate.) |
| <a id="run-address"></a>**Run address** | A [run's](#run) full primary key: the `(environment, runId)` composite (ADR 0065 decision 9), carried by `WorkflowRunAddress` on every run-addressed store operation, in every backend, and at every ingress. Keyed by [run id](#run-id) alone, a caller-chosen id would be a cross-tenant handle; under the composite, the same id in two [environments](#environment) names two distinct runs, and neither is visible from, nor collides with, the other. The environment half is validated against the environment-name grammar in the address constructor as well as at the contract ingress, because the name is half the key in the delimited-key backends. Listings, wait and dispatch queries answer addresses; leases and save conflicts carry them; keyset paging orders by environment then run id. The environment is not a payload field on the index entry. |
| <a id="run-derivation-key"></a>**Run-derivation key** | The deployment secret (at least 256 bits) deterministic [run ids](#run-id) are derived under (ADR 0065 §9): an idempotent start's id is HMAC-SHA256 over the length-framed (owner group, [environment](#environment), workflow id, idempotency key) tuple, and a schedule's scheduler-run id is the same MAC over its deployment-globally-unique schedule id under a distinct domain label, each emitting the grammar's 32 lowercase hex. Keying the derivation is what stops an adversary computing a victim's run id offline and pre-creating it; a start whose derived id is occupied by a run that is not the same logical start is refused as a collision rather than reported as that run. One instance serves the whole deployment (exposed through the management seam), because two components holding different keys would derive divergent ids for the same logical start and say so nowhere. Without a configured key, idempotent starts and the schedules surface refuse — fail closed, never an unkeyed derivation. |
| <a id="runner"></a>**Runner** | An execution host that claims and executes [runs](#run); self-registers and heartbeats to the [runner registry](#runner-registry). |
| <a id="runner-api"></a>**Runner API** | The control-plane surface every [runner](#runner) store interaction goes through (ADR 0065): claim, [lease](#lease), [checkpoint](#checkpoint) save/load, timer and message queries, catalog artifact pulls. Deployed as a separately scalable component sharing the store with the governance API, so execution load never rides the governance request path. Runners hold NO store credentials, and **no platform credential is minted for them either**: a runner authenticates with the machine principal it already has (client credentials, private-key JWT, or mTLS through the deployment's IdP), so a decommissioned host leaves no long-lived platform-issued secret to steal. Environment bindings are resolved per request from a bounded cache, which is what gives the [revocation fence](#runner-revocation-fence) its effect, and [lease](#lease) ownership derives from the authenticated principal rather than from a client-supplied owner string. Tenant separation is enforced at the API, not in runner-resident code. Every run-addressed operation names the run's address, `(environment, runId)`, in its route, and the claimed environment is validated against the principal's bindings before any store touch, refusing exactly as a lost lease does (ADR 0065 §9); release alone skips the bindings check, because a revoked runner handing work back is wanted. |
| <a id="runner-environment-binding"></a>**Runner ↔ environment binding** | One [environment](#environment) per [runner](#runner) (many runners per environment): a runner is provisioned for exactly one environment's [credentials](#credential)/network and must be authorized by that environment's [administrators](#environment-administrator) before it is dispatchable. The lifecycle is `Pending → Authorized`, `Authorized ⇄ Quarantined` ([quarantine](#runner-quarantine)/reinstate), and `Revoked → Authorized` ([revoke](#runner-revocation-fence)/re-authorize); only `Authorized` is dispatchable. The [runner API](#runner-api) resolves a binding by the record's bound machine principal rather than by a runner id, and **no principal may hold a platform binding and a tenant one at once** — that pair is a laundering route out of a sealed environment into the never-sealed platform one, so a principal holding both is bound to nothing at all (ADR 0065 decision 2). |
| <a id="runner-fleet"></a>**Runner fleet** | The set of [runners](#runner) serving one [environment](#environment), scaled horizontally and coordinated only by the [lease](#lease). Named where a property holds across all of them rather than for one, for example a [runner quota](#runner-quota) metered per [owner group](#owner-group) rather than per runner, or a workload that would exhaust every runner an environment has. |
| <a id="runner-pre-authorization"></a>**Runner pre-authorization** | An administrator authorizing a [runner](#runner) id for an [environment](#environment) *before* any runner has registered under it. It names the machine principal that will register (`expectedPrincipal`) rather than the id alone, so the id cannot be squatted in the meantime (ADR 0065 decision 2); an unnamed pre-authorization is refused. Contrast **register-then-approve**, where the runner registers first and the administrator decides on the row it created. |
| <a id="runner-pre-authorization-withdrawal"></a>**Runner pre-authorization withdrawal** | Removing an authorization record no [runner](#runner) has registered against, freeing the runner id. It exists for one situation: a [pre-authorization](#runner-pre-authorization) that named the wrong principal, which no later decision can correct because the principal never moves once bound. It is **not** how a serving runner is stopped — that is the [revocation fence](#runner-revocation-fence), which keeps the record auditable and expires the runner's [leases](#lease). Withdrawal is refused once a runner has registered under the id (ADR 0027). |
| <a id="runner-quarantine"></a>**Runner quarantine** | Temporarily excluding a faulted [runner](#runner) from new dispatch while its in-flight [runs](#run) drain; the status becomes `Quarantined` (not dispatchable). Reinstated to `Authorized` by authorizing it again, with no re-registration. The temporary counterpart of the permanent [runner revocation fence](#runner-revocation-fence). |
| <a id="runner-quota"></a>**Runner quota** | A bound on what one caller may drive through the [runner API](#runner-api) (ADR 0065). Five dimensions are metered — claims, checkpoint requests, checkpoint bytes, [lease](#lease) renewals, and catalog reads — each at two scopes, the [owner group](#owner-group) and the machine principal, with the tighter refusing. Both scopes exist because either alone leaves a hole: a per-runner bound is escaped by registering more runners, which an autoscaling deployment does by itself, and a per-tenant bound alone lets one runaway runner consume its tenant's allowance and starve its own peers. A refusal is a `429` naming the quota and the counter it was measured against, so a runner backs off the dimension it exhausted rather than everything it does, and it is the one non-2xx a runner may hold on rather than fail an advance for — boundedly, because a fabricated refusal is indistinguishable from a real one. Releasing a lease is never metered: refusing it would strand a lease on a runner trying to hand work back. Metering is on unless a deployment states otherwise. The shipped in-process meter counts PER INSTANCE, so a multi-instance deployment admits N times each rate until it supplies a shared-state guard (ADR 0066). Once the [tenancy ledger](#tenancy-ledger) has admitted an owner group, a principal whose environments carry none fails closed (bound to nothing) rather than sharing the deployment counter; eviction from the counter table is per counter and never forgives a deficit. |
| <a id="runner-registry"></a>**Runner registry** | The store-backed table of [runners](#runner) and the [versions](#version) they host; a runner missing heartbeats goes **Stale**, past TTL it is pruned and its [runs](#run) become claimable. |
| <a id="runner-revocation-fence"></a>**Runner revocation fence** | Permanently removing a compromised [runner](#runner) (status `Revoked`) and stopping its in-flight work at once: revoke expires every [lease](#lease) the runner holds at the store, so an authorized peer reclaims its [runs](#run) immediately and the revoked runner's next checkpoint write conflicts. Leases are expired by the authorization's **bound machine principal**, which is what owns them, never by the runner id: the id is client-supplied, so expiring by it would both miss every real lease and let a runner registered under an id equal to another principal's name expire that principal's work on revocation. A row with no bound principal fences nothing, because no runner has claimed the id and so no lease exists. The fence is one of two halves: it stops work already in flight, and re-resolving [bindings](#runner-environment-binding) on renewal and both [checkpoint](#checkpoint) operations stops the runner acquiring more, within the resolver's cache window. Renewal is the load-bearing one, since an unchecked renewal extends the lease indefinitely and the fence would have nothing left to bound. Releasing a run is deliberately never refused, because a revoked runner handing work back is what the platform wants. Enforced in the store and at the API, not on the runner (a cooperative self-check is worthless against a compromised host). Returning needs a deliberate re-authorization. |
| <a id="schedule"></a>**Schedule** | A durable [run](#run) of the built-in scheduler workflow (reserved [workflow](#workflow) id `$schedule`, #896) that fires a target [version](#version) on a cron cadence. On each due occurrence it starts the target through the governed [trigger](#trigger) idempotently, advances a watermark, then suspends on a [timer](#wait) until the next; it rides the same wait index, [lease](#lease), and [environment](#environment) pinning as any run, and is excluded from operator run listings. Only a [runner](#runner) advertising `servesSchedules` claims schedule runs for its environment, so the control plane can refuse a schedule in an environment nothing serves. Between fires the scheduler run sits `Suspended` on its timer [wait](#wait); the schedules surface labels this state **Waiting** (rather than `Suspended`, which reads as broken for a cron cadence). |
| <a id="scoped-step-path"></a>**Scoped step path** | The address of a [step](#step) inside nested [sub-workflows](#sub-workflow-step): `parentStepId/childStepId[/...]` (slash-delimited; safe because Arazzo stepIds match `^[A-Za-z0-9_\-]+$`). A bare stepId addresses a root step only. Used by breakpoints (`pause.beforeSteps`), run-to-here (`until.beforeStepId`), and the [trace](#trace)'s `pausedBefore`. |
| <a id="sealed-checkpoint"></a>**Sealed checkpoint** | A [checkpoint](#checkpoint) whose [payload](#checkpoint-payload) is tenant-encrypted under its [environment checkpoint key](#environment-checkpoint-key) while its [envelope](#checkpoint-envelope) stays control-plane-readable (ADR 0065): governance keeps every verb over the run; the platform, its backups, and every other tenant see only ciphertext for the data. |
| <a id="step-into-step-over"></a>**Step-into / step-over** | The debugger verbs over a [sub-workflow step](#sub-workflow-step): step-over treats it as one unit (the parent record's status/outputs); step-into descends into its [nested trace record](#nested-trace-record), the canvas following, breadcrumb back. Descent over a recorded prefix is client-side [trace](#trace) navigation; acquiring a deeper stop is a stateless replay with a scoped `until`. [Resume](#resume) verbs and the durable [cursor](#cursor) stay parent-scoped. |
| <a id="store-incarnation"></a>**Store incarnation** | The tenant-attested generation of the control plane's durable store (ADR 0065). It increments when the tenant attests a restore, which is what distinguishes "the platform rolled my [run](#run) back" from "I restored a backup and know it". The same observation, opposite responses. Held per [environment](#environment) in the tenant's own anchor store, strictly monotonic and never zero; the first attestation is made when the environment is created, and no run in an environment with none can be opened or checkpointed. The demo's production runner records the first attestation at startup, standing in for the tenant operator. |
| <a id="sub-workflow-step"></a>**Sub-workflow step** | A [step](#step) bound to another [workflow](#workflow) (`workflowId` binding). Executes inline within the parent's [run](#run): no child run entity, no separate [cursor](#cursor), its result materialized on the parent step's record. |
| <a id="tenancy-ledger"></a>**Tenancy ledger** *(proposed)* | The deployment's single row recording every [owner group](#owner-group) admitted to hold an [environment](#environment) here (ADR 0065). It is both the census and the interlock. As a census it answers "how many distinct owner groups are there" from one row rather than a scan of every environment. As an interlock it carries an etag that a create introducing a group must compare-and-swap, so two simultaneous introductions cannot both observe a single-group deployment and both commit. Append-only: deleting the last environment of an owner group does not remove it, because a removal cannot prove absence and commit in one operation. It over-refuses rather than under-refuses, and being recorded in it is never an exemption from the rule. Held by `IEnvironmentStore` rather than a store of its own, so a durable deployment cannot be wired with a ledger that is not durable. It is also the signal that a deployment is tenant-aware: once it has admitted an owner group, a [runner quota](#runner-quota) or capacity count that cannot be attributed to a tenant fails closed. |
| <a id="tenant-anchor"></a>**Tenant anchor** | The small write-ahead record, in a store only the tenant can write (`ITenantAnchorStore`, in memory or on the tenant's own PostgreSQL), holding what the tenant last committed for a [run](#run): the epoch high-water mark, the committed and pending marks (each a [checkpoint digest](#checkpoint-digest) at an ordering key), the [re-anchor](#re-anchor) counter, and the disposition (ADR 0065). It is what makes a control-plane rollback or substitution *detectable* rather than merely undesirable. The control plane holds every [checkpoint](#checkpoint) but cannot rewrite the tenant's record of which one is current. The store enforces exactly the acceptance predicate under a whole-record compare-and-swap; the [runner](#runner)'s sealing store, given one, evaluates the open decision table on every load of an environment on its [key ring](#runner-key-ring) and stages every save with the tenant before dispatching it, and the runner client refuses to serve a sealed environment without one. A refusal is not advanced: the lease goes back and the run is left for the operator. |
| <a id="schedule-registry"></a>**Schedule registry** | The deployment-global map `scheduleId` → (its [environment](#environment), its scheduler [run](#run)) — both the uniqueness gate and the resolver for the schedules surface, whose routes deliberately carry no environment. Registration precedes the scheduler run's creation, so the registry's atomic insert conflict is what enforces the [schedule](#schedule) contract's deployment-global id uniqueness: under the composite `(environment, runId)` run key (ADR 0065 §9) two environments can hold the same run id, so a run-key collision cannot observe a schedule created in another environment. A crash between registration and run creation self-heals (re-creating the same schedule finds its own identical registration and the named start converges); a registration whose run creation was refused is rolled back so it cannot shadow the id. A deleted (cancelled) schedule keeps its registration, because its scheduler run still occupies the derived address. Per-backend, like every management store. |
| <a id="transport-bounds"></a>**Transport bounds** | The two limits of the [execution budget](#execution-budget) that bound a single [step](#step) and not the [run](#run) (ADR 0068): the step timeout, the longest one request may take from the send to the response having been read, and the maximum response size. Set and tightened as the budget's other limits are, and applied where every run executes, to whatever transports its binder returned, so no binder can leave a run unbounded. Unlike fuel and the wall clock they cannot be verified from a checkpoint, so the [runner](#runner) alone enforces them and a breach is not a budget [fault](#fault): the step has failed with no response, and its `onFailure` actions are dispatched without response context, as they are for any failure of the exchange (a refused connection, a body that stops arriving, a body that is not the JSON it claims). Each retry spends fuel, which is what ends a run against a source that never answers. |
| <a id="trigger"></a>**Trigger** | How a fresh [run](#run) is started (as opposed to [resuming](#resume) a suspended one): the HTTP, message, or [schedule](#schedule) trigger surface. All three converge on the governed control-plane start endpoint. |
| <a id="wait"></a>**Wait** | Why a [run](#run) is `Suspended`: a timer (`dueAt`) or a correlated message (`channel` + [`correlationId`](#correlation-id)). |
| <a id="workflow-deployment"></a>**Workflow deployment** | The deployment of a [version](#version)'s verified [native binary](#native-binary) to a function platform for one (environment, runtime target): driven `Queued → Deploying → Deployed \| Failed` by a deploy worker *on the runner* (the runner holds the environment's cloud credentials, ADR 0059), carrying the function invoke URL once `Deployed`. Read-only on the control plane, which records and reports the state the runner drives. |

## Security and governance

Every access decision has **two planes**: WHO can do WHAT (capability scopes) and WHERE (reach).
Both must pass.

| Term | Definition |
|------|------------|
| <a id="access-request"></a>**Access request** | A control-plane resource any principal submits to ask for elevated access to a specific [workflow](#workflow); routed to that workflow's [administrators](#administrator); approval writes an [entitlement](#entitlement). A request can never target a third party, and is decided under the [independent-decision](#independent-decision) rule. |
| <a id="administrator"></a>**Administrator** | A member of a [workflow](#workflow)'s or [environment](#environment)'s governing set (see [environment administrator](#environment-administrator)); the only third-party grant in the access model. |
| <a id="approver-inbox"></a>**Approver inbox** | The queue showing an approver every pending [access](#access-request)/[availability](#availability-request)/[runner](#runner-environment-binding) request across everything they administer, without naming a subject first. |
| <a id="browser-mediated-acquisition"></a>**Browser-mediated acquisition** | Bringing a [source document](#source-document) in through the author's own browser (**paste** the document text, or **upload** the saved file) when it sits behind a browser login/session the control-plane server cannot replay (ADR 0052). The answer for "a document I can open in my browser once I have logged in": the browser is the authenticated agent, and no server-side credential custody is involved. The first-class alternative to a [source fetch](#source-fetch) for session-protected documents. |
| <a id="audit-chain"></a>**Audit chain** | One writer's run of audit records in an [audit sink](#audit-sink) (ADR 0069): a JSON Lines stream in which every record carries the chain's id (a version 7 UUID, so a writer's chains sort by when they were opened), its sequence from zero, and the hash of the line before it. Its first record is the *open record*, which names the *writer*, the instance the chain belongs to (an id that defaults to the machine's name and under which the sink keeps its chains), and the chain it continues. Each control plane instance owns its own chain and coordinates with no other. A writer abandons a chain it failed to append to, since that chain's last line is then unknown, and opens a new one whose first record names the abandoned chain and the hash of the last record known stored there (the *continuation*); a chain that reaches its record limit rolls over the same way, and a writer that starts continues its own last chain, read back from the sink, under a head signed at once. That continuation freezes the tail the last process left unsigned and does not authenticate it. `AuditChainWriter` writes it and `AuditChainVerifier` checks it, naming the first break: a torn tail, a malformed or foreign record, a sequence gap, or a hash mismatch. |
| <a id="audit-anchor"></a>**Audit anchor** | A signed [audit chain](#audit-chain) head as it is published outside the [audit sink](#audit-sink) (ADR 0069): an `audit.head` span and a log record carrying the chain's id, the head's sequence, the hash it vouches for, the key id and the signature. A collector that holds it can show that a chain offered later is not the chain that was signed, since a chain cut short of the anchor or rewritten after it cannot hold it. `AuditChainVerifier` checks a chain against an anchor it is given. |
| <a id="audit-head"></a>**Audit head** | A record of an [audit chain](#audit-chain) whose signature, under the audit's own key, vouches for every record before it (ADR 0069). Signed by default every 64 records or once the oldest unsigned record is 60 seconds old, and when a chain is left in good order. The records after the last head are the *unsigned window*: altering or removing them is shown by no signature yet. A head that cannot be signed degrades the deployment's health and never fails a request. |
| <a id="audit-read-record"></a>**Audit read record** | The [audit chain](#audit-chain)'s record of a read, or of an attempt at one (ADR 0070): the actor, the target and the *disclosure tier* (`full`, `redacted`, `refused`), never what was read. A read that discloses a payload is recorded before it is answered and is refused when its record cannot be appended; a refusal record never fails the request. A *refusal record* is the record of a `GET` that names a resource and answers with a non-disclosing not-found: the probe, by the actor, for the id it asked after. A subject's refusals are recorded up to a bound a minute (60 by default) and past it as one record carrying the count that was *suppressed*. A runner keeps an [audit chain](#audit-chain) of its own, since it has no path to the control plane's [sink](#audit-sink) and is not trusted to report into it, and records there every secret it resolves, naming the secret's reference and never the material. On the runner a secret is resolved whether or not its record can be appended, because run execution is never gated on the sink. |
| <a id="audit-sink"></a>**Audit sink** | The append-only destination every [governance audit](#governance-audit) record, read record and authentication refusal is appended to synchronously after the action commits (ADR 0069), outside the operational store. It stores the bytes of any number of [audit chains](#audit-chain) and nothing else (`IAuditSink`; a directory of files for development, memory for tests). Each record carries the hash of the previous one, the chain head is signed on a cadence with the executor package signing stack under the audit's own key, and every signed head is also emitted through the span and log so an external collector holds anchors the sink's owner cannot rewrite. The secured postures assert a sink and a head signer at startup and refuse governance mutations while the sink is unavailable; reads and runs are never gated on it. Verified by `arazzo-runs audit verify`, which reads the sink directly and not through the control plane. |
| <a id="audit-subject"></a>**Audit subject** | The identity a [governance audit](#governance-audit) record names as its actor: the principal's canonical subject, resolved from the deployment's configured subject claim (`sub` by default, the claim a [grant binding](#grant-binding) keys on), then the authorized party or client id for a client-credentials token that names no subject, then the authentication name, and `anonymous` when the request carries no principal; paired with the actor's [owner group](#owner-group) read from its own stamped [`sys:`](#internal-sys-tag) identity. Resolved once per request by the access binding, so every surface records the identity authorization used. Never the OIDC display name, which is a label for approver queues (`requesterLabel`), not an identity. |
| <a id="authentication-telemetry"></a>**Authentication telemetry** | What the host adds in one registration, `AddArazzoAuthenticationTelemetry()` (ADR 0071), since the host owns authentication (ADR 0042): one middleware that reads each request's authentication result, whatever the scheme. A counter dimensioned by scheme, outcome and reason carries the rate; a failure appends an *authentication record* to the [audit chain](#audit-chain) naming the scheme, the reason, the remote address and, where the result named them, the issuer and subject, and never token material. Failure records are capped for each remote address, with the suppressed count recorded. A request with no credential is not a failure. Required in the secured postures. The [runner API](#runner-api) records its own refusals of a [machine principal](#machine-principal) in the same chain, as governance records whose outcome is the refusal (`refused-no-principal`, `refused-forbidden`, `refused-conflict`, `refused-not-found`, `refused-quota`), capped for each principal. |
| <a id="capability-scope"></a>**Capability scope** | A token capability tier (`catalog:read`, `runs:write`, `credentials:write`, …) gating API operations. Say "capability scope", not bare "scope", where ambiguity is possible. |
| <a id="checkpoint-callback-token"></a>**Checkpoint callback token** | The short-lived, run-scoped bearer token a function dispatched by an out-of-process [execution backend](#execution-backend) presents on every [checkpoint](#checkpoint) load and save (ADR 0062): `{expiryUnixSeconds}.{base64url(HMAC-SHA256(secret, "environment:runId:expiry"))}`, an HMAC over the run's full `(environment, runId)` [address](#run-address), minted by whichever component dispatched the function and validated by the checkpoint surface against the address in the request URL, so a token minted for one environment's run does not validate for the same run id at another. It is the whole authority that surface has to work with, because its caller is a machine acting for one run and holding no principal of its own, so nothing else could say which run a callback may touch: **the token is that surface's [reach](#reach) gate**. A surface is therefore not served at all unless a secret is configured to validate one. A leak authorises exactly one run, and only until the token expires. Distinct from the `checkpoint-token` subkey of the [payload key](#payload-key) and from the checkpoint protection key that wraps checkpoints at rest; see [normalization decision K](#normalization-decisions). |
| <a id="channel-credential"></a>**Channel credential** | The [credential](#credential) of an AsyncAPI (channel) [registered source](#registered-source) (ADR 0051): the same auth kinds as HTTP, read as credential *shapes* (`bearer` = a token/SAS presented at connect, `basic` = SASL user/password, `oauth2ClientCredentials`, `mtls`), plus the environment's broker **server URL** as non-secret `serverUrl` config (the channel analogue of the HTTP `baseUrl` override). The transport protocol comes from the source document's `servers[].protocol`, never the binding; the [runner](#runner) builds the source's message transport from the binding at bind time via a protocol-dispatched factory. Broker auth is connection-time, so a channel credential — like `mtls` — is connection-scoped and never usage-scoped to an individual run. |
| <a id="connected-provider"></a>**Connected provider** | An OAuth/OIDC provider whose **content API accepts a brokered user token**, registered by a deployment so a [source fetch](#source-fetch) can retrieve a document *as the user* (ADR 0052). This is the git-host and API-platform class (GitHub, GitLab, Azure DevOps, bearer-fronted API catalogs), the **specialized** fetch tier — not a way to reach a portal whose document endpoint is guarded by a browser session (that is [browser-mediated acquisition](#browser-mediated-acquisition)). Configuration: an OIDC issuer (endpoints via discovery) or explicit authorize/token endpoints, a client id + secret reference, scopes, and the host patterns it covers. GitHub is a connected provider whose extra repos/browse surface sits on top of the shared machinery. |
| <a id="credential"></a>**Credential** | A per-[registered-source](#registered-source), per-[environment](#environment) binding of a **[secretRef](#secretref)** plus non-secret configuration. For an OpenAPI source the kinds attach per request (except connection-scoped `mtls`); for an AsyncAPI source the same kinds describe the broker credential — see [channel credential](#channel-credential). Its **status** (`Valid`/`ExpiringSoon`/`Expired`) is derived on read; rotation is re-pointing the reference. |
| <a id="data-key"></a>**Data key** | The per-encryption AES-256-GCM key for one [checkpoint payload](#checkpoint-payload), derived from the [payload key](#payload-key) over `(environmentId, keyId, runId, sequence, salt)` with every field length-framed (ADR 0065 decision 5). Derived, never wrapped and stored, so there is no key blob in the row and no KMS call on the save path. The salt is drawn fresh inside every encryption *operation*, never per logical checkpoint, because re-encrypting after a `409` with a cached salt would repeat a `(key, nonce)` pair; the nonce is the counter's first value, which is safe only because of that. |
| <a id="digest"></a>**Digest** (identity digest) | The canonical digest over a stamped identity set — equal iff set-equal. The stable key [administrators](#administrator) are indexed by and removed by; [membership](#membership) lookups enumerate a caller's subset digests against it. |
| <a id="eligibility"></a>**Eligibility** | The PIM-style "you may self-elevate this" grant (*approve-as-eligible* on an [access request](#access-request)): durable permission to activate access JIT without re-approval. Eligible is not active — wielding requires an explicit, audited, time-boxed activation. |
| <a id="entitlement"></a>**Entitlement** | A per-principal stored grant (never in the IdP) binding a subject claim to a [capability scope](#capability-scope) and a [reach](#reach), optionally time-boxed. Capability = token claims ∪ stored entitlements. |
| <a id="external-schema-reference"></a>**External schema reference** | An inputs-schema `$ref` to an attached `jsonschema` document (never a `sourceDescription` — the Arazzo spec pins that enum). The PREFERRED base is the document's absolute root `$id` (its canonical identity); the virtual relative path `schemas/<name>#<pointer>` is the fallback for an `$id`-less document. Packaged alongside the [source documents](#source-document) at [publish](#publish) and registered with the generation resolver under both identities. A reference matching no attached document is a validation error. |
| <a id="governance-audit"></a>**Governance audit** | The retained trace a governance action leaves (ADR 0038): a span on the `Corvus.Arazzo` activity source naming the [audit subject](#audit-subject) (actor and tenant), the target resource, the outcome and, for an environment-scoped action, the environment, plus an audit-grade log record. Emitted for security-posture changes and for the actions that exercise access — [access-request](#access-request) decisions including the [independent-decision](#independent-decision) refusal and self-elevation, [credential](#credential) custody, [grant binding](#grant-binding) and [rule](#security-rule) authoring whether by an operator, the bootstrap or the approval service, [runner authorization](#runner-environment-binding), [promotion](#promotion), administrator transfers, and run start. Payload-safe by construction: it carries only identifiers and a controlled outcome label, never a step output or secret. The mutation counterpart of the read-access audit that the sensitive [step-output disclosure tier](#step-output-disclosure-tier) applies to a journal read. |
| <a id="grant-binding"></a>**Grant binding** | A `{claimType, claimValue}` → per-verb [reach](#reach) mapping (each verb `Denied`, `Unrestricted`, or a set of [rule](#security-rule) names), optionally pinning further [identity dimensions](#identity-dimension) (`additionalClauses`, matched as a conjunction by [membership](#membership)). A verb's rule set is a **conjunction**: every named rule must admit the row, so adding a rule only ever narrows the grant. Either/or reach is a **union of bindings** (one binding per route) — grants compose as OR across a caller's matched bindings, never within one rule list. The API/wire name is *security binding*; docs and UI say **grant binding**. |
| <a id="grantee"></a>**Grantee** | A real person/team/role/workflow named by governance surfaces, resolved (via the [merged grantee search](#merged-grantee-search), [principal-directory](#principal-directory) search, observed-identity typeahead, or a validated well-known subject id) to the exact **[resolved identity](#resolved-identity)** the deployment stamps. A write names a grantee by its **grantee reference**, `{kind, value}` (plus a display label), and the control plane resolves it again before storing it (ADR 0008): the directory, then the recorded observed identities, then the policy's mapping of the kind; a client never supplies an identity. |
| <a id="identity-dimension"></a>**Identity dimension** | One `{dimension, value}` key of a stamped [`sys:`](#internal-sys-tag) identity (e.g. `sys:tenant`, `sys:sub`, `sys:iss`). An **ambient identity dimension** is derived from request context (host, route, gateway header) rather than the token, stamped identically at runtime and grant-authoring moments. |
| <a id="independent-decision"></a>**Independent decision** | The rule that no request is ever decided by its own requester: approve and deny on [access](#access-request) and [availability](#availability-request) requests refuse the requester (403 `own-request`) even when they administer the target, so `decidedBy` always names a second pair of hands; the requester's own exit is *withdraw*. For access requests the bar keys on the request's *subject* (who the decision would empower), not the audit actor. The designed exception is self-elevation of an [eligibility](#eligibility): the eligibility itself was independently decided. |
| <a id="internal-sys-tag"></a>**Internal (`sys:`) tag** | A reserved-prefix [reach label](#reach-label) stamped by the deployment shell: immutable, client-invisible, rejected on user input; the unforgeable key administration and [grants](#grant-binding) rely on. |
| <a id="membership"></a>**Membership** (identity matching) | The governing match rule for administration, [grant-binding](#grant-binding) applicability, and credential [usability](#usability): a principal matches a named identity iff the principal's whole stamped [`sys:`](#internal-sys-tag) identity **contains** it (subset test) — never by exact set-equality, and never against raw token claims. |
| <a id="merged-grantee-search"></a>**Merged grantee search** | The [grantee](#grantee)-search default when a [principal directory](#principal-directory) is configured: the directory (every searchable kind) unioned with the observed-identity typeahead, directory-preferred on a `(kind, value)` collision, as one bounded unpaged result set. A directory failure degrades a merged search to observed results; only an explicit `source=directory` search surfaces it (502). |
| <a id="one-shot-fetch-secret"></a>**One-shot fetch secret** | A header credential the author pastes to authenticate a single server-side [source fetch](#source-fetch) against an endpoint that accepts one in a request header (ADR 0052): a bearer/PAT, an API key (a named header), or Basic — the same schemes the §13 [credential](#credential) machinery models. Used once, never stored, never logged. |
| <a id="owner-group"></a>**Owner group** *(proposed)* | The tenancy an [environment](#environment) belongs to (ADR 0065), stamped at create from the authenticated principal under the deployment's unforgeable internal prefix, and immutable thereafter. A catalog [version](#version) carries the same stamp from its creator, and every [run](#run) of it inherits it; a version is made [available](#availability), scheduled and run only in an environment whose owner group is its own, so the group a run is stamped with is the group its capacity is charged to. Stamped whether or not a row-security policy is configured, because ownership and [reach](#reach) are different questions: an earlier form of the multi-tenancy gate read ownership from the reach policy and was therefore unevaluable in the modes that forbid one. In a mode that does not enforce reach it is provenance only and is never presented as an isolation boundary. Where no reach policy is configured it is read from the deployment's declared owner-group claim; a principal carrying no such claim stamps none, so a deployment that publishes nothing to tell owner groups apart has exactly one. The prefixed key is refused in operator-supplied tags in every mode, so a client cannot name itself into another group through a create body. |
| <a id="partial-identity"></a>**Partial identity** | A [grantee](#grantee) resolution that yields only some of the [identity dimensions](#identity-dimension) the deployment stamps. Flagged because under [membership](#membership) matching a partial identity is *broader* than intended — every principal whose stamped identity contains those dimensions matches it — and authoring a grant on one raises the broadening-overlap advisory naming any subsumed [grantees](#grantee). |
| <a id="payload-key"></a>**Payload key** | The 32-byte symmetric key, held only in the tenant's custody on the [runner key ring](#runner-key-ring) and never by the control plane, that every [checkpoint payload](#checkpoint-payload) secret derives from (ADR 0065): the per-encryption [data key](#data-key) plus the per-generation `envelope-mac`, `wait-index`, and `checkpoint-token` subkeys. Its id and rotation are recorded by the [environment checkpoint key](#environment-checkpoint-key) registration. |
| <a id="persona"></a>**Persona** | A named operator archetype the UX targets (operator/SRE, publisher/owner, connections admin, security admin, approver, requester); the demo's persona selector drives [capability-scope](#capability-scope) gating from one source of truth. |
| <a id="policy-refresh-bound"></a>**Policy refresh bound** | The interval within which every control-plane replica reloads the [security rules](#security-rule) and [grant bindings](#grant-binding) from the shared store, so a grant revoked through one replica stops on all of them; 5 seconds by default, set by the host when it registers the refresh, and a control plane in a reach-enforcing posture refuses to map a persistent policy without one (P1-14). |
| <a id="platform-ceiling"></a>**Platform ceiling** | The unconditional bound on what an approved [access request](#access-request) may write (ADR 0010): [capability scopes](#capability-scope) at most the request's intersected with the run-access allowlist, subject pinned to the requester, [reach](#reach) pinned to the target workflow through the [per-workflow reach rule](#per-workflow-reach-rule), expiry at or before the deployment maximum. Enforced in the grant path itself, whichever approval strategy decided. The code also says *platform cap*; docs and UI say **platform ceiling**. |
| <a id="principal-directory"></a>**Principal directory** | The pluggable directory seam (LDAP/AD, Keycloak, SCIM, Entra ID, Okta, Google) that searches people/teams/roles and returns [resolved identities](#resolved-identity), each expanded to full [membership](#membership) (a `sys:group`/`sys:role` per membership). It resolves *who*, never *what they may do*. |
| <a id="provider-connection"></a>**Provider connection** | The per-`(principal, provider)` authenticated link to a [connected provider](#connected-provider): minted by the brokered popup flow, the user token held server-side (in-process custody), never handed to the browser. Reach is whatever the user's own identity can see. |
| <a id="reach"></a>**Reach** | Row-level visibility: which records a caller can see/affect per verb (read/write/purge), defined by [security rules](#security-rule) and [grant bindings](#grant-binding). |
| <a id="reach-label"></a>**Reach label** | The umbrella term for the `{key, value}` labels [reach rules](#security-rule) match against: **security tags** on catalog [versions](#version) and [runs](#run) (inherited by runs from their version), **management tags** on [environments](#environment), [registered sources](#registered-source), and [credentials](#credential). Never say bare "tags" — *user tags* are the separate free-form display/filter metadata. |
| <a id="reach-mirror"></a>**Reach mirror** | The queryable projection of a row's *current* [reach labels](#reach-label) that a store's server-side [reach](#reach) predicate evaluates (ADR 0067): a side table on the relational backends, a `securityTags` array on Mongo and Cosmos, label sets/subjects/entities on the broker-class backends. Written with the document and re-set in the same write when an update re-tags, because a stale mirror leaks the row to the scope it left and hides it from the scope it joined at once, while the store's own point read disagrees with its own list. |
| <a id="read-audit"></a>**Read audit** *(designed)* | The three-tier rule for reads (ADR 0070). A read that discloses a payload tier is audited with the actor, the target and the [disclosure tier](#step-output-disclosure-tier). A read refused as a non-disclosing not-found because the row is outside the caller's [reach](#reach) is audited with the actor, the target kind and the requested id, since the refusal is the probing signal and the record is internal. Successful lists, searches, counts and index-row gets are metered, not audited. Every read record carries the same [audit subject](#audit-subject) and dimensions as a mutation record and lands in the same [audit sink](#audit-sink). |
| <a id="registered-source"></a>**Registered source** | An entry in the control plane's `/sources` registry: a named [source document](#source-document) registered once and referenced by [workflows](#workflow), with per-[environment](#environment) [credentials](#credential). A `jsonschema` source registers a JSON Schema document for **[external schema references](#external-schema-reference)**. |
| <a id="resolved-capability-view"></a>**Resolved capability view** | The Access Overview's `capabilities` section: the [capability scopes](#capability-scope) a [grantee](#grantee)'s matched [bindings](#grant-binding) confer, resolved exactly as the runtime resolver does — expired bindings confer nothing; an [eligible](#eligibility)-only binding shows as *eligible*, not active. |
| <a id="resolved-identity"></a>**Resolved identity** | The full stamped [`sys:`](#internal-sys-tag) identity a [grantee](#grantee) resolves to: the principal's own [identity dimensions](#identity-dimension) plus a `sys:group`/`sys:role` per membership (full membership expansion), exactly as the deployment's runtime resolver stamps it. Grants are authored against it and [membership](#membership) matching compares against it, so the authoring and runtime moments cannot drift. |
| <a id="secretref"></a>**secretRef** | A scheme'd *reference* to secret material in an external store (`keyvault://`, `vault://`, `env://`, …) — never the material itself. Only [runners](#runner) resolve it, at bind time. |
| <a id="security-rule"></a>**Security rule** | A named, reusable boolean row-filter expression over [reach labels](#reach-label), written in the `simple`-[criterion](#criterion) grammar (e.g. `tenant == $claim.tenant`). The reusable WHERE vocabulary a [grant binding](#grant-binding) points at. |
| <a id="self-elevation-guard"></a>**Self-elevation guard** | The server-side check on [grant binding](#grant-binding) create and update that refuses a binding conferring anything (read, write or purge [reach](#reach), or a [capability scope](#capability-scope)) on the author themselves, decided by [membership](#membership): the author's stamped [`sys:`](#internal-sys-tag) identity contains the binding's claim and every `additionalClauses` clause (ADR 0014). An `eligibleOnly` binding counts, since stored [eligibility](#eligibility) is honoured by self-elevation; a binding that confers nothing does not. The `*` primary contains every caller, the author included. Inert where there is no caller to elevate (the unscoped posture). A refusal is audited as `refused-self-elevation`. |
| <a id="source-fetch"></a>**Source fetch** | The server-side retrieval of a remote [source document](#source-document) (`POST /sources/fetch`): no browser CORS, one fetch implementation. Its authentication is **matched to how the endpoint is protected** (ADR 0052): none for a public URL; a header credential the author holds (a [one-shot fetch secret](#one-shot-fetch-secret) or a saved workload [credential](#credential) binding); or a [connected provider](#connected-provider) token where the endpoint's content API accepts one. A document behind the author's own browser session is *not* fetchable server-side and comes in through [browser-mediated acquisition](#browser-mediated-acquisition) instead. The caller then attaches or registers the result; the fetch itself stores nothing. |
| <a id="step-output-disclosure-tier"></a>**Step-output disclosure tier** | The §14 gate on reading a [run](#run)'s recorded step OUTPUTS (its step journal), above ordinary run-metadata [reach](#reach): step outputs can carry the sensitive data the workflow processed (for a KYC flow, identity data). Reading them needs the `runs:outputs:read` [capability scope](#capability-scope) in addition to `runs:read` (the baseline tier). A [version](#version) an author classifies `outputsSensitivity: sensitive` then has its whole journal REDACTED for callers below the stronger grant — write [reach](#reach) on the run — so a read-only observer sees each step marked redacted with no payload, while an operator reads it in full. Every read of the journal is audited (a `workflow.journal.read` span plus an audit log record) at the disclosure tier it reached: *full*, *redacted*, or *refused* (the run was out of reach or absent) — so a sensitive read, disclosed or not, always leaves a trace. |
| <a id="tenant-shell"></a>**Tenant shell** | A deployment wrapper that ANDs a mandated [rule](#security-rule) (e.g. `sys:tenant == $claim.tenant`) and [internal-tag](#internal-sys-tag) stamping into every decision, so multi-tenant isolation is inescapable and users can only narrow within it. |
| <a id="usability"></a>**Usability** | The label-superset test (`IsUsableBy`) governing which [runs](#run) may use a [credential](#credential): the run must carry all the binding's usage tags. Distinct from [reach](#reach) (superset test, not rule match). |
| <a id="wait-index-blinding"></a>**Wait-index blinding** | Storing a [wait](#wait) match key and [correlation id](#correlation-id) as a MAC under the `wait-index` subkey of the [payload key](#payload-key), so the control plane can match a delivered message to a parked [run](#run) without learning the business key (ADR 0065). The MAC input is length-framed, and the subkey includes `environmentId`, so one tenant's `staging` message cannot wake its `prod` run. As built, a run in an environment on the [runner key ring](#runner-key-ring) parks on the *blind wait index*, `{keyId}.{base64url(HMAC)}`, in place of its channel and correlation id, in its region and in the index column; a channel-only wait is blinded with a sentinel kind byte in place of the correlation field, so absence is its own value and it is one constant per channel; the runner API takes a message claim by index and never sweeps a sealed environment by channel; and the delivering runner hands back a run whose region says it parked on an index it did not query. The run-level [correlation id](#correlation-id) is not yet blinded, since it is the control plane's own trace id until an initiator supplies one at a sealed start. |
| <a id="per-workflow-reach-rule"></a>**Per-workflow reach rule** | The per-workflow [security rule](#security-rule) the [platform ceiling](#platform-ceiling) pins a grant's reach to: named `workflow-access:<workflowId>`, expression `sys:workflow == '<workflowId>'`, system-owned, written idempotently by the approval service on the first grant (ADR 0010). The name prefix is reserved: the authoring API refuses to create or update a rule under it (audited `refused-reserved-name`), and the service checks an existing rule's expression before reusing it, so the name can never be squatted ahead of an approval to widen every later grant. |

## <a id="normalization-decisions"></a>Normalization decisions

Conflicts found by the 2026-07 docs sweep, and the canonical resolutions. Renames were marked ⚠
while pending; the 2026-07 normalization pass has since applied them all, so no ⚠ remain.

| # | Conflict | Resolution |
|---|----------|------------|
| A | "Scope" means (1) capability tier, (2) the per-verb grant value `Scoped`, (3) the UI's "Scopes" panel which actually edits security *rules*. | (1) is canonical: **capability scope**. Say **scoped reach** for (2). The UI surface is **Rules** (tag `arazzo-rules-panel`); `ui-design.md` and `security-ui-design.md` copy updated. |
| B | The grant object has four names: grant / security binding / grant binding / claim→rule binding. | **Grant binding** is canonical in docs/UI; **security binding** is recorded as the API/wire synonym. |
| C | "Source" is overloaded: in-document description, the file, the registry entry, and the UI "Sources" tab that actually manages credentials. | Three precise terms: **source description**, **source document**, **registered source**. The credential-management tab is now **Connections** (was "Sources"); demo and `ui-design.md` updated. |
| D | "Draft" is also allocation-campaign jargon for a pooled document being built at a store's write leaf (`ValidateDraft`). | **Draft** is the lifecycle term only. Scope-qualify the allocation jargon as **write draft** (or rename to *builder document*) in campaign docs/code as touched. |
| E | "Publish" as mint-a-version vs the `catalog-design.md` "publish/hosting service" that serves a version at an endpoint. | **Publish** = mint a catalog version. The endpoint-serving service is the **hosting service** (`catalog-design.md` future-phase section updated). |
| F | Bare "tags" ambiguity (user tags vs security tags vs management tags). | Always qualify: **user tags** / **security tags** / **management tags**; **reach labels** is the umbrella. |
| G | The Access area was once labelled "Reach scopes", re-fusing the two planes. | Say **reach rules**; avoid "reach scopes". |
| H | "Readiness" described as a soft check in one place and a hard gate in another. | Readiness is a **hard gate** on promotion and the add-workflow wizard; views may *display* readiness, but promotion never bypasses it. |
| I | "Deployment" carried two senses, an installation of the platform and the act of publishing one version's native binary to a function platform. The glossary used both while defining only the second, and the ADRs use the first throughout without defining it. | **Deployment** is the installation. The narrower sense keeps its qualifier as **workflow deployment** and is never shortened to "deployment" in prose. Raised by the [threat model](threat-model.md), which needs the installation sense to name a blast radius. |

| J | "Digest" now means two unrelated things: the [identity digest](#digest) over a stamped identity set, and the [checkpoint digest](#checkpoint-digest) introduced by ADR 0065. | Bare **digest** keeps its existing meaning (identity digest). Always write **checkpoint digest** in full for the ADR 0065 sense; it is a content hash over checkpoint bytes and shares nothing but the word. |
| K | "Checkpoint token" names two unrelated secrets: the ADR 0062 bearer token a dispatched function presents on its callback, and the `checkpoint-token` subkey ADR 0065 derives from the [payload key](#payload-key). A third, the checkpoint *protection* key, wraps checkpoints at rest. | Write **[checkpoint callback token](#checkpoint-callback-token)** in full for the ADR 0062 credential and **checkpoint-token subkey** for the ADR 0065 derivation. Never bare "checkpoint token": the two have different holders, lifetimes, and consequences on disclosure. |
