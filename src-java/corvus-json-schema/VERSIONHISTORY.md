# Version History

The version history of `io.github.corvus-dotnet:corvus-json-schema`, the Java port of the Corvus.Text.Json V5 runtime evaluator. It is versioned independently of the Corvus NuGet packages, whose history is in the repository's [VERSIONHISTORY.md](../../VERSIONHISTORY.md).

## V0.1.3

V0.1.3 fixes wrong results for patterns of several forms, runs patterns with a backreference that earlier versions refused, and limits what a pattern from outside can cost: the time of a match, and the size of a pattern. Versions 0.1.0 to 0.1.2 are affected.

### New features

- **A match of a pattern is limited to 1 second.** A schema and an instance that come from outside could make a match of a `pattern` or `patternProperties` regular expression run for as long as they liked: `^(?:(a+)\1*)+$` takes time that doubles with each "a" of a string that ends in "b". `CompileOptions.Builder` has `patternMatchLimit(Duration)`, which defaults to 1 second (`CompileOptions.DEFAULT_PATTERN_MATCH_LIMIT`), and `noPatternMatchLimit()`. A match that goes over the limit is abandoned, and `isValid`, `validate` and `evaluate` throw the new `PatternMatchLimitException`. None of them answers for it. `java.util.regex` has no limit of its own: the library counts the characters the engine reads and the times it asks for the length, reads the clock every 4,096 of them (more often for a long translation), and writes an empty lookahead into the translation where the engine could go on without either. Nothing is allocated for it. This changes behaviour: a match that ran for more than a second used to end, and now throws.

- **A match that runs out of stack is the same error.** `java.util.regex` matches a repetition of a group by recursion, and `^(a|b)*$` threw `StackOverflowError` on a string of a few thousand characters. Alternatives that are each one character are now written as one class, and a repetition whose body has one way to match and that what follows cannot start inside, such as `^"(?:[^"\\]|\\.)*"$`, is written possessive. Neither recurses. A repetition that still does, such as `^(?:\w+\s?)*$`, throws `PatternMatchLimitException` with `isStackLimit()` true when the stack of the thread runs out.

- **A pattern over a limit of size is refused as too large.** A pattern has at most 1,048,576 characters, groups nested 200 deep, 32,768 capturing groups and 524,288 ranges in its classes, and its translation at most 1,048,576 characters, 8,192 ways through one part, 16,777,216 characters written on the way and 200 copies of a body. A pattern over one throws the new `PatternTooLargeException` when the schema is compiled. It is a `SchemaCompilationException`, and its message names the limit and never says the pattern is invalid. The limit on the translation counts the same length on Java 17, 21 and 25. `SchemaCompilationException` is no longer final.

- **The cache of compiled patterns is bounded, and an evaluator keeps matchers for its own schema only.** The library kept every pattern it compiled in a cache of the process, so that identical patterns share what was compiled, and the cache was never emptied. Each pattern had a number of the process, and an evaluator kept its matchers of `java.util.regex` in an array indexed by that number. So a process that compiles schemas from outside kept every pattern it had ever seen, and the evaluator of a schema with one pattern held an array as long as the count of patterns the process had compiled: in the test of this, 4,006 places for a schema with three patterns. The cache now holds 1,024 patterns at most, counted as 64 MiB at most. Over either bound the patterns compiled first go, oldest first, and a pattern counted as more than 2 MiB is not kept at all. These are the bounds of the Go module and the Rust crate. A validator holds the patterns of its own schema, so a pattern that has left the cache is still matched, and is compiled again only for a schema compiled later. A pattern is counted as 512 bytes, 2 for each character of its source and 130 for each character of its translation: of 59 shapes of pattern measured on Java 17, 21 and 25, none held more than a third of its count. A pattern that the engine runs now has a place among the matchers of its own schema, given when the schema is compiled, so an evaluator's array is as long as its schema has such patterns. Compiled code and the interpreter read the same place, nothing is allocated in the steady state, and the cache is read only when a schema is compiled. A process that compiled 60,000 schemas with two patterns each on one thread, in a heap of 96 MB, ran out of heap after 42,000 of them (30,000 with the interpreter), and now ends with 5 MB in use (6 MB with the interpreter).



### Bug fixes

- **A separated list with a `$` inside it.** The library matches a pattern of the form `^item(separator item)*$`, such as `^([a-z]+)(\.[a-z]+)*$`, without a regular expression (and likewise the forms with `+`, and `^(item separator)*item$`). It read the first item and the repeated group as sequences of characters and classes, and a `$` at the end of either was read and then dropped. So `^x(,a$)*$` was matched as `^x(,a)*$`. A `$` holds only at the end of the string, so the group of `^x(,a$)*$` can match once at most, and only as the last thing in the string. `{"pattern": "^x(,a$)*$"}` was valid for `"x,a,a"`, where it is not. `^x$(,a)*$` was valid for `"x,a"`, and `^(a,$)*b$` for `"a,b"`. Compiled code and the interpreter were both affected, and so was a pattern used for `patternProperties` or `propertyNames`. A list with a `$` at the end of its first item or of its group is now matched by the regular expression. An escaped `\$` is a literal character and such a list is matched as before. No other form of pattern was affected. A table of 101 patterns with an anchor, a word boundary or a lookaround inside one of the forms the library matches by itself, with answers from V8, is now part of the tests.

- **A counted repetition whose body can match the empty string.** In ECMA-262 a repetition that must run a number of times runs that many, and an iteration that matches nothing counts as one of them. `java.util.regex`, which runs the translated pattern, goes on to what follows the repetition after any iteration that matched nothing. So for `(^|x){2}a` on `"xa"`, ECMA-262 takes `^` and then `x`, and `java.util.regex` took `^` and looked for `a` at once. `{"pattern": "(^|x){2}a"}` was not valid for `"xa"`, where it is. `^(?:-|(?!$)){2}$` did not take `"-"`, and `(\b|a){2}a$` did not take `"aa"`. The patterns affected have a group with a count of two or more (`{2}`, `{2,}`, `{2,5}`, lazy or not) whose body matches the empty string in some places only: through `^`, `$`, `\b`, `\B`, a lookaround or a backreference. A body that matches the empty string anywhere, such as `(a|)` or `(a*)`, was not affected, nor were `*`, `+`, `?` and counts below two. The answer was only ever "does not match" where it should have been "matches". Compiled code and the interpreter were both affected, and so was a pattern used for `patternProperties` or `propertyNames`. Such a repetition is now written for `java.util.regex` with a copy of its body for each iteration it must run, followed by the iterations it may run. A repetition that would need more than 200 copies in all, such as `(^|x){201}`, is refused with `SchemaCompilationException` ("Unsupported regular expression"), and is not run with another meaning. A pattern that nests such repetitions three deep can take much longer to answer than it did, as every way of running the iterations is now tried.

- **A backreference to a group of a repetition, of an alternative or of a lookahead.** In ECMA-262 a backreference matches the text its group captured on the way the match took, and the empty string when the group did not take part. The groups of a repeated body are unset when an iteration starts, and an iteration that matches nothing is not taken once the minimum is met. `java.util.regex`, which runs the translated pattern, differs on each point, and the library refused most patterns in which the difference could show (a backreference to a group that an iteration can skip, or to a group of a repetition whose body can match the empty string, or of a lookahead that may not have matched). Three faults were found in what it did run. A repeated group whose body has one way to match, such as `(?:x(.)){1,2}`, is run by `java.util.regex` as a unit, and when it gives back an iteration the groups inside keep the text of the iteration given back. So `{"pattern": "^(?:x(.)){1,2}\\1"}` was not valid for `"xxxb"`, where it is. A count of one, as in `(a(){1})?\2a`, was run the same way, and that pattern did not take `"a"`. And `java.util.regex` does not restore the groups of a lookahead when the match fails after it and goes back, so `^(?:(?=([ab]))[ab](?:c|ca)\1)*$` took `"acab"`, which it does not match. Compiled code and the interpreter were both affected, and so was a pattern used for `patternProperties` or `propertyNames`. A pattern with a backreference that `java.util.regex` would read differently is now written once for each way through the choices that decide what the groups it reads hold (an alternative, an optional part, how many times a repetition runs), so that each backreference stands where its group is known to be set, or known not to be. The iteration of a repetition that runs last is written apart from the others, and where it is past the minimum it must take a character. Of the 6,838 patterns of the `empty-loops` family of [ecma262-regex-test-data](https://github.com/corvus-dotnet/ecma262-regex-test-data), 341 were refused and none is now, and every answer is V8's. A pattern that would be written with more than 256 alternatives or 1,048,576 characters is refused, with a message that says so.

- **A group of a lookahead that only some of its ways set.** A lookahead takes the first way its body matches, in the order ECMA-262 tries them, and the match never goes back into it. So after `(?=(a)?b)` the group holds "a" before "ab" and nothing before "b". The library refused a pattern that reads such a group after the lookahead, unless the ways were alternatives of the whole lookahead. It also answered one kind wrongly: `java.util.regex` takes an iteration that matches the empty string and leaves the repetition, where ECMA-262 goes on to the other ways of the body, so the two find the first match of a lookahead in a different order. `{"pattern": "^(?=((?:c??)?))\\1$"}` was not valid for `"c"`, where it is. Such a lookahead is now written by ways: each choice in it that decides what the groups read after it hold is written after a test that the ways ECMA-262 tries first fail, where the test holds such a way followed by all that remains of the lookahead. No pattern is refused for this reason.

- **A group of a lookaround, read in the same iteration of a repetition.** `java.util.regex` does not restore the groups of a lookaround when the match fails after it and goes back. In a repetition, the lookaround of a later iteration sets the group, the match goes back into the earlier iteration, and a backreference there reads the text of the later iteration. The library refused such a pattern where it saw a place to go back to between the lookaround and the backreference, as in `^(?:(?=([ab]))[ab](?:c|ca)\1)*$`, and it missed some: `{"pattern": "^(?:(?=([ab]))[ab](?:c\\1|ca\\1))*$"}` was valid for `"acab"`, where it is not, and so were patterns with the backreference in a lazy repetition (`^(?:(?=([ab]+?))(?:\1.)*?b)+$` did not take `"bab"`) or in a case-insensitive group (`(?i:^(?:(?=(a|))c\1)*$)` took `"ca"`). A backreference that the match can reach that way is now written after another run of the lookaround, at the place it stood at, which is found from the text matched since or from the start of the iteration. No pattern is known that is refused for this reason.

- **A backreference in a lookbehind, or to a group of one.** ECMA-262 matches a lookbehind backwards, from its last term to its first. So a backreference in it reads a group that stands after it, as in `(?<=\1(a))b`, which holds after "aa", and a group of a repetition in it holds the leftmost iteration, as in `(?<=([abc])+)x\1`. `java.util.regex` matches a lookbehind forwards, and the library refused every pattern with a backreference inside a lookbehind or to a group inside one. It now writes the lookbehinds for which the captures of the backward run can be told while matching forwards: a backreference to an outer group; groups and backreferences at a fixed distance from the end of the lookbehind; alternatives, which are tried in order either way; and a repetition of a body of fixed length that stands first, which runs as often as it can when greedy and its minimum when lazy. Any other lookbehind whose groups are read, such as `(?<=(x*?)a*)\1` or `(?<=\1a*(b))x`, is still refused, with a message that says so. This is the one exception to the rule that a pattern that is valid with the `u` flag is run with its ECMA-262 meaning. The other reasons to refuse one are limits of size. Three such patterns were refused with "a pattern java.util.regex does not compile", which named a fault of the translation and not of the pattern: a lookbehind that starts with a repetition whose body holds a counted group with alternatives, as in `(?<=(?:(a|b)(?:x|b){2})+)\1`, was written with a lookbehind whose length `java.util.regex` cannot work out. It is now written with one it can. A translation that `java.util.regex` rejects is no longer a reason to refuse a pattern. It is an `IllegalStateException` that says it is a fault of the library, except where the translation overflows the stack of the compiler of `java.util.regex` (some thousands of groups on a stack of 1 MB), which is refused as "a pattern too large for java.util.regex to compile".

- **A backreference inside a case-insensitive group.** `(?i:\1)` matches text that is the same as the group's under ECMA-262's Canonicalize: simple case folding for a pattern that is valid with the `u` flag, and the uppercase of one UTF-16 code unit otherwise. The case-insensitive backreference of `java.util.regex` compares by the case mappings of the JDK. Measured over every pair of characters that either side equates, with the `u` flag: on every JDK it also equates "i" and "I" with U+0130 and U+0131 (10 ordered pairs), which ECMA-262 does not; on Java 21 it does not equate 60 pairs that ECMA-262 does (characters given a case partner since Unicode 15), and on Java 25 six (U+0390 and U+1FD3, U+03B0 and U+1FE3, U+FB05 and U+FB06); and on Java 17 it throws `StringIndexOutOfBoundsException` for a group that holds a character beyond the Basic Multilingual Plane. So the library used it only where a group could hold no cased character but an ASCII letter, and refused the rest, such as `^(.)(?i:\1)$`. The comparison is now written out for `java.util.regex`, character by character, with the classes of equivalent characters of the library's own Unicode data, so the answer is ECMA-262's and the same on every JDK, for patterns valid with the `u` flag and for those valid only without it. No such pattern is refused for the comparison. The entries below say how long the comparison is, and which part of it the engine now does. A case-insensitive backreference in a lookbehind to a group of more than one character that ends after the place the backreference is tried at, as in `(?i:^(b*)(?<=\1)c$)`, which takes `"bbc"`, looks for its group in the whole text.

- **A pattern that is valid only without the `u` flag matches UTF-16 code units.** A pattern that is not valid with the `u` flag, such as one with the escape `\-` or `\&`, is read without it, and ECMA-262 then matches UTF-16 code units. A character beyond the Basic Multilingual Plane is two of them. The library read such a pattern, and matched the string, by character. So `{"pattern": "^\\-?.$"}` was valid for `"𐐀"` (U+10400), where V8 says the pattern does not match: the dot takes one code unit and two are there. A character beyond the Basic Multilingual Plane written in such a pattern is two atoms, so a quantifier after it repeats its second code unit and a class holds each of the two, and neither was so: `^\-?𐐀*$` matched the empty string, which it does not in V8. A class range from one such character to another, which without the flag runs from a low surrogate down to a high one, is not valid in either grammar, and was accepted. `^\-?[𐐀-\udfff]$`, which is valid, was refused. Such a pattern is now read as code units, and a string with a character beyond the Basic Multilingual Plane is given to `java.util.regex` with each half of a surrogate pair written as a character of its own (a private-use character of plane 15), in a buffer the evaluator keeps. A string without such a character is matched as before, and the translation of a pattern with no surrogate in it is unchanged. A pattern that is valid with the `u` flag matches characters, as before. The escape of a surrogate that is not half of a pair, such as `"\ud800"`, was and is refused by the parser in a schema and in an instance (`JsonParseException`), so no pattern is matched against such a string.

- **A case-insensitive backreference under a count.** The comparison of a case-insensitive backreference is written out for `java.util.regex`, and for a group that can hold any character it had a test for each of the classes of equivalent characters, over 1,400 of them, each written twice with what finds the other character: 136,020 characters for `^(?i:(.)\1)$` and 228,060 for `^(?i:(..\W)\1)$`. A count over such a backreference is written with a copy for each iteration, and two copies were over the limit of 65,536 characters, so `^(?i:(..\W)\1{2})$` and `^(?i:(.)\1{2})$` were refused ("a repetition this long of a body that can match the empty string"). The classes are now numbered and written as two tests, one of the quotient of the number by the square root of the count and one of the remainder, of about 38 sets each: two characters are in one class when a set of each test holds both. The two patterns above are 13,347 and 24,872 characters, and both counts are translated. Translating the 98,839 patterns of the test data took 90 s before and takes 20 s now.

- **A case-insensitive backreference to a group of several characters is compared character by character.** ECMA-262 compares the text of the group with the text at the reference one character at a time, by Canonicalize, which with the `u` flag is simple case folding. V8 13.6 compares the two texts by full case folding instead, so that `/^(..)\1$/iu` matches the four characters U+00DF, "S", "s", U+1E9E, where `/^(.)(.)\1\2$/iu` does not. The test data marks such records as a deviation of V8 (`full-case-folding`). The library follows ECMA-262: `^(?i:(..)\1)$` does not take that text. It did so before for the patterns it translated. One marked record, `^(?<n0>\1|ß)*?(..\W){1,2}\2{2}$` with the `i` flag, was refused for the length of its comparison (the entry above) and is now translated, with the answer ECMA-262 gives. `EcmaRegexTest` has eight such patterns with the answers V8 gives for the same pattern written with a group for each character.

- **A lookbehind over a repetition inside a repetition.** A lookbehind whose length `java.util.regex` cannot bound is written as a search for its start: from each start the body is run forwards, and it must end where the lookbehind stands. The body ran on past that place and came back, and for a repetition inside a repetition it tried every way to split the text after the place before the first way that ended at it. From a start before a character the body cannot take, it tried every way to split the text up to that character. `(?<=(?:[ax]+){2,})$` on a text of 40 letters and a hyphen took over 150 seconds, where V8, which runs a lookbehind backwards, takes microseconds. Each character the body takes now follows a test that the place is not yet the one the lookbehind stands at, and where the characters the body can take are a set of few ranges, the body is tried only at a start from which every character up to that place is in the set. The pattern above takes 0.13 seconds for six such texts, with the start of the JVM. A lookbehind whose groups are read, which is written in other forms, is not changed.

- **A lookahead whose group is read after it, over a counted repetition.** Such a lookahead is written by ways, and every way an iteration could match was written with all the iterations after it. A body that can match the empty string, as in `(?=((?:a|){0,20}?)a)\1a$`, has two ways for each iteration, of which one matches nothing and is not a way ECMA-262 takes once the minimum is met. So the text doubled with each iteration of the count: 597,763 characters for a count of 12, and a count of 13 or more was refused ("a pattern with this many ways through the groups it reads"). A way on which an iteration past the minimum matches nothing is no longer written, and the translation of that pattern is 268 characters for a count of 12, 436 for 20 and 4,216 for 200. A body whose alternatives set groups that are read after the lookahead, as in `^(?=((?:(a)|(b)){0,12}))\1\2\3$`, had a way for every choice of every iteration, and was refused too for a count of 8 or more. An iteration that another iteration follows is now written apart from the ways: the next iteration unsets what it set, so nothing after it reads that. Whether another follows is decided where the iteration is written. That pattern is 8,989 characters. Up to 200 iterations of such a lookahead are written, and more are refused.

- **The ways through a part of a pattern are written as a tree.** A pattern with a backreference that `java.util.regex` would read wrongly is written once for each way through the choices that decide what the groups it reads hold, as alternatives. Ways next to each other often start with the same text: in `^(?:xy(?:(a)|b)\1|z)*$` both ways through the first alternative start with "xy", and a repetition whose last iteration is written apart starts every way with the iterations before it. That text is now written once, and the rest of each way follows as alternatives. One pattern of the test data, a repetition of two around a lookahead with five groups, came to 6,238,952 characters and is now 197,523. A start that sets a group inside a lookaround which the rest reads is not shared, as `java.util.regex` does not undo such a group when it tries the next alternative.

- **A count over a backreference.** A repetition that must run two or more times over a body that can match the empty string in some places only is written with a copy of the body for each iteration, as `java.util.regex` leaves such a repetition after an iteration that matched nothing. A backreference is such a body, and so is a lookahead followed by one. But a body with one way to match where it stands, with no alternatives and no repetition that may run a number of times or another, matches nothing in every iteration after one in which it matched nothing, so leaving the repetition there is what ECMA-262 comes to. Such a body is no longer copied: `^(a*)\1{3}b$` is written with `\1{3}`. With the comparison of a case-insensitive backreference written out, four or five copies were over the limit of 65,536 characters, so `^(?i:(.)\1{5})$` and `^(?i:(..)\1{3})$` were refused ("a repetition this long of a body that can match the empty string"). They are translated now, whatever the count.

- **A case-insensitive backreference is compared by `java.util.regex` where it compares as ECMA-262 does.** The comparison was written out for every character a group could hold, in 13,347 characters for a group of one character that can be any character and 24,872 for a longer group, and each test of it is a search through the text. A pattern that reads such a group in several places, in the tests of a lookahead, came to millions of characters: one pattern of the test data to 16.8 million. The library now asks the engine of the JVM it runs on, once, about every pair of characters that a case mapping of the JDK or a class of ECMA-262 relates. A character is left to the engine when the engine agreed with ECMA-262 on every pair it is in, and the comparison is written out only for the others: "i", "I", U+0130 and U+0131 on every JDK, the pairs that Unicode 15.1 and 16 added on Java 21, six characters on Java 25, and every character beyond the Basic Multilingual Plane on Java 17, whose engine throws `StringIndexOutOfBoundsException` on one. The answers are the same on every JDK. `^(?i:(.)\1)$` is 1,370 characters on Java 25, 2,128 on Java 21 and 5,729 on Java 17, and that pattern of the test data is 4.2 million on Java 21.

- **The limits of size.** A translation could have 256 ways through one part of a pattern, 1,048,576 characters, and 65,536 characters of copies of bodies. The forms above are shorter than they were, and the limits are now 8,192 ways, 1,048,576 characters, as many characters of copies as fit in that, and 16,777,216 characters written on the way (see the new features). Of the 98,839 patterns of the test data, four are over a limit, the same on Java 17, 21 and 25. With the limits as they were, 63 were.

- **A repetition of a body that takes no character, and the empty alternatives of a repetition that can run no times.** `(?:^|$){1000}` is run once, whatever its count: a body that takes no character matches the same however often it is run in one place. `(?:^|$)*`, which can run no times, is not run at all. And `(?:a|)*` is written as `a*`: ECMA-262 does not take an iteration that matched nothing once the minimum is met. `java.util.regex` ran the count, and tried the empty alternative at every place. `^(?:(?:a|)*?x)*?$` read a string of 41 characters nine million times, and now reads it 82 times.

- **A long literal, many lookbehinds, and counts inside counts.** `java.util.regex` took 13 seconds to compile a pattern of 131,072 times "a", and 35 seconds for one of 174,762 lookbehinds. The translation now has an empty group after the first 1,024 characters of a literal it starts with, and a choice that is never taken after every sixteenth lookbehind, and both compile in a fraction of a second. The matcher the library has for a group with an exact count wrote the group out, and `(?:(?:a{2}){2}){2}...` 140 deep took the whole heap. It now stops at 4,096 characters.

- **`\k` in a class, in a pattern with a named group.** In a pattern with a named group ECMA-262 has `\k` only as a reference to one, in the grammar without the `u` flag too. So `(?<n>a)[\k]` is not valid. The library accepted it, with `\k` read as the letter "k". It now throws `SchemaCompilationException`. In a pattern with no named group `[\k]` is still the letter, as Annex B says.

- **The Script value `Katakana_Or_Hiragana`, and the counts of a quantifier out of order.** These are two places where V8 13.6 and ECMA-262 differ on what is a valid pattern, and the library follows ECMA-262. `PropertyValueAliases.txt` has the Script value `Katakana_Or_Hiragana` (`Hrkt`), so ECMA-262 has it, for `Script` and for `Script_Extensions`. No character has it. The library refused `\p{sc=Hrkt}` with the `u` flag, as V8 does, and read it without the flag as the letter "p" and what follows. It is now valid and takes no character, and `\P{sc=Hrkt}` takes every character. And ECMA-262 compares the two counts of a quantifier whatever their size, where the library kept a count only up to 2,147,483,646, so it accepted `a{2147483648,2147483647}`, as V8 does. That is no longer valid. These came from 106,259 patterns built around the property names and the forms of Annex B, given to V8: after these changes the library differs from V8 on 16 of them, which name one of the four scripts that Unicode 17 added and V8 13.6, with Unicode 16, does not have.

These came from testing the library against the [ECMA-262 regular expression test data](https://github.com/corvus-dotnet/ecma262-regex-test-data), which has V8's answers for 98,839 patterns and their texts, in 13 files. Compiled and interpreted on Java 21, and compiled on Java 17 and 25, no answer the library gives differs from V8's (4,176,244 answers or more in each of the four runs), and no pattern that is not valid is accepted. A pattern that is valid only without the `u` flag is asked about every text, those with a character beyond the Basic Multilingual Plane too. The 46,500 texts that hold a surrogate that is not half of a pair are not asked, as no JSON string here can hold one, and the answers of the 62 records the data marks as a deviation of V8 from ECMA-262 are not compared. The library refuses 713 valid patterns of the data, all of them under the exception for a lookbehind whose groups only matching backwards can tell (517 in `lookarounds`, 165 in `engine-faults`, 31 in `case-folding`), and none for size. Ten patterns do not always answer for all their texts within five seconds, where V8 takes milliseconds: they nest repetitions whose bodies can match nothing around groups that are read, and are written with their iterations apart and tried every way. Run alone on Java 21, each gives V8's answers, nine of them in 2 to 62 seconds for all their texts and one in 290 seconds. The library sets no time limit on a match, and the README lists the ten. The translation of a pattern that needs none of the above is unchanged, character for character: every pattern of the JSON-Schema-Test-Suite and of the schemas of jsonschema-benchmark. Translating the 98,839 patterns of the test data takes 7 s, and their translations come to 32.9 million characters. Before the last seven entries above it took 16 s and they came to 66.0 million.

The library was also run against 215,803 generated patterns of the forms above (repetitions whose bodies can match nothing, lookbehinds, case-insensitive backreferences, lookaround groups that are read, patterns valid only without the `u` flag on texts beyond the Basic Multilingual Plane, counted repetitions in lookaheads whose groups are read, and counts over case-insensitive backreferences), with V8's answers for 48,971,620 texts. Its answer differs from V8's for 1,289 of them, in 136 patterns, and each is one of the three deviations of V8 that the test data names: a match that starts between the two halves of a surrogate pair (690), a backreference compared by full case folding (9), and a case-insensitive modifier group answered differently from the `i` flag (590). It refuses 10,290 of the patterns: 10,286 under the exception for a lookbehind whose groups only matching backwards can tell, and 4 for size, each a lookahead with two or more repetitions whose groups are read, inside a repetition. Before the last seven entries above it refused 5,409 of them for size.

## V0.1.2

V0.1.2 fixes a `StackOverflowError`, and a wrong `isValid` result, for a schema whose `not` is part of a loop, and stops the interpreter allocating when it validates. There are no API changes. `isValid` changes for one more kind of schema, described below. Versions 0.1.0 and 0.1.1 are affected.

### Bug fixes

- **A `not` that leads back to the schema it is in.** A schema can loop without consuming the instance. The library abandons such an evaluation at `maxDepth` (128 by default) and throws `SchemaEvaluationDepthException`. Evaluating `not` went around that guard. For a schema such as `{"not": {"$ref": "#"}}`, validating an instance that reached the `not` recursed until the thread's stack was full, and `isValid`, `validate` and `evaluate` threw `StackOverflowError`. A `not` is now under the guard, so `validate` and `evaluate` throw `SchemaEvaluationDepthException` and `isValid` returns false. The fault is in the schema. No instance causes it for a schema without such a loop, so a program was exposed only if it compiled schemas it did not write.

- **`isValid` for a schema that loops under a `not`.** With the loop elsewhere, as in `{"$defs": {"loop": {"allOf": [{"$ref": "#/$defs/loop"}]}}, "not": {"$ref": "#/$defs/loop"}}`, the guard stopped the loop and counted the abandoned branch as false, and the `not` turned that into true. `isValid` returned true for an evaluation that had been abandoned, where its documentation says false. `validate` and `evaluate` threw `SchemaEvaluationDepthException` for such a schema, and still do.

- **`isValid` is false whenever the evaluation went beyond the maximum depth.** This is the rule that corrects the result above, and it also changes `isValid` for a schema whose `anyOf` recovers after the depth is exceeded. In `{"$defs": {"a": {"anyOf": [{"$ref": "#/$defs/a"}, true]}}, "$ref": "#/$defs/a"}` the first branch loops and is abandoned, and the second branch is true. `isValid` returned true for it and now returns false, as its documentation says. `validate` throws `SchemaEvaluationDepthException` for this schema, as it did before. Such a schema goes beyond any `maxDepth`, so code that relied on true here has to take the loop out of the schema.

- **The interpreter allocated on every validation.** The library validates with generated bytecode by default, and that path allocated nothing. With the interpreter chosen for validation (`-Dcorvus.jsonschema.interpret=true`), each instance cost between 36 and 350 bytes. Two things allocated. Thirteen keyword checks created the function that builds a result's message, whether or not a collector would ever ask for it. And `required`, with the required names of a dependency, looked each name up in the instance by its `String`, which encoded it to UTF-8 on every lookup. The checks now create that function only when results are collected, and the names are kept as UTF-8 beside the strings. The interpreter now allocates nothing on the validation path, on Java 17, 21 and 25. The project's CI ran only the conformance suite through the interpreter. It now runs the allocation test and the API tests through it too.

## V0.1.1

Regular expressions that follow ECMA-262 where 0.1.0 followed `java.util.regex`.

### Bug fixes

- **Every Unicode property of ECMA-262, with the same data on every JDK.** `\p{...}` now covers all 53 binary properties and their aliases. 0.1.0 knew about 20, and a pattern with any other, such as `\p{Dash}`, was read as the literal text `p{Dash}`. `\p{Emoji}`, `\p{Emoji_Presentation}` and `\p{Extended_Pictographic}` had that fault on Java 17, whose `java.util.regex` lacks them. `\p{Script_Extensions=...}` (`scx`) is now its own property and no longer Script, and `\p{White_Space}` is the Unicode property, where 0.1.0 used the set of `\s` (which has U+FEFF and lacks U+0085). The data for General_Category, Script, Script_Extensions and the binary properties is Unicode 17, carried by the library, so a pattern no longer means something different on Java 17, 21 and 25.

- **ECMAScript 2025 pattern syntax.** Modifier groups (`(?i:...)`, `(?m:...)`, `(?s:...)`, `(?i-s:...)`), a group name shared by groups in separate alternatives, and `\u` escapes in group names are now valid, as they are in V8. Case-insensitive matching is the Canonicalize of ECMA-262 (Unicode simple case folding with the `u` flag grammar), `^` and `$` in a multiline group see ECMA-262's four line terminators, and `\w` and `\b` in a case-insensitive group count U+017F and U+212A.

- **Lookbehind of any length, counted in characters.** A lookbehind whose length `java.util.regex` cannot bound, such as `(?<=(?:ab)+)x`, was an error, and one with two unbounded repetitions, such as `(?<=(\d+)(\d+))$`, compiled and never matched. Both now match as ECMA-262 says. A lookbehind before a character beyond the Basic Multilingual Plane counted UTF-16 code units, so `(?<=^.{2})a` missed a string that starts with an emoji. It now counts characters.

- **Backreferences that mean what ECMA-262 says, or an error.** A backreference to a group with alternatives, such as `^(a|b|c)+?\1$`, tested the wrong thing and matched strings it should not. A backreference could also read what a group captured in an earlier iteration of a repetition (`^(?:(a)|b)*\1$`) or in a negative lookahead (`(?!(a))\1b`), which ECMA-262 unsets. These are fixed. A few valid patterns have a backreference that `java.util.regex` cannot give the ECMA-262 meaning (one inside a lookbehind, or to a group inside one; one to a group of a lookaround that may not have matched; one to a group that the repetition holding both can skip, or of a repetition that can match the empty string; a case-insensitive one, unless the only cased characters its group can hold are ASCII letters, without `k` and `s` under the `u` flag grammar). Compiling a schema with one now throws `SchemaCompilationException` with a message that starts "Unsupported regular expression" and names the construct. 0.1.0 ran some of them with another meaning.

- **Smaller corrections.** Leading zeros in a `\u{...}` escape (`\u{0000000061}`) are read. Group names are checked against ID_Start and ID_Continue of Unicode 17, and script names against the scripts of Unicode 17, on every JDK. Groups nested more than 200 deep make a pattern invalid, where 0.1.0 overflowed the stack, in a schema and in a string checked with the `regex` format.

## V0.1.0

The first release of the Java port of `Corvus.Text.Json.RuntimeEvaluator`.

### New features

- **A JSON Schema evaluator for Java and Kotlin.** It covers draft 4, 6, 7, 2019-09 and 2020-12 and passes all 7,966 tests of the JSON-Schema-Test-Suite, with the same single exclusion as the C# runner. It runs on Java 17 or later, is one jar with no dependencies, and can be used from Kotlin as it is.

- **Compiled to JVM bytecode.** A schema is compiled once into a hidden class, one method per schema node holding only the checks that node needs, which the JIT then optimises as it would hand-written code. Property names are dispatched by length and 64-bit words, common pattern shapes are matched without a regular expression engine, and `unevaluatedProperties` is decided from the coverage known at compile time where it can be.

- **Allocation-free validation.** Validating a parsed `JsonDocument`, or JSON text through the validator's reused per-thread buffers, allocates nothing in the steady state.

- **Results and annotations.** Evaluation with a results collector at the Basic, Detailed or Verbose level gives the same rows as the C# `JsonSchemaResultsCollector`, and annotations as `JsonSchemaAnnotationProducer` extracts them.
