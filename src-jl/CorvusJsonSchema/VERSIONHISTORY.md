# Version History

The version history of `CorvusJsonSchema`, the Julia port of the Corvus.Text.Json V5 runtime evaluator. It is versioned independently of the Corvus NuGet packages, whose history is in the repository's [VERSIONHISTORY.md](../../VERSIONHISTORY.md).

## V0.1.0

The first release of the Julia port of `Corvus.Text.Json.RuntimeEvaluator`.

### New features

- **A JSON Schema evaluator for Julia.** It covers draft 4, 6, 7, 2019-09 and 2020-12 and passes all 7,966 tests of the JSON-Schema-Test-Suite, with the same single exclusion as the C# runner. It needs Julia 1.10 or later and has no dependencies.

- **Compiled to fail-fast plans.** A schema is compiled once into a node graph and plans that hold only the checks each subschema needs. An object is checked in one pass over its properties, with the keywords of `$ref`, `allOf`, `if`/`then`/`else`, dependencies and `oneOf`/`anyOf` branches fused into it. Property names are looked up by length and 64-bit words, common pattern shapes are matched without a regular expression engine, and `unevaluatedProperties` is decided from the coverage known at compile time where it can be.

- **Ready when loaded.** One interpreter runs the plans, and a precompile workload puts it in the package image. Nothing is generated or compiled when a schema is compiled, so the first validation in a process does not wait for Julia's compiler.

- **ECMA-262 patterns.** `pattern` and `patternProperties` have ECMA-262 semantics, through a translator in the package that writes each pattern for the PCRE2 that Julia bundles. A backreference to a group that has not taken part matches the empty string, the groups of a repeated body are unset when an iteration starts, and an iteration that matches the empty string is refused once the minimum count is met, as ECMA-262 specifies and PCRE2 does not do by itself. A lookbehind captures what ECMA-262 captures matching it backwards, where that can be written for PCRE2, and a case-insensitive backreference is run in every pattern that is valid with the `u` flag. A pattern that cannot be written with exactly the same meaning is refused when the schema is compiled, with a `CompileError` that names the construct: some backreferences to or inside a lookbehind of no fixed length, and a case-insensitive backreference in a pattern that is only valid without the `u` flag. The README lists them, and names the one exception to a pattern that is valid with the `u` flag never being refused: a lookbehind of no fixed length whose groups are read in a way that only matching it backwards can tell. A pattern that is valid only without the `u` flag matches UTF-16 code units, as ECMA-262 says, so `^\-?.$` does not match one character beyond the Basic Multilingual Plane. A lookbehind of no fixed length is searched for from the place it stands at backwards, with its body held to that place. A case-insensitive backreference is compared one character at a time, which is ECMA-262's Canonicalize and not the full case folding V8 13.6 applies with the `i` and `u` flags. A match that reaches a PCRE2 limit throws and is never reported as no match. What is a pattern is what ECMA-262 says: `\k` in a class is an error in a pattern with a named group, a count whose first number is the greater is an error however large the numbers (`a{2147483648,2147483647}`, which V8 13.6 takes), and the Script value `Katakana_Or_Hiragana` (`Hrkt`), which no character has and V8 13.6 does not know, is a name. A count of one character or class is run whatever the count, so `a{1000000000}` and `^\p{L}{1,300000}$` are patterns like another. A match has 500 million steps of PCRE2, where PCRE2 by itself gives ten million, which three patterns of the [ECMA-262 regular expression test data](https://github.com/corvus-dotnet/ecma262-regex-test-data) pass that V8 answers. A match that reaches the limit, or the limit on its memory, throws a `MatchError` that names the limit. A match of a pattern that is valid only without the `u` flag against a string with a character beyond the Basic Multilingual Plane allocates nothing in the steady state.

- **Limits on patterns.** A schema and an instance may both come from outside, so one match of a `pattern` or `patternProperties` regular expression is limited to one second (`pattern_match_limit`, in seconds, and `nothing` for no limit), and a pattern has limits of size (1,048,576 bytes, groups 200 deep, 131,072 terms, a translation of 1,048,576 bytes written in 524,288 steps, and what PCRE2 holds, which is 64 KiB compiled). A match that reaches its limit throws a `PatternMatchError` whose `limit` is `:time`, `:memory` or `:steps`, and a pattern over a limit of size is a `PatternTooLargeError` when the schema is compiled, which is not the error of a pattern that is not valid. Neither is ever an answer. PCRE2 has no clock and its count of steps does not bound time, so a match that uses a first allowance of steps is run again by code that reads a clock. `^\p{L}+$` answers on a string of a million letters, where it reached the memory limit on 150,000. A repetition of what can match the empty string inside another is written once at each level and not twice, and a long literal pattern compiles in time proportional to its length. The README says what the limits cost and what they do not bound.

- **Formats in time proportional to the string.** The checks of `format` read a string of the instance, and none is a regular expression. Two took time in proportion to the square of the length of the string. An internationalized host name (`idn-hostname`, and the host of an `idn-email`) was decoded and encoded label by label whatever its length: a string of 1,000,000 characters took from 10 seconds to more than a minute. It is at most 1,012 bytes now (253 characters of four bytes, which is the longest there can be), and a longer string is answered from its length. The `regex` format looked for each group name among all those before it, and kept the alternatives around each: 125,000 groups of one name took more than a minute. It puts the names in order now and compares each with the one before it, and keeps three numbers for a name. The slowest check of a hostile string of 1,000,000 characters takes 121 ms. The README lists how each format is bounded.

- **The same results with every Julia release.** The package reads Unicode properties and case mappings from its own Unicode 17 tables and never from Julia or its PCRE2, whose Unicode versions differ between Julia releases. Patterns and the `hostname`, `idn-hostname` and `idn-email` formats give the same answers with Julia 1.10 and 1.13. The one exception is a case-insensitive backreference such as `(.)(?i:\1)`, which PCRE2 compares: with Julia 1.10 (PCRE2 10.42, Unicode 14) it does not hold equivalent the thirty pairs of characters that Unicode 15.1 and 16 made equivalent. The README lists the pairs. The fix is to update to Julia 1.13, where the answers are those of V8. Of the thirteen files of the test data, Julia 1.10 differs from V8 on 1,026 answers in twenty patterns, each on a text of one of those pairs.

- **Allocation-free validation.** Validating a parsed `Document`, or JSON text through the validator's reused buffers, allocates nothing in the steady state.

- **Results and annotations.** Evaluation with a results collector at the Basic, Detailed or Verbose level gives the same rows as the C# `JsonSchemaResultsCollector`, and annotations as `JsonSchemaAnnotationProducer` extracts them.
