# Version History

The version history of `corvus-json-schema` for Object Pascal (`src-pas/corvus-json-schema`), the Object Pascal port of the Corvus.Text.Json V5 runtime evaluator. It is versioned independently of the Corvus NuGet packages, whose history is in the repository's [VERSIONHISTORY.md](../../VERSIONHISTORY.md).

## V0.1.1

V0.1.1 fixes wrong results for two kinds of pattern, and patterns that took the engine longer than anyone would wait. It also refuses patterns that are not valid and were accepted. And it bounds what a pattern can cost: one match of a pattern is limited to a second by default, and a pattern has limits of size. Both add to the API (an option and two exceptions) and change what a program sees for a pattern that reaches one. Version 0.1.0 is affected.

### Limits

A schema and an instance may both come from outside. Neither is to make a validation run without end, hold memory out of proportion to what it was given, or take long to compile. The README has the whole of this under [Limits](README.md#limits).

- **One match of a pattern is limited to a second by default.** Until now a match on the backtracking matcher had no bound on its time or on its memory. A pattern of a few characters never answered (`^(?:(a+)\1*)+$` on thirty `a` and a `b`, `(a*)*b` after one `é`), and `(?:a?){2147483647}` on the empty string took 2 GB and raised `EOutOfMemory`. Now the matcher counts its steps and reads a monotonic clock every 4,096 of them, and with a limit the backtracking of a match holds 1,048,576 entries (16 MB) at most. A match that reaches either is abandoned and the validation raises the new `EJsonSchemaPatternMatchLimit`, which has the `Pattern`, the `Limit` in milliseconds and `Memory`. `IsValid` and `Evaluate` raise it, `TryIsValid` and `TryEvaluate` return `False` with its message, and the compile functions raise it when the match was of a `patternProperties` pattern against a property name the schema declares. A limit is never reported as an instance that is not valid. The new `WithPatternMatchLimit` sets the limit in milliseconds (`DefaultPatternMatchLimit` is 1000), and `NoPatternMatchLimit` turns it off, which restores a match with no bound. The limit is for each match and not for a validation. Validation still allocates nothing in the steady state with the limit on.

- **A pattern has limits of size.** Until now nothing bounded a pattern but the depth of its groups, and an alternation of a million characters compiled to 238 MB. A pattern may now be 1,048,576 bytes long, nest its groups 1,000 deep, and have a size of 1,048,576 bytes as the parser counts it: 64 bytes for each term, 32 for each further alternative, 8 for each range of a class and of what case folding or a negated property builds, and so on, so that 16,384 literal characters are at the limit. Compiling a schema with a pattern over a limit raises the new `EJsonSchemaPatternTooLarge`, which has the `Pattern`, the `Keyword`, the name of the `Limit` and its `Value`. It is not `EJsonSchemaCompileError`: the pattern is not read past the limit, so nothing is known of whether it is valid. Groups nested more than 1,000 deep were `EJsonSchemaCompileError` and are now `EJsonSchemaPatternTooLarge`. The largest pattern of each of 25 kinds that the limits admit compiled in 1 to 252 ms and kept 2.2 MB at most. The `regex` format has the same limits, and a string over one is not a valid regular expression to it. The limits and the size are the Go module's, and the tests hold the two to the same size for 122 patterns.

- **A long string is not an internationalized host name.** The checks of the `format` keyword read strings of the instance, and none is under the limit of a match. The check of `idn-hostname`, which is also the check of the domain of an `idn-email`, decodes and encodes Punycode, looks for a kana for every katakana middle dot and walks the neighbours of every joiner. Each of those takes time that grows with the square of a label, and the check did them for a label of any length: a host name of 100,000 different letters took 10 seconds to refuse, one of 100,000 katakana middle dots after a kana took 8, and at a million characters neither answered in a minute. An internationalized host name has 253 characters at most, so a string over 1,012 bytes is now refused without being read. No answer changes. Every other format was measured on 248 strings of 100,000 and of 1,000,000 characters made to be slow, and takes time proportional to the string: the slowest of them took 77 ms for a million characters.

- **Many group names are read in time proportional to their number.** The parser of the pattern engine looked for a group name by going through every name it had, for each named group and for each reference to one. The limits of size admit 8,191 named groups, and a pattern of 8,000 groups with names of 40 characters took 1.4 to 2 seconds to compile, on a machine under load. So did the `regex` format for a string of the instance with that text, where no limit of a match applies. The names are now found through a hash table, and the same pattern takes 40 to 60 ms. No answer changes.

### Bug fixes

- **A pattern that could not match the text it was given was tried all the same.** `(?:a{1000}){1000}` needs a million characters. On a string of 100,000 the matcher ran its loops to the end of the string from every position of it, and neither it nor `(?:a|b){2147483647}c` answered in 20 seconds. The need of a counted repetition now counts the iterations it has still to make, each at the least its body consumes, and a search stops at the first position from which the pattern cannot fit. Both answer at once. No answer changes.

- **Patterns that took time that doubled with each character now answer.** The matcher looks at the next character of the string before it takes a way, and takes no way that character rules out, as V8 does. And it remembers the places where every way has failed, for a pattern with no backreference, so it goes through no place twice. `(a*)*b` after one `é`, `^(?:é+)+$` on forty of them, `^(?=.)(?:a|aa)+$` and `(?i:\b(?:\w+\W?)+\b!)` on sixty characters met the limit of a match, or had no answer before there was one, and now answer at once. The memory is 8 MB at the most and the thread keeps it, so the steady state still requests no memory. Of the 125 worst cases that were built to try the limits, 34 gave no answer in 20 seconds before this version. Now 97 answer, 26 end at the limit of a match within 1.02 seconds, and 2 are refused for size. No answer changes.

- **A long literal pattern took time that grew with the square of its length.** The matcher that multiplies out the alternatives of a pattern copied the pattern a character at a time. A literal pattern of 16,000 characters took 126 ms to compile and one of 128,000 took 6.6 seconds. They now take 4 ms and 55 ms.

- **Three matchers took time that grew with the square of the string.** The matchers that are not the pattern engine have no limit, so each must read the string a bounded number of times. In a pattern of alternatives, a sequence of classes that is not anchored is tried at every position and reads its width at each: `[a-z]{50000}[0-9]|x` took 5.2 seconds on 100,000 characters. A literal that is not anchored was searched for the same way. And the final sequence of a list such as `^(?:[a-z]+,)*[a-z,]+[0-9]$` is tried after every item, and one that can read through the separators read to the end of the string each time: 8.6 seconds for 33,333 items. A sequence or a literal wider than 64 that is tried at every position, and a list whose final sequence does not stop at the next separator, are now matched by the pattern engine, which has the limit. A list also worked out whether the string is ASCII once for every item, which it now does once. No answer changes.

- **A property escape built its set every time a pattern named it.** `\p{L}` written 16,000 times held 16,000 sets of 684 ranges and took 675 ms to compile. A pattern now builds the set of a property expression once.

- **A pattern that is valid only without the `u` flag, on a string with a character beyond the Basic Multilingual Plane.** The package reads a pattern with the grammar of the ECMA-262 `u` flag, and with the grammar of a pattern with no flag when the first refuses it, as `\-` outside a class or `\_` make it do. ECMA-262 matches a pattern with no `u` flag by UTF-16 code unit, and the package matched it by code point. A character beyond the Basic Multilingual Plane is two code units, so `{"pattern": "^\\-?.$"}` was valid for `"\ud801\udc00"` (the one character U+10400), where it is not, and `{"pattern": "^\\-?[^a]{2}$"}` was not valid for it, where it is. The same went for a class, a quantifier, a group, a backreference, a lookbehind and a case-insensitive group, and for the patterns of these shapes that the package matches without the pattern engine. Such a character written in the pattern is two atoms, and was read as one: `^\-?\ud801\udc00?x$` requires the high surrogate and makes the low one optional, and was taken to match `"x"`. A class range between two such characters, as in `^\-?[\ud801\udc00-\ud801\udc28]$`, runs from a low surrogate down to a high one. It is an error in both grammars and was accepted, and `^\-?[\ud801\udc00-\udfff]$`, which is valid, was refused. Such a pattern is now matched by code unit, and the engine reads the code units from the UTF-8 text without making a copy of it. A pattern that is valid with the `u` flag was never affected, nor was a string within the Basic Multilingual Plane.

- **A repetition whose body cannot consume a character.** A pattern such as `(?:((?=x)|()|){4,5}?){4}?$` repeats a body that can match only the empty string. ECMA-262 lets the iterations up to the minimum be empty and refuses an empty one after it, so the repetition is the body the minimum number of times. The backtracking matcher ran it as written, and so tried every combination of the alternatives of every iteration: up to 3 to the power of 16 for that pattern, at every position of the string. The schema compiled and the first match did not return, in any time worth waiting. The matcher now runs such a body once when the minimum is one or more, and not at all when it is zero. What the body's groups hold afterwards is unchanged, since each iteration starts with them cleared and at the same position, so only the last iteration decides. A backreference inside the group it names, as in `(a\1)`, is now read as the empty string, which is what it always matched, so that a body made of such references is seen to consume nothing. V8 makes both rewrites. Of the patterns of the ECMA-262 regular expression test data, which V8 answers within 250,000 backtracks each, 23 did not finish in 5 seconds, and 21 of those now do.

- **A counted repetition before a rest of the pattern that cannot fit.** `(?:\1|[^a]|$(?:a?|(?<!^)){4}?){4,6}?(\b|a)+?a$` repeats a body that can be empty in 17 ways at the end of the string, and what follows the repetition needs one more character. The matcher tried every combination of those ways, 17 to the power of 4, before it found that out each time. It now works out, for every counted repetition, the least number of bytes that the rest of the pattern consumes, and gives up at the repetition when fewer are left. V8 does the same at every choice. The two patterns of the test data that still did not finish in 5 seconds took 8 and 11 seconds for their texts, and now take 4 and 135 milliseconds. No answer changes.

- **`\k` in a class, in a pattern with a named group.** Without the `u` flag `\k` is the letter `k`, but only in a pattern with no named group. In a pattern that has one, `\k` must be a reference such as `\k<n>`, and in a class it cannot be one, so `(?<n>a)[\k]` is an error. The package read the `\k` of the class as the letter `k` and accepted the pattern. Compiling such a schema now raises `EJsonSchemaCompileError`. `[\k]` with no named group in the pattern is the letter `k`, as before.

- **A quantifier whose first count is the greater, with counts beyond 2,147,483,647.** `a{3,2}` is an error, and so is any quantifier whose first count is greater than its second, whatever the size of the numbers. The package kept a count as a number that stops at 2,147,483,647, so the two counts of `a{2147483648,2147483647}` looked equal and the pattern was accepted, as it was for any two counts at or beyond that number. The counts are now compared as the numbers written, and compiling such a schema raises `EJsonSchemaCompileError`. V8 13.6 accepts these patterns, for the reason the package did, so here the package follows ECMA-262 and not V8. A count beyond 2,147,483,647 is still valid and still means more characters than a string can have.

- **The Script value `Katakana_Or_Hiragana`.** ECMA-262 takes the values of `Script` and `Script_Extensions` from the Unicode file `PropertyValueAliases.txt`, which lists `Katakana_Or_Hiragana` and its alias `Hrkt`. No character has that value, in either property. The package did not know it, so `\p{sc=Hrkt}` was refused by the grammar of the `u` flag and read with no flag, as the characters `p{sc=Hrkt}`. `{"pattern": "^\\P{Script=Hrkt}$"}` was then not valid for `"a"`, where it is. `\p{sc=Hrkt}`, `\p{Script=Katakana_Or_Hiragana}` and the same with `scx` or `Script_Extensions` are now valid with the `u` flag and match no character, and with `\P` they match any character. V8 13.6 refuses the value, so here the package follows ECMA-262 and not V8.

- **Where V8 departs from ECMA-262.** The package follows ECMA-262 there. Besides the two entries above, V8 13.6 takes `\p{WSpace}`, which is not a name ECMA-262 lists, and takes some patterns with one name on two groups that can both take part in a match, such as `(?<m>a)(?:x|(?<m>b))`. The package already read the first with no flag, as the characters `p{WSpace}`, and refused the second. Both are now tested, with 28 patterns for the names.

- **The ECMA-262 regular expression test data.** The engine now agrees with V8 on every pattern and every text of the 13 files that a document can hold: 98,839 patterns and 4,268,313 answers, with no pattern left unanswered. None of them reaches the limit of a match or a limit of size. The texts it cannot hold are the 31 of `lone-surrogates.jsonl` with half of a surrogate pair, which the parser refuses. The answers of the 62 records where V8 is known to depart from ECMA-262 are not compared.

- **A separated list with a `$` inside it.** The package matches a pattern of the form `^item(separator item)*$`, such as `^([a-z]+)(\.[a-z]+)*$`, without the pattern engine (and likewise the forms with `+`, and `^(item separator)*item$`). It read the first item and the repeated group as sequences of characters and classes, and a `$` at the end of either was read and then dropped. So `^x(,a$)*$` was matched as `^x(,a)*$`. A `$` holds only at the end of the string, so the group of `^x(,a$)*$` can match once at most, and only as the last thing in the string. `{"pattern": "^x(,a$)*$"}` was valid for `"x,a,a"`, where it is not. `^x$(,a)*$` was valid for `"x,a"`, and `^(a,$)*b$` for `"a,b"`. A pattern used for `patternProperties` or `propertyNames` was affected in the same way. A list with a `$` at the end of its first item or of its group is now matched by the pattern engine. An escaped `\$` is a literal character and such a list is matched as before. No other form of pattern was affected. A table of 101 patterns with an anchor, a word boundary or a lookaround inside one of the forms the package matches by itself, with answers from V8, is now part of the tests.

## V0.1.0

The first release of the Object Pascal port of `Corvus.Text.Json.RuntimeEvaluator`.

### New features

- **A JSON Schema evaluator for Object Pascal.** It covers draft 4, 6, 7, 2019-09 and 2020-12 and passes all 7,966 tests of the JSON-Schema-Test-Suite, with the same single exclusion as the C# runner. It is a native port of the Go module and has no dependencies beyond the compiler's run-time library. Free Pascal 3.2.2 or later is the compiler it is built and tested with. The source is in the Delphi dialect and is written to be Delphi-compatible, but it has not been compiled with Delphi.

- **Compiled to fail-fast plans.** A schema is compiled once into a node graph and plans that hold only the checks each subschema needs. An object is checked in one pass over its properties, with the keywords of `$ref`, `allOf`, `if`/`then`/`else`, dependencies and `oneOf`/`anyOf` branches fused into it. Property names are looked up by length and 64-bit words, common pattern shapes are matched without a regular expression engine, and `unevaluatedProperties` is decided from the coverage known at compile time where it can be.

- **ECMA-262 patterns.** `pattern` and `patternProperties` have ECMA-262 semantics, through an engine in the package that agrees with V8 on 61,383 patterns and 1,057,650 match answers. A pattern runs on an automaton over ASCII text where it allows one, and on a backtracking matcher otherwise. The backtracking matcher has no step budget, so a pattern with nested quantifiers can take exponential time on a text it does not match.

- **The same results whichever compiler builds it.** The package reads Unicode properties and case mappings from its own Unicode 17 tables and never from the compiler's run-time library.

- **Every array read is range checked.** Range checking is on in every unit. On the paths every validation takes the check is one inline comparison, written out in accessor functions that raise `ERangeError` as the compiler's check does.

- **Allocation-free validation.** Validating a parsed `TJsonDocument`, or JSON text through the thread's reused buffers, allocates nothing in the steady state. A thread that has validated should call `JsonSchemaReleaseThreadScratch` before it ends.

- **Results and annotations.** Evaluation with a results collector at the Basic, Detailed or Verbose level gives the same rows as the C# `JsonSchemaResultsCollector`, and annotations as `JsonSchemaAnnotationProducer` extracts them. The rows are the same, byte for byte, as the Go module's for every case of the JSON-Schema-Test-Suite.
