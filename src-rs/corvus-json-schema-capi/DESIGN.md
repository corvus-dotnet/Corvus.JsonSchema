# corvus-json-schema C ABI: design

A C library over the `corvus-json-schema` crate, with a header-only C++ wrapper on top. It is the base for the C/C++
and Swift bindings; Ruby and PHP bind the crate directly from Rust (see "Other languages" below).

**The gate.** The C/C++ library must be faster than Blaze on the jsonschema-benchmark corpora, or it is not worth
doing. The crate meets it today: in the benchmark's harness, pinned, it parses and validates faster than Blaze on all
37 corpora (geometric mean 0.37 of Blaze's time), and validates already-parsed instances faster on 34 (0.54). The C
library adds a function call per operation, so it is measured again in the same harness (see "Testing").

## Layout

`src-rs/corvus-json-schema-capi`, a crate of its own (`corvus-json-schema-capi`, not published to crates.io):

- `src/`: the `extern "C"` functions over `corvus-json-schema` (path dependency, as the Python binding has).
- `include/corvus_json_schema.h`: the C header, generated by cbindgen and committed (CI checks it is current).
- `include/corvus_json_schema.hpp`: the C++ wrapper, header-only, written by hand.
- `tests/`: Rust tests through the C functions, and C and C++ tests built with CMake.
- `cmake/` and a `corvus-json-schema.pc.in`: the CMake package configuration and pkg-config file shipped with the
  libraries.

The library is `corvus_json_schema` (`libcorvus_json_schema.so`/`.dylib`, `corvus_json_schema.dll` with its import
library, and a static library for each), built as `cdylib` and `staticlib`.

## Conventions

- **Prefix.** Every symbol starts `cjs_`; types are `cjs_validator`, `cjs_options` and so on; constants `CJS_`.
- **C99, opaque handles.** Every object is an opaque pointer created and freed by the library (`cjs_validator_free`
  and so on, each taking NULL). The only structs in the header are `cjs_str` (a pointer and a length) and the enums,
  so the library can change any object without breaking the ABI.
- **Strings in** are UTF-8 as `(const char *ptr, size_t len)`, not NUL-terminated (`len` 0 with a NULL `ptr` is the
  empty string). The library checks UTF-8 and reports `CJS_INVALID_UTF8`.
- **Strings out** are `cjs_str` views into memory the library owns, valid until the owning object is changed or
  freed (each function says which). They are not NUL-terminated: `printf("%.*s", (int)s.len, s.ptr)`.
- **Errors.** Every fallible function returns `cjs_status`: `CJS_OK` (0), `CJS_INVALID_ARGUMENT` (a NULL handle,
  an out-of-range value), `CJS_INVALID_UTF8`, `CJS_INVALID_JSON`, `CJS_COMPILATION_FAILED` (an unresolvable
  reference, an invalid pattern), `CJS_DEPTH_EXCEEDED` (a schema that recurses in place beyond the maximum depth),
  `CJS_PANIC` (a bug in the library). The message, and for invalid JSON the byte offset, are in thread-local
  storage until the thread's next call: `cjs_last_error_message()`, `cjs_last_error_offset()`.
- **Results come through out-parameters**, so a valid instance and a failed call cannot be confused:
  `cjs_status cjs_validator_validate_json(const cjs_validator *, const char *json, size_t len, bool *valid)`.
- **No unwinding across the boundary.** Every function catches Rust panics (`CJS_PANIC`; the library is built with
  `panic = "unwind"`, the crate's own release profile notwithstanding). Callbacks must not unwind into the library:
  C++ exceptions are caught in the C++ wrapper's trampolines.

## API

### Version

```c
uint32_t cjs_version(void);          /* (major << 16) | (minor << 8) | patch, of the library */
cjs_str  cjs_version_string(void);   /* "0.1.0" */
#define CJS_VERSION_MAJOR 0           /* ...and MINOR, PATCH: the header's version, to compare with cjs_version() */
```

### Options

A builder, so that options can be added without breaking the ABI.

```c
cjs_options *cjs_options_new(void);
void         cjs_options_free(cjs_options *);
cjs_status cjs_options_set_default_dialect(cjs_options *, cjs_dialect);   /* CJS_DRAFT4 ... CJS_DRAFT202012 */
cjs_status cjs_options_set_assert_format(cjs_options *, cjs_tristate);    /* CJS_DEFAULT, CJS_TRUE, CJS_FALSE */
cjs_status cjs_options_set_assert_format_in_legacy_drafts(cjs_options *, bool);
cjs_status cjs_options_set_assert_content(cjs_options *, bool);
cjs_status cjs_options_set_base_uri(cjs_options *, const char *, size_t);
cjs_status cjs_options_set_entry_point(cjs_options *, const char *, size_t);
cjs_status cjs_options_set_max_depth(cjs_options *, uint32_t);
cjs_status cjs_options_add_format(cjs_options *, const char *name, size_t name_len,
                                  cjs_format_fn, void *user_data, cjs_free_fn free_user_data);
cjs_status cjs_options_set_resolver(cjs_options *, cjs_resolve_fn, void *user_data, cjs_free_fn free_user_data);
```

### Callbacks

```c
typedef void (*cjs_free_fn)(void *user_data);
/* A format assertion: whether the string (or a number's JSON text) is valid. */
typedef bool (*cjs_format_fn)(void *user_data, const char *value, size_t len);
/* A document resolver: for an absolute URI, the document's JSON text through cjs_resolved_set_json (which copies
   it), or nothing for an unknown document. A status other than CJS_OK fails the compilation. */
typedef cjs_status (*cjs_resolve_fn)(void *user_data, const char *uri, size_t uri_len, cjs_resolved *out);
cjs_status cjs_resolved_set_json(cjs_resolved *, const char *json, size_t len);
```

- A format callback runs during validation, on whichever thread validates, so it must be thread-safe (a validator
  is shared between threads). The resolver runs only during compilation, on the compiling thread.
- `user_data` lives as long as anything uses it: the options and every validator compiled from them hold a
  reference, and `free_user_data` (may be NULL) runs when the last one is freed.

### Validators

```c
cjs_status cjs_compile(const char *schema, size_t len, const cjs_options * /* NULL: defaults */, cjs_validator **out);
cjs_status cjs_compile_uri(const char *uri, size_t len, const cjs_options *, cjs_validator **out);
cjs_validator *cjs_validator_clone(const cjs_validator *);   /* cheap: shares the compiled program */
void           cjs_validator_free(cjs_validator *);

cjs_status cjs_validator_validate_json(const cjs_validator *, const char *json, size_t len, bool *valid);
cjs_status cjs_validator_validate_document(const cjs_validator *, const cjs_document *, bool *valid);
cjs_status cjs_validator_evaluate_json(const cjs_validator *, const char *json, size_t len,
                                       cjs_collector *, bool *valid);
cjs_status cjs_validator_evaluate_document(const cjs_validator *, const cjs_document *, cjs_collector *, bool *valid);
```

- A validator is immutable: any number of threads may use one at once.
- `validate_json` is the main path: it parses into per-thread buffers and validates in place, with no allocation in
  the steady state. This needs a crate addition, `Validator::validate_json(&str)`, which parses into the
  `JsonDocument` parser's reused buffers and evaluates them before they are released (no `JsonDocument` is built).
  The Python binding's `is_valid_json` gains it too.

### Documents

For an instance validated more than once, or against several schemas: the text is parsed once.

```c
cjs_status cjs_document_parse(const char *json, size_t len, cjs_document **out);           /* copies the text */
cjs_status cjs_document_parse_borrowed(const char *json, size_t len, cjs_document **out);  /* text must outlive it */
void       cjs_document_free(cjs_document *);
```

A document is immutable and may be shared between threads.

### Results

```c
cjs_collector *cjs_collector_new(cjs_results_level);   /* CJS_BASIC, CJS_DETAILED, CJS_VERBOSE */
void           cjs_collector_free(cjs_collector *);
void           cjs_collector_clear(cjs_collector *);
size_t         cjs_collector_count(const cjs_collector *);
/* Row i's fields; the views are valid until the collector is next evaluated into, cleared or freed. */
bool    cjs_collector_is_match(const cjs_collector *, size_t i);
cjs_str cjs_collector_message(const cjs_collector *, size_t i);
cjs_str cjs_collector_evaluation_location(const cjs_collector *, size_t i);
cjs_str cjs_collector_schema_location(const cjs_collector *, size_t i);
cjs_str cjs_collector_instance_location(const cjs_collector *, size_t i);
/* The annotations of a verbose evaluation as JSON text, grouped by instance location, keyword and schema location
   (the crate's collect_annotations); valid until the collector next changes. */
cjs_status cjs_collector_annotations_json(cjs_collector *, cjs_str *out);
```

A collector is used by one thread at a time. Rows are read through functions rather than a struct, so rows can gain
fields without breaking the ABI.

## The C++ wrapper

`corvus_json_schema.hpp`, header-only, C++17, namespace `corvus::json_schema`:

- `validator` (copy is `cjs_validator_clone`, move transfers), `options` (a builder), `document`, `collector`, each
  owning its handle (RAII).
- Inputs as `std::string_view`; outputs as `std::string_view` (views with the C lifetimes above).
- Errors as exceptions: `corvus::json_schema::error`, with the `cjs_status`, the message and the offset.
  `validator::try_validate(...)` returns the status instead, for code built without exceptions.
- Format validators and resolvers as `std::function`, kept alive through `user_data` and freed by `free_user_data`;
  the trampolines catch exceptions (a throwing format validator reports invalid, a throwing resolver fails the
  compilation with its message).

A later addition, not in the first version: validating a C++ DOM the caller already holds (nlohmann::json,
simdjson, RapidJSON) without serialising it, through a table of callbacks implementing the crate's `Instance` trait.
A call per value makes that slower than `validate_json` on text, so it is only for callers whose data is already
parsed.

## Threading and memory

- Validators and documents are immutable and thread-safe. Options and collectors are not: one thread at a time.
- Every handle is freed by its `_free` function; nothing else the library returns needs freeing.
- Parsing reuses per-thread buffers (released above 16 MiB of nodes), as `JsonDocument::parse` does.

## Versioning and compatibility

- The library is versioned independently (`Cargo.toml`), like the crate and the Python and TypeScript packages, and
  tagged `capi-v<version>`. Before 1.0, a minor version may break the ABI; from 1.0, only a major one.
- Adding functions or enum values is not a breaking change; changing a signature, a struct (`cjs_str`) or an enum
  value is.
- `cjs_version()` lets a caller check at run time that the library it loaded matches the header it compiled with.

## Distribution

- A release builds the shared and static libraries for Linux (x86_64, aarch64; glibc and musl), macOS (universal2)
  and Windows (x64, arm64), and attaches archives with the headers, the CMake package configuration and the
  pkg-config file to a GitHub release (`capi-publish.yml`, on a version change, honouring `no_release`).
- vcpkg and Conan ports later. Swift gets an XCFramework from the macOS build.

## Testing

- **Rust tests through the C functions** (the crate's rlib, so `cargo test` covers them): the whole
  JSON-Schema-Test-Suite through `cjs_compile` and `cjs_validator_validate_json`, and through a collector at each
  level, compared row by row with the crate's own results; errors, invalid UTF-8 and JSON, callbacks (including one
  that fails), threads sharing a validator.
- **C and C++ tests** with CMake, against the built libraries (shared and static) on Linux, macOS and Windows; on
  Linux also under AddressSanitizer and UndefinedBehaviorSanitizer.
- **cbindgen**: CI regenerates the header and fails if it differs from the committed one.
- **Performance**: a C++ implementation of the jsonschema-benchmark protocol (parse, compile, cold, warm) in the
  benchmark's harness, pinned, against Blaze and against the Rust `corvus-rs`: the gate above, and the cost of the
  C boundary.

## Other languages

- **Swift** uses this library: a SwiftPM package with a binary target (an XCFramework for Apple platforms; Linux to
  be decided once the package layout is known), and a Swift API over it.
- **Ruby and PHP** bind the crate directly from Rust (magnus, ext-php-rs), each with an `Instance` implementation
  that reads the language's own values in place, as the Python binding does: through a C library they would have to
  serialise every value first, or pay a callback per value.
